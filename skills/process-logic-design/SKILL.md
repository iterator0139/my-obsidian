# 流程逻辑梳理

先证明流程能够闭合，再做架构或任务拆分。不要用模块、类、接口或技术名词替代流程结论。

## 输入与边界

1. 阅读当前需求、权威设计、基线行为和相关测试；区分已证实事实、目标承诺与假设。
2. 明确本次讨论的起点、终点和排除范围。把正常路径、异常中断和未确认的延伸范围分开。
3. 列出参与方，以及每个参与方能读取、能修改、能触发的事实或效果。
4. 区分持久化事实、运行时状态和外部观察结果；不得用任一类替代另一类。

关键信息未知时，记录为待决问题；不要据此发明实现或拆开发任务。

## 先画图，再写说明

流程图是必需产物，不是可选装饰。使用 Mermaid `flowchart`、`stateDiagram-v2`、`sequenceDiagram`
或最能准确表达关系的图；图中必须写出条件、分支合流、并发开始点和退出条件。

先绘制一张**总流程图**，表示从触发到最终结论的全局路径。总图只保留：

- 主要阶段；
- 持久化或不可逆效果；
- 关键判断；
- 子流程入口和最终出口。

当某一节点包含任一情形时，把它展开为独立的**子流程图**：多个条件分支、循环、并行活动、
外部效果、失败处理，或无法用一句话准确描述的步骤。总图节点用子流程名称引用它；子流程
只解释该节点内部，不重复整个总图。必要时继续分层，直到每张图都能被读者独立复述。

不要把并发关系画成顺序关系。对每个等待、循环或监听，图和文字都必须说明“仅当什么条件成立时退出”。

## 必须梳理的逻辑

用状态、条件和结果描述下列内容，不写类名或函数签名：

1. **事实与状态**：每个事实由谁维护、保存在哪里、谁能观察、哪些转换合法。
2. **主路径**：从触发到最终结论的严格顺序；注明每次持久化、外部效果和可见输出。
3. **分支路径**：重复、缺失、延迟、失败、并发和未知结果分别如何处理。
4. **重入路径**：已有过程结束或中断后，如何依据持久化事实确定当前位置；哪些工作绝不重做。
5. **退出规则**：每个子流程、循环和后台活动的正向退出条件。

## 外部效果检查

对每个不可逆效果，明确回答：

1. 效果前持久化了什么意图或状态？
2. 明确成功、明确失败、结果未知时，各自如何观察和收敛？
3. 重试会不会重复产生效果？若会，什么机制实际提供去重？
4. 效果后运行时中断会留下什么可用事实？

不得将条件写入、锁、消息送达或状态查询泛化成它们没有提供的保证。先写出该机制的确切保证，
再判断是否覆盖所需性质。

## 设计文档模板

```markdown
# <主题>流程逻辑设计

> 状态：草案 / 已确认
> 本文在架构与任务拆分之前定义流程，不定义实现结构。

## 1. 目标、范围与术语
## 2. 已确认事实、假设与待决问题
## 3. 状态与事实表
## 4. 总流程图
## 5. 子流程图
### 5.1 <总图节点一>
### 5.2 <总图节点二>
## 6. 分支、失败、并发与未知结果
## 7. 重入与不重做规则
## 8. 不变量与退出条件
## 9. 架构与任务拆分门禁
```

总流程图和所有必要子流程图必须位于正文中。若无法画出某个节点的子流程，说明该节点的
输入、状态或结果尚未定义；停在待决问题，不进入下一阶段。

## 进入下一阶段的门禁

仅当以下问题都有明确答案时，才进入能力契约、责任架构或开发任务拆分：

- 每条触发路径如何到达可观察结论；
- 每个状态由谁写入，谁只读取；
- 过程如何重入，已完成工作如何跳过；
- 并发、重复和未知结果没有未解释的效果；
- 每个活动都有明确退出条件；
- 未解决的外部语义已列为独立验证门禁。

完成后，输出“可拆分结论”：按总图中的真实交接边界划分可独立实现的切片；不要按文件、类或技术名词切分。
