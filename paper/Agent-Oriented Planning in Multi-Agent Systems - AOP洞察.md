# Agent-Oriented Planning in Multi-Agent Systems：洞察与规律

> 论文：Ao Li 等，[[https://arxiv.org/abs/2410.02189|Agent-Oriented Planning in Multi-Agent Systems]]（AOP）

## 一句话总结

AOP 研究的不是如何让单个 Agent 更聪明，而是如何让多个能力不同的 Agent 被可靠地组织起来：任务要拆得可执行、覆盖完整、彼此不重复，并且能根据执行反馈持续修正。

## 论文解决的问题

多 Agent 系统通常有一个 meta-agent 负责拆解用户问题和分配 Agent。仅靠 prompt 进行规划容易出现三类失败：

- **不可解决**：子任务和 Agent 能力不匹配，或子任务本身过于复杂。
- **不完整**：拆分后遗漏关键要求、上下文或前置依赖。
- **冗余**：多个 Agent 重复搜索、计算或分析同一内容。

因此，好的规划不能只问“应该拆成哪些任务”，还要问“谁能做、是否做全、是否重复”。

## AOP 的核心机制

```text
用户问题
  ↓
快速拆分与初步分配
  ↓
Reward Model：评估子任务—Agent 是否匹配
  ↓
任务修改：重新描述或继续拆分
  ↓
Detector：检查完整性、依赖和冗余
  ↓
Agent 执行
  ↓
反馈循环：必要时重新规划
```

### 1. Reward Model：预测谁能解决什么

模型输入是子任务和 Agent 的能力描述，输出二者匹配的质量分数：

```text
score = M(子任务，Agent 描述)
```

训练数据通过实际调用多个候选 Agent 获得，再由 scorer 按正确性、相关性和完整性评分。Reward Model 学习预测这个质量分数，从而在正式执行前筛掉明显不合适的分配。

推理时：

- 分数高：接受当前分配；
- 分数低：比较所有 Agent，选择最高分者；
- 所有 Agent 分数都低：认为任务对单个 Agent 过于复杂，需要重新拆分。

### 2. Sub-Task Modifications：区分“不会做”和“没说清楚”

如果一个 Agent 看起来有能力，但子任务仍可能执行不好，AOP 使用该 Agent 的代表性成功任务进行相似度比较。

- 与历史成功任务相似：Agent 可能有能力，只是当前任务缺少上下文，要求 meta-agent **重新描述任务**。
- 与历史任务都不相似：任务可能过于复杂，要求 meta-agent **详细拆分任务**。

这是一条重要规律：任务失败不一定意味着 Agent 能力不足，也可能是任务描述没有提供执行所需的信息。

### 3. Detector：检查完整性、冗余和隐藏依赖

Detector 由 LLM 通过 role-play prompt 实现：

- 从原始问题提取关键要求，并逐项匹配子任务；
- 检查子任务是否需要尚未提供的前置依赖；
- 比较子任务之间是否重复或对最终答案没有贡献；
- 输出缺失信息、冗余任务以及增加、删除、合并任务的建议。

如果发现依赖缺失，meta-agent 会增加获取依赖信息的子任务，并把结果传给依赖它的后续任务。

## 实验得到的规律

### 1. 规划质量比 Agent 数量更重要

主实验中 AOP 的准确率为 43.7%，高于 GPT-4o（33.3%）和 HUSKY（39.6%）。但 AOP 也使用了更多 token 和时间，说明收益主要来自更可靠的规划，而不是低成本。

### 2. 三个原则确实对应不同的失败来源

定量评估中，AOP 相比 GPT-4o 的平均得分为：

| 原则 | GPT-4o | AOP |
|---|---:|---:|
| 可解决性 | 0.763 | 0.938 |
| 完整性 | 0.822 | 0.969 |
| 非冗余性 | 0.986 | 0.993 |

最明显的提升在可解决性和完整性，说明“分错 Agent”和“漏掉任务”比重复任务更关键。

### 3. Detector 是影响最大的组件

消融实验：

| 方法 | 准确率 |
|---|---:|
| AOP | 43.7% |
| 去掉 Detector | 36.6% |
| 去掉 Reward Model | 38.7% |
| 去掉 Representative Works | 41.1% |

去掉 Detector 后下降最大，说明计划审查不是附加功能，而是多 Agent 系统稳定性的核心。

### 4. 静态能力描述与动态历史能力互补

自然语言描述表达 Agent 的一般能力，representative works 表达 Agent 过去实际成功完成过的任务。两者结合比单独使用任一表示更好：

| Agent 表示 | 准确率 |
|---|---:|
| 只有自然语言描述 | 31.8% |
| 只有代表性任务 | 16.8% |
| 两者结合 | 43.7% |

规律是：静态描述适合做粗粒度筛选，历史成功案例适合做具体任务匹配。

### 5. 更强的专业 Agent 可以进一步放大规划收益

使用 Qwen2-Math-7B 和 DeepSeek-Coder-V2 替换部分通用 Agent 后，Husky-QA 准确率额外提升约 1.8%。在 MATH 实验中，多个数学 Agent 协作的 AOP 达到 72%，高于单独使用 GPT-4o 或 Qwen2-Math-7B。

因此，AOP 与“专家模型”是互补关系：专家模型提供能力，AOP 负责把能力分配到正确的子任务。

### 6. 隐藏依赖是一个独立的错误来源

开启 Detector 的缺失依赖处理后，准确率从 43.7% 提升到 46.2%。这说明即使任务拆分表面上完整，任务之间的输入依赖仍可能没有显式表达。

## 可迁移的设计规律

### 规律一：不要只做任务分解，要做任务验证

```text
生成计划 ≠ 验证计划
```

规划系统应在执行前验证：任务是否可执行、输入是否充分、任务之间是否重叠。

### 规律二：把“不可执行”拆成三种原因

发现任务失败时，应区分：

1. Agent 能力不匹配；
2. Agent 有能力，但任务描述不完整；
3. 任务本身过于复杂，需要继续分解。

三种原因对应三种不同修复动作：换 Agent、重写任务、继续拆分。

### 规律三：计划需要反馈闭环

一次性生成完整计划很脆弱。更可靠的系统应允许执行结果反过来影响后续计划：补充任务、修改任务描述、重新分配 Agent 或调整依赖关系。

### 规律四：Agent 数量增加后需要分层选择

Agent 太多会带来上下文窗口压力和能力相近的问题。可先按能力分组，再先选择 Agent 组、后选择组内 Agent：

```text
所有 Agent → 数学/搜索/代码/写作分组 → 组内选择具体 Agent
```

### 规律五：多 Agent 的价值取决于任务可并行性

如果问题能够拆成相互独立的搜索、计算、分析任务，多 Agent 更有价值；如果所有步骤高度串行，增加 Agent 可能只增加通信和调度成本。

## 对实际系统设计的启示

一个可落地的多 Agent 系统至少需要维护四类信息：

1. **能力目录**：每个 Agent 能做什么、不能做什么；
2. **任务状态**：任务是否已完成、失败或需要重试；
3. **依赖图**：某个任务需要哪些前置结果；
4. **成功案例库**：Agent 过去解决过哪些相似任务。

在工程实现上，最值得优先加入的不是更多 Agent，而是：

- 一个任务—Agent 匹配器；
- 一个计划完整性/冗余审查器；
- 一个显式依赖管理机制；
- 一个基于执行结果的重规划循环。

## 局限与批判性观察

- 主实验主要基于 Husky-QA 数值推理任务，虽然能验证协作机制，但不等同于所有开放式现实任务。
- Reward Model 的训练数据依赖 scorer；人工评分和全参数微调可以继续提升准确率，说明评估器质量会影响 AOP。
- Detector 主要通过 LLM prompt 实现，存在评估不稳定和提示词依赖问题。
- AOP 提高了准确率，但带来了更多 token 消耗和执行时间，实际应用需要根据任务价值决定是否启用完整规划流程。
- Agent 数量并非越多越好；当上下文、通信和重复能力成为瓶颈时，需要分组、筛选或限制候选 Agent。

## 最终洞察

这篇论文最重要的贡献不是提出一个更复杂的 Agent 编排流程，而是把多 Agent 规划从“凭经验写 prompt”转变为一个可检查、可修正的系统工程问题：

```text
规划质量 = 可解决性 × 完整性 × 非冗余性 × 依赖正确性
```

多 Agent 系统的瓶颈通常不是“有没有足够多的 Agent”，而是“能否把正确的任务交给正确的 Agent，并保证任务之间的信息流动是完整且不重复的”。
