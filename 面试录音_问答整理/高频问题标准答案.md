# 高频问题标准答案

> 用途：面试前口播练习。每个问题都按“答题思路 + 完整回答”整理，尽量结合你当前最核心的场景：Shopee 广告系统、商家运营智能助手、多 Agent、记忆、RAG、Text-to-SQL、评测和业务落地。

## 使用方法

不要逐字背诵，建议固定每题的结构：

1. 先给结论；
2. 再讲背景和问题；
3. 然后讲你的方案；
4. 补一个真实例子或指标；
5. 最后主动讲边界和下一步。

口语上尽量少说“然后”“这个”“这样一个”。可以用“第一、第二、第三”“我的判断是”“边界上”来替代。

## 1. 请做一个自我介绍

### 答题思路

用 90 秒讲清三件事：你现在做什么、做过哪两个核心项目、你想让面试官记住什么标签。重点不是罗列经历，而是把自己定位成“在线 AI/Agent 工程落地型候选人”。

### 完整回答

面试官您好，我叫陈宏，目前在 Shopee 主要做广告系统和 Agent 架构相关的工作。我的经历可以概括成两条主线。

第一条是广告系统工程。我作为核心开发参与了垂类广告系统从 0 到 1 的搭建，包括在线引擎、数据流、计费链路，以及预算平滑、预估校准、排序公式等广告机制策略。这个阶段让我对高并发在线系统、广告投放链路和算法策略落地有比较深入的理解。

第二条是商家运营智能助手 Agent。我主导了一个面向广告运营的 Agent 系统，解决运营在知识查询、数据查询和复杂归因诊断三个场景下效率低的问题。技术上做了意图路由、多 Agent 调度、四层记忆、Agentic RAG、Text-to-SQL 和评测闭环。这个项目让我比较系统地沉淀了 Agent 从 demo 到生产系统落地需要解决的问题，比如可控性、上下文管理、工具治理、失败处理和效果评估。

更早之前我在百度做机器学习平台和模型调研平台，所以整体上我比较擅长在线 AI 系统里算法、工程和业务之间的结合。接下来我也希望继续深耕 Agent 工程方向，把复杂业务场景里的自动化能力真正做成可靠可用的生产系统。

## 2. 介绍一下商家运营智能助手项目

### 答题思路

先讲业务背景，再讲三类场景，最后讲架构。不要一上来堆 Agent 名词。

### 完整回答

这个项目的背景是 Shopee 广告系统持续演进后，广告策略、投放规则和数据链路都变得越来越复杂，运营同学在日常工作里有很多重复但又依赖专业知识的任务。我们梳理下来主要有三个高频痛点。

第一是知识查询。广告机制、策略规则、操作 SOP 分散在不同文档里，运营要靠人工翻文档和问研发，效率比较低。第二是数据查询。运营经常需要看广告组、商家、市场维度的投放表现，过去很多查询要提给数据同学或研发同学。第三是复杂归因诊断，比如曝光下降、ROI 下降、预算消耗异常，要结合多张表、多个指标和广告机制判断原因。

所以我们做了一个面向广告运营的智能助手。架构上先用意图识别把用户请求分到知识查询、数据查询、复杂诊断、闲聊和 unknown 几类；知识查询走 Agentic RAG，数据查询走相对固定的 Text-to-SQL workflow，复杂归因诊断走 Plan/Execute 的多 Agent 架构。为了支撑长程任务，我们还设计了短期记忆、工作区记忆、文件系统记忆和长期记忆，分别解决对话连续性、任务状态保持、大工具结果外置和历史经验沉淀。

这个项目不是单纯的问答 demo，而是内部运营真实使用的工具。当前知识查询和单表数据查询相对成熟，复杂归因诊断也能覆盖一部分结构化路径明确的问题，但对长期策略优化和跨系统自动执行仍然需要继续演进。

## 3. 你们一开始怎么选择业务场景？怎么判断价值？

### 答题思路

回答“不是拍脑袋选 Agent 场景”，而是从运营工作流、使用频次、效率卡点、可落地性四个维度选。

### 完整回答

我们不是先有 Agent 再找场景，而是先从运营的实际工作流里找效率瓶颈。广告运营的日常流程大概包括计划创建、投放盯盘、异常发现、归因诊断、优化建议和复盘。我们会和运营同学反复沟通，把他们日常最常问、最耗时、最依赖研发或数据团队的问题整理出来。

判断场景价值时，我主要看四个维度。第一是使用频次，如果一个问题每天都会发生，自动化收益就比较稳定。第二是效率卡点，也就是原来人工处理要花多久、涉及多少人。第三是影响范围，看它是只影响一个运营，还是能覆盖整个广告运营团队。第四是可落地性，因为不是所有复杂任务都适合第一阶段自动化。

基于这个判断，我们第一期选择了知识查询、数据查询和复杂归因诊断。知识查询频次高、文档分散；数据查询能明显减少人工取数；复杂归因虽然难，但业务价值高，过去经常需要研发和策略同学介入。这样选出来的场景既有短期可交付价值，也能沉淀 Agent 长程任务能力。

## 4. 为什么要用多 Agent，而不是一个 Agent 解决所有问题？

### 答题思路

核心是任务形态不同：知识查询、数据查询、复杂诊断不是同一种问题。强调“不是为了追概念”，并主动说明什么时候不用多 Agent。

### 完整回答

我们不是为了追概念才做多 Agent，而是因为这三个场景的任务形态差异很大。

知识查询本质上更像检索增强生成，关键是召回完整证据和避免幻觉；数据查询链路相对固定，更适合 workflow 化的 Text-to-SQL；复杂归因诊断是长程任务，需要多步规划、调用多个工具、分析中间结果、做失败处理和局部重试。如果把这些能力都塞进一个 Agent，prompt 会越来越大，工具集合也会过宽，模型容易出现目标漂移、上下文膨胀和无效工具调用。

所以我们先用意图识别做一级路由，把固定链路和开放链路分开。复杂归因诊断再由主 Agent 做 plan，把任务拆成 DAG 节点，委派给不同 subagent 执行。每个 subagent 只拿自己的目标、必要上下文和工具，执行后把 summary 和 evidence 回传给主 Agent。这样做有三个收益：职责更清晰，上下文天然隔离；部分节点可以并行执行；失败时能定位到节点级别，方便重试或局部 replan。

边界上，如果任务是强流程、强约束、步骤稳定的，我会优先用 workflow 或 Skill，不会为了用多 Agent 而用多 Agent。多 Agent 更适合不确定性更强、需要动态规划的复杂任务。

## 5. 你们整体技术架构是什么？

### 答题思路

按“入口层、能力层、长程任务层、治理层”讲，比直接列模块更清晰。

### 完整回答

整体架构可以分成四层。

第一层是入口和意图识别层。用户 query 进来后，我们先做基础预处理和意图识别，把请求分成知识查询、数据查询、复杂归因诊断、闲聊和 unknown。对于 unknown 或信息不足的请求，会引导用户补充条件，而不是直接执行。

第二层是场景能力层。知识查询走 Agentic RAG，通过多轮检索、父子 chunk 和章节回溯解决文档碎片化问题；数据查询走 Text-to-SQL workflow，包括 query 改写、表列召回、列值探测、SQL 生成、执行纠错和共识投票；复杂归因诊断走 Plan/Execute 多 Agent。

第三层是长程任务执行层。Planner 会把复杂任务拆成 DAG，每个节点包含任务说明、输入输出、依赖关系和预期 evidence。执行器按依赖关系调度 subagent 或工具，支持并发执行、重试、失败标记和局部 replan。

第四层是治理和评测层。这里包括工具权限、参数校验、超时重试、上下文压缩、四层记忆、日志记录、离线 Golden Set 评测和线上采纳率监控。我的理解是，Agent 要从 demo 变成生产系统，关键不只是模型调用，而是这些治理能力要跟上。

## 6. Plan/Execute 是怎么工作的？

### 答题思路

强调“把复杂任务变成可校验、可调度、可回放的 DAG”。回答要包含输入、输出、校验、执行、汇总。

### 完整回答

Plan/Execute 的核心是把一个开放的复杂任务转成可校验、可调度、可回放的 DAG。

在 Plan 阶段，我们会把用户 query、业务边界、系统工具能力、few-shot 样例、历史 SOP 或长期记忆一起拼进 prompt，让强模型输出一个结构化 JSON。这个 JSON 里每个节点会包含 role、instruction、input、output、dependency 和 expected evidence。dependency 用来表达节点之间的前后依赖关系。

生成 DAG 后，不会直接执行，而是先做两层校验。第一层是结构校验，比如字段是否完整、依赖关系是否有环、是否有孤立节点、JSON 格式是否满足 schema。第二层是语义校验，用 rubric 判断任务拆分是否合理、节点是否可执行、是否越过系统能力、粒度是否过粗或过细。

执行阶段会按 DAG 的拓扑关系调度。没有前置依赖的节点可以并发执行；每个 subagent 只拿到它需要的上下文和工具，避免把全部历史塞进去。执行完成后，每个节点返回 summary、关键结果和 evidence，主 Agent 再汇总这些结果，判断是直接回答用户，还是需要 replan。

这样做的价值是把长程任务的不可控性限制在节点级别，也让失败定位、回放和评测都更容易。

## 7. 子任务失败怎么办？拆分不合理怎么办？

### 答题思路

分三类：计划生成失败、工具偶发失败、结构性失败。主动讲局部 replan 和下游节点传播。

### 完整回答

我们把失败分成几个阶段处理。

第一类是 Plan 阶段失败。模型生成的 DAG 可能格式不对、依赖有环、字段缺失，或者语义上不可执行。结构问题会走 schema 和 DAG 校验，不通过就带错误信息 replan。语义问题会用 LLM judge 按 rubric 评估，比如节点是否越权、是否缺少关键步骤、拆分粒度是否合理，不通过也会重新规划。

第二类是执行阶段的偶发失败，比如工具超时、参数格式错误、下游服务短暂不可用。这类问题通常可以带错误信息做有限次重试，同时设置超时、最大步数和熔断，避免 Agent 空转。

第三类是结构性失败，比如某个节点确实拿不到必要数据，或者执行结果证明原计划缺少关键步骤。这时不会简单重跑整条链路，而是把当前节点标记失败，并把依赖它的下游节点标记为受影响，然后把失败原因、已有 evidence 和当前状态返回给 planner 做局部 replan。前面已经成功的中间结果可以继续复用。

我觉得这里最重要的是失败要有 evidence。不能只告诉模型“失败了”，而要告诉它失败在哪个节点、失败原因是什么、影响哪些下游目标。这样 replan 才不是盲目重新生成。

## 8. 四层记忆分别是什么？为什么这么设计？

### 答题思路

每层绑定一个问题：短期连续性、工作区防漂移、文件系统外置大结果、长期经验复用。

### 完整回答

我们把记忆拆成四层，是因为 Agent 在长程任务里遇到的问题不止一个，不能都靠对话 history 解决。

第一层是短期记忆，也就是当前 session 的对话历史和推理过程，主要解决多轮交互的连续性。第二层是工作区记忆，用来保存当前任务的 plan、todo、关键中间状态和当前目标，主要解决长程任务执行过程中目标漂移的问题。第三层是文件系统记忆，用来外置比较大的工具结果，比如 SQL 查询结果、日志片段、表格数据、报告草稿，prompt 里只保留摘要和引用，避免上下文膨胀。第四层是长期记忆，主要沉淀用户偏好和成功任务经验，下次类似 query 进来时可以检索出来拼进 prime。

读写时机上，任务开始时会根据 query 检索长期记忆并组装 prompt；执行过程中工作区会持续更新 plan 和 todo；上下文达到阈值后会压缩，保留最初目标和最近上下文，中间部分摘要并外置到文件系统；任务结束后再抽取可复用经验进入长期记忆。

这套设计的核心不是让 Agent “记得越多越好”，而是把不同生命周期、不同体积、不同可信度的信息放到不同位置，减少上下文污染和目标漂移。

## 9. 如果机器挂了，记忆是不是就丢了？怎么做高可用？

### 答题思路

这是你的短板题，要诚实区分“当前项目现状”和“生产化演进”。不要硬说已经完善。

### 完整回答

这个问题要分当前项目现状和生产化演进来看。

在我们当前项目里，四层记忆主要是为了解决单个长程任务的上下文管理问题，不是一个完全成熟的分布式状态系统。所以如果只看当前实现，工作区状态和部分中间文件的高可用能力确实还不够完善，机器异常时恢复能力有限。

如果要把它做成更严格的生产化系统，我会从三层改造。第一是状态持久化，把 task id、session id、plan、todo、节点状态、工具调用结果和文件系统引用都写到持久化存储，而不是只放在进程内存。第二是 checkpoint 机制，每个 DAG 节点执行完成后写 checkpoint，机器挂了可以从最近成功节点恢复，而不是整条链路重跑。第三是路由和幂等，同一个 task 后续请求可以根据 task id 找到状态；工具调用要有 request id 和幂等设计，避免恢复后重复执行产生副作用。

长期记忆还要单独做准入和回滚，因为它会影响未来任务。比如只有经过 judge 或人工确认的成功经验才能写入，发现污染后要能删除或降权。我的判断是，Agent 记忆要生产化，不能只看 prompt 设计，必须把它当成一套状态管理和数据治理系统来做。

## 10. 为什么从普通 RAG 升级到 Agentic RAG？

### 答题思路

用一个 SOP bad case 说明普通 RAG 的问题，再讲索引侧和推理侧两类优化。

### 完整回答

普通 RAG 最大的问题不是完全搜不到，而是对 SOP、多跳问题和条件链条不稳定。

比如运营问一个预算分配 SOP，关键前置条件可能在上一节或相邻段落里，单次向量检索只命中了操作步骤，没有命中前置约束。模型拿到不完整上下文后，可能生成一个看起来合理但实际执行不通的答案。还有一些归因类问题，需要先理解问题，再查指标定义，再查异常原因，单次检索很容易漏信息。

所以我们做了两类改造。第一类是索引侧，用父子 chunk、相邻窗口和章节回溯解决上下文碎片化。检索时可以先用细粒度 chunk 提高命中率，再回溯到更大的父 chunk 补全上下文。第二类是推理侧，用 Agentic RAG 或 ReAct 范式，让模型看到 observation 后决定是否继续检索、换 query、扩大范围或停止。

当然不是所有 query 都需要多轮检索。简单事实类问题走低延迟路径就够了，只有 SOP、多跳诊断、信息不完整的问题才走 Agentic RAG。后续更理想的是加后置 verifier，如果答案证据不足或引用冲突，再触发二次检索，而不是固定多轮。

## 11. RAG 怎么评估效果？

### 答题思路

不要只说 LLM judge。按检索、答案、线上采纳三层讲。

### 完整回答

RAG 的评估我会拆成三层。

第一层是检索层，关注有没有把正确证据召回。这里可以看 recall@k、MRR、NDCG，也可以对关键文档或关键 chunk 做人工标注，看目标证据是否出现在 top k 里。对于 SOP 类问题，单看 chunk 命中还不够，还要看前置条件和步骤是否都被召回。

第二层是答案层，关注生成结果是否正确、是否有引用、是否幻觉。短答案可以用关键词、实体 F1 或规则打分；开放答案可以用 LLM judge，但要固定 judge 模型版本、rubric 和 few-shot，同时保留人工锚点样本，避免模型升级导致评测漂移。

第三层是线上业务层，关注运营是否采纳、是否二次追问、是否需要转人工、平均节省多少时间。因为 RAG 最终不是为了离线分数好看，而是要让运营能少翻文档、少问研发。

我们当前的评测会结合 Golden Set、人工抽检和线上反馈。后续我会更重视 bad case 回流，把线上答错、证据缺失、用户不采纳的 case 持续加入测试集。

## 12. Agent 评测体系怎么构建？

### 答题思路

按“结果正确性、过程可靠性、业务有效性”三层讲，再解释为什么多评分器。

### 完整回答

我会把 Agent 评测分成三层：结果正确性、过程可靠性和业务有效性。

第一层是结果是否正确。不同任务要用不同评分器。Text-to-SQL 可以看 execution match，也就是 SQL 执行结果是否和标准答案一致；RAG 可以看关键实体、引用证据和答案事实是否正确；复杂归因诊断可以看主因、辅因是否命中，以及最终建议是否可执行。

第二层是过程是否可靠。Agent 不只是最终答案对就行，中间过程也要可控。比如有没有无效工具调用、有没有漏掉关键 checkpoint、有没有越权查询、有没有在证据不足时强行下结论、是否进入死循环。这些过程指标能帮助我们定位到底是检索、规划、工具还是生成环节出了问题。

第三层是业务是否有效。线上我会看运营采纳率、人工二次修改率、转人工比例、平均处理时长和重复问题解决率。因为 Agent 的价值最终要落到业务效率，而不是只看离线准确率。

多评分器的原因是任务可判定性不同。SQL 可以用代码评测，开放问答只能部分用实体和规则，复杂诊断需要 LLM judge 和人工抽检结合。为了降低 LLM judge 的不确定性，我们会固定 judge 版本、使用 rubric、加入人工锚点样本，并持续把线上 bad case 回流到 Golden Set。这样评测系统才是一个持续演进的闭环。

## 13. LLM judge 本身不稳定，怎么保证评测科学性？

### 答题思路

承认 LLM judge 不适合当唯一真理。讲四件事：固定版本、rubric、人工锚点、多评分器交叉验证。

### 完整回答

LLM judge 确实不能当成唯一真理，尤其是开放问题和复杂诊断问题，模型版本变化、prompt 变化都会带来评分漂移。所以我的做法是把它作为评测体系的一部分，而不是全部。

第一，固定 judge 模型版本和评测 prompt。离线回归时不能频繁换 judge，否则分数变化可能来自 judge，而不是被测系统。第二，用明确 rubric 约束评分维度，比如事实正确性、证据完整性、是否越权推断、建议可执行性，而不是让模型泛泛地打一个总分。第三，保留人工标注的锚点样本，包括正例、负例和边界 case，每次评测都看 judge 在这些样本上的稳定性。第四，对可规则化的部分尽量不用 LLM judge，比如 SQL execution match、实体 F1、引用是否存在、工具调用次数、是否命中 checkpoint，都可以用程序评测。

所以我的理解是，评测科学性的关键不是完全不用 LLM judge，而是把主观判断拆小，把能规则化的部分规则化，把必须主观判断的部分用固定 judge、rubric 和人工锚点约束起来。

## 14. Text-to-SQL 是怎么做的？

### 答题思路

讲清为什么不能直接生成 SQL，以及每个阶段解决什么问题。

### 完整回答

我们没有直接让模型一次性生成 SQL，因为用户表达、业务口径、表名字段名之间有明显 gap，直接生成很容易出现表选错、字段选错、条件值不匹配和 SQL 幻觉。

所以我们把链路拆成几个阶段。第一步是 query 理解和改写，把用户自然语言里的业务对象、指标、时间范围、过滤条件抽出来。第二步是 schema linking，包括 table recall 和 column recall，先用表和字段的业务描述、使用场景、历史 case 做向量召回，再用 LLM 做语义选择。第三步是 column exploration，主要解决 value mismatch。比如用户说新加坡，但数据库里可能存的是 SG；用户说某类 campaign，但表里是枚举 code。我们会对关键枚举列查真实分布，把候选值补进上下文。第四步是 SQL 生成和执行纠错，如果执行报错，就把错误信息带回模型做反思修正。最后是共识机制，比如多次生成后如果执行结果一致或 SQL 结构一致，就采用更稳定的结果。

这套方案对单表和少量 join 的场景比较有效，核心收益来自 schema linking 和列值探测。当前难点是复杂多表 join，尤其是表关系隐含、业务口径不统一的时候，光靠 prompt 不够，需要表关系图谱、查询日志样本、标准指标层，甚至针对 SQL 生成做 SFT。

## 15. Value mismatch 怎么解决？

### 答题思路

用具体例子说清“用户词”和“数据库真实值”不一致，然后讲列值探测。

### 完整回答

Value mismatch 指的是用户 query 里的表达和数据库真实存储值不一致。比如用户说“新加坡市场”，模型可能生成 `region = 'Singapore'`，但库里实际存的是 `SG`；用户说“搜索广告”，表里可能存的是某个 campaign type code。如果不处理这个问题，表和字段都选对了，SQL 仍然会查不出结果。

我们的处理方式是在 schema linking 后增加 column exploration。对于被选中的关键列，尤其是枚举列和过滤条件相关列，会查询它的真实取值分布，把可能的枚举值、缩写、code 和样例补进上下文。对于数值列，会补充分布范围、单位和典型值，避免模型生成不合理条件。

这个机制的本质是把数据库真实世界的信息暴露给模型，而不是让模型靠先验猜。它对 region、campaign type、status、seller type 这类枚举字段特别有效。边界是如果业务口径本身不清楚，或者多个表对同一指标定义不同，还需要指标口径治理和标准语义层，不能只靠列值探测解决。

## 16. 复杂多表 join 怎么解决？

### 答题思路

这是高风险题。不要说“prompt 优化一下”。要讲表关系、指标层、日志样本、SFT、固定高频查询 Skill 化。

### 完整回答

复杂多表 join 是 Text-to-SQL 里最难的一类问题，因为它不只是 SQL 语法问题，而是业务建模问题。模型需要知道哪些表能 join、join key 是什么、时间粒度是否一致、指标口径是否一致，以及哪些过滤条件应该落在哪张表上。

我会分几层解决。第一层是补充表关系元数据，把常见表之间的 join key、主外键关系、时间粒度、适用场景维护成显式信息，而不是只给字段列表。第二层是建设指标语义层，把高频指标如 ROAS、GMV、cost、click、impression 的定义、口径和推荐查询路径沉淀下来，减少模型临时拼口径。第三层是利用历史查询日志，把真实用户 query 和人工 SQL 作为 few-shot 或训练样本，让模型学习公司内部常见 join pattern。第四层是对高频固定分析需求，不一定走自由 Text-to-SQL，而是沉淀成指标 API 或 Skill，让模型只负责参数填充。

如果数据量和样本足够，后续可以考虑做 SQL SFT 或者针对 schema linking 做专门模型。但我的判断是，复杂 join 的核心优先级应该是先把表关系和指标口径治理清楚，否则模型能力再强也会在业务歧义上犯错。

## 17. 项目效果怎么样？怎么定义成功？

### 答题思路

不要只报准确率。按“北极星指标 + 分场景指标 + 当前边界 + 下一步”回答。

### 完整回答

我们定义成功不是单看模型准确率，而是看运营能不能少找研发、少手工查数，并且最终结果能不能被采纳。

北极星指标主要是任务采纳率和人工节省时长。分场景看，知识查询关注答案正确率、引用证据和用户是否继续追问；数据查询关注 SQL execution accuracy、查询成功率和结果是否被使用；复杂归因诊断关注主因命中率、路径完整性、运营采纳率和是否减少研发介入。

从当前阶段看，知识查询和单表数据查询相对成熟，复杂归因诊断还更像运营 Copilot，而不是完全自动驾驶。它能覆盖结构化路径明确的问题，比如曝光下降、预算消耗异常、ROI 波动这类有固定排查路径的问题；但对长期策略优化、多表复杂分析、跨系统自动执行还不够稳定。

所以如果面试官问 70% 采纳率高不高，我会说不能孤立看这个数字。复杂归因原本需要研发和策略同学人肉排查，Agent 能自动覆盖一部分问题已经有价值，但下一步必须通过 bad case 回流、plan evidence 约束、评测集扩充和高频诊断 Skill 化继续提升稳定性。

## 18. 70% 采纳率是不是太低？怎么提高？

### 答题思路

主动承认阶段性，不要防守。把 70% 拆成任务类型差异，再讲提升路径。

### 完整回答

我不会简单说 70% 很高。我的理解是，它说明系统已经能解决一部分结构化路径明确的问题，但还没有达到完全自动化的程度。

要看具体任务类型。知识查询和单表数据查询的准确率可以更高，因为答案边界相对清晰；复杂归因诊断天然更难，因为它涉及多指标、多表、多阶段推理，还可能需要业务经验判断。过去这些问题很多需要研发或策略同学人工排查，所以 70% 的采纳率在早期阶段有业务价值，但确实还有明显提升空间。

提高上我会做四件事。第一，把未采纳 case 分类，区分是检索缺证据、plan 漏节点、工具执行失败、指标口径不清，还是最终建议不可执行。第二，把 bad case 回流 Golden Set，做离线回归，而不是只靠线上试错。第三，在 plan 阶段增加 expected evidence 和 checkpoint，让每个结论都能追溯到数据或文档证据。第四，把高频固定诊断路径沉淀成 Skill 或 workflow，减少开放式规划的不确定性。

所以我对这个数字的态度是：它证明方向有价值，但也明确暴露了下一阶段要从“能回答”升级到“稳定、可验证、可规模化交付”。

## 19. 广告系统主要做了什么？和普通推荐有什么区别？

### 答题思路

先讲广告系统链路，再讲广告独有机制：预算、出价、计费、ROI、流控、校准。

### 完整回答

广告系统和普通推荐有相似的地方，比如都有召回、排序、过滤、特征和模型预估，但广告系统多了商业约束和投放目标，所以工程和策略上会更复杂。

我参与的广告系统主要包括几块。第一是在线引擎 pipeline，从请求进来后做候选召回、广告过滤、特征拼装、预估、排序、混排和返回。第二是数据流建设，包括广告主、广告计划、商品、预算、出价、投放状态等数据同步到在线系统，并保证实时性和一致性。第三是广告机制策略，比如预算平滑、预估校准、出价和排序公式、流控和平控，目标是在平台收入、用户体验和广告主 ROI 之间做平衡。第四是计费链路，广告曝光或点击后需要可靠记录、异步消费、去重和可恢复，保证计费准确。

和普通推荐相比，广告系统不能只追求点击率或用户体验，还要考虑广告主成本、转化效果、预算消耗节奏和平台商业收益。比如预算平滑要避免广告主预算过早消耗完；校准要保证预估值和真实转化更一致；流控要稳定整体 ad load，避免大盘波动。我的优势是既理解在线工程链路，也参与过这些机制策略的落地。

## 20. 为什么不用 LangChain / LangGraph 等开源框架？

### 答题思路

不要否定开源。讲“部分借鉴、部分自研”，核心原因是业务状态、长程任务和内部工具集成。

### 完整回答

我不会说开源框架不好。我们实际也会参考 LangChain、LangGraph、Claude Code、AutoGen 这类项目的设计思路，只是没有把核心长程任务调度完全建立在某个框架上。

原因主要有三点。第一，我们的业务工具和内部系统比较多，权限、参数校验、日志、超时、重试、数据安全都要和内部基础设施结合，完全套开源框架改造成本不一定低。第二，复杂归因诊断里有比较强的状态管理需求，比如 plan、todo、节点状态、工具结果、文件系统外置和局部 replan，这部分我们希望有更细粒度的控制。第三，评测和可观测也需要和业务指标结合，比如每个节点的 evidence、采纳率、bad case 回流，这些不是简单 agent loop 就能解决的。

所以我们的策略是：固定链路可以借鉴 workflow 框架；通用工具调用和 prompt 编排可以参考 LangChain；但核心的任务状态、DAG 调度、记忆和评测闭环，我们更倾向于按业务场景自研。边界上，如果今天重新做，我会更积极吸收 LangGraph 或 Skills 这类成熟抽象，减少重复造轮子，但仍会保留业务状态和治理层的控制权。

## 21. MCP、Tools、Skills、Workflow、Agent 分别是什么关系？

### 答题思路

这是高频新范式题。要给清晰边界，并承认你当前项目没有大规模 MCP 落地。

### 完整回答

我理解它们是不同层次的抽象。

Tool 是最小的可调用能力，比如查 SQL、查文档、拉指标、发请求。MCP 更像工具接入协议，用标准方式描述工具、参数、返回和鉴权，让 Agent 能接入外部系统。Skill 是更高一层的能力封装，通常包含任务说明、使用边界、资源文件、示例和可能的执行入口，适合把稳定高频任务沉淀成可复用能力。Workflow 是固定步骤的流程编排，适合强约束、步骤稳定的任务。Agent 则负责开放任务里的理解、规划、工具选择和动态决策。

放到我的项目里，知识查询和 Text-to-SQL 的部分链路可以 workflow 化；高频固定归因路径可以沉淀成 Skill；内部查询、指标拉取、文档检索可以通过 MCP 或统一 tool registry 暴露；复杂诊断仍然由 Agent 做 plan 和调度，但它调用的是更受控的 Skill、Workflow 或 MCP tool，而不是裸工具集合。

需要说明的是，我们当时项目没有大规模基于 MCP 落地，更多是自研工具注册和内部 workflow。如果今天重构，我会把 MCP/Skills 作为工具治理和能力复用的重要方向，尤其是鉴权、参数预填、schema 校验和审计这几块。

## 26. 一句话版本速记

### 多 Agent

不是为了追概念，而是因为知识查询、数据查询和复杂归因三类任务形态不同；固定链路 workflow 化，开放长程任务多 Agent 化。

### 记忆

短期记忆保连续性，工作区记忆防目标漂移，文件系统记忆外置大结果，长期记忆沉淀用户偏好和成功经验。

### Plan/Execute

核心是把开放复杂任务转成可校验、可调度、可回放的 DAG，并把失败限制在节点级别。

### RAG

Agentic RAG 解决的是 naive RAG 在 SOP、多跳问题和上下文碎片化上的不稳定，不是所有 query 都走多轮。

### 评测

Agent 评测要分结果正确性、过程可靠性和业务有效性，不能只看一个 LLM judge 分数。

### Text-to-SQL

多阶段拆分是为了解决表字段选择、value mismatch 和执行纠错；复杂 join 的关键是表关系和指标口径治理。

### ROI

成功不是单看准确率，而是看运营采纳率、人工节省时长、转人工比例和 bad case 是否持续减少。

### 求职动机

不是单纯换工作，而是希望把已有 Agent 落地经验放到更主线、更复杂、更长期建设的场景里继续做深。
