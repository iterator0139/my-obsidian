**回答：** 它其实整个挑战的话还是在整个的稳定性方面，包括几个方面的稳定性。一个就是你的一个目标的稳定性，目标的稳定性这里的话就是包括因为你的长城人物目标是一个远期的目标，但是你每一步执行的时候它可能又是一个近期的目标。然后这样的话你随着你的任务的部署越来越多，你的上下文的窗口可能越来越大，然后你里面的信息变得越来越杂乱，这个时候你的目标可能已经失焦了。

所以的话这是一个目标不稳的问题，这个话我们可以通过上下稳的一个管理，包括你的一个工作区记忆的这样一个机制去给他做一个reminder这样一个机制，然后能够让他在每一步的时候都能够玩持续的一个记住他最终的那个目标。

第二个问题就是他的一个路径不稳定的一个问题。路径不稳定其实就包括几个方面，就是你每一次任务它对于对一个同一个query，它可能都会有不同的一些执行路径，然后这样的话其实是我们不太希望看见的。我们更希望它是能够去有稳定可复现的这样一个执行路径。所以这部分我们可能会通过一些比如这样一个plan is Q的这样一个机制，就是让它的这样一个规划能够借助我们的这样一个fuel shot，包括我们这样一些人工的这些案例库，然后能够让它能够去做到一个目标拆解的更更符合我们的预期的这样一个功能。

还有一个解决它这样一个执行路径不稳定性，就是我们可以在它的每一个执行的节点中间去引入这样一个验证的这样一个角色，然后去通过这样一个局部的验证能够去去探测他的一个中间结果，然后能够让他去做到一些自我的一些路径上的修正和我们整个整体的一个plan的一个流畅的执行。

## Q12. 中途 check 是否有效

**问题：** 中间去介入去做check这个方式真的是真的是有效的吗？第三方纠偏本身的认知是不足的，这个挑战挺大。

**回答：** 对，这是一个挑战，但我认为这是一个好的范式，因为它其实现在agent的任务执行来说，它其实跟人类的这个模式很像，因为它是一个开放的，然后多步的长程的搜索的这样一个过程。然后你往往走到中间步骤的时候，你如果发现你当前确实你的一个结果和你的预期偏差很大，那这个时候正常就是理想的动作就应该去做一个纠片。但是你如果连自己都不知道你的结果怎么样，那你这个行为那就更加没办法去做一个反馈的。所以还是需要有这样一个反馈信号，然后能够让整个的agent的执行workflow能够做一些这种纠片以及回环的这样一些动作。

您说的这个非常有道理，所以这个时候他的问题就变成了你怎么去保证他的一个评判器的一个客观性和他的一个准确性。然后这个问题的话我们可以通过训练以及它的一个原评测我觉得可以去做解决。因为你想要去达到这样能力，那你只能去从模型能力上去突破了，包括你可以给它做微调，然后你比如对某一个类型的问题你给它做一个数据集体上的一些微调，然后它对这一类问题它能有很好的一个判断。

## Q13. 为什么不把源头模型做好

**问题：** 你做一个中途check模型的微调，那你为什么不一开始不把这个对源头的这个模型做好呢？

**回答：** 对，这个是涉及到一个值得拆分的问题。像我们也知道现在的强机座模型的话，它其实是经过了多轮的这样一个预训练以及后训练来做的，然后它预训练和后训练之间的任务它其实也是不一样的。然后它其实在做这些不同任务的训练的时候，它是需要去保证你后面的训练的数据以及范式不影响你前面的一些任务能力的，强机座模型它其实是有这样一个保证机制在里面的。

所以这就涉及到你对于一个全参数来一个大模型来说，你想去给它集成多个能力，这个想法当然是好的，我们需要全才，但是往往在实际的实现当中，你的一些微调可能就会去影响到之前的它的能力。所以说这个的话是一个成本和你的一个效果的取舍问题，你通过职责隔离的话可能去会有一个权衡的一个平衡的动作在里面。

第一段是广告系统架构，这部分我是从 0 到 1 深度参与了整个全链路的建设和持续演进。我认为里面最有技术成就感的是，首先包括离线数据流、在线的引擎 pipeline，我都是有从 0 到 1 完整搭建的经验。第二个是持续架构优化，包括做了数据流读取范式、存算取的范式优化。

算法层面，我在广告系统算法里面担任机制策略核心开发者的角色。算法和工程贴合比较紧密，我深度参与了广告机制算法策略的设计和落地，包括预算平滑、CTR/CVR 校准、智能出价、G-Fed 二价机制等。我理解每一个机制策略的设计理念、要解决的问题以及如何实现。

第二段项目经验主要是商家运营智能助手 Agent 项目，我也是设计主导者，做 Agent 工程化落地实践。我认为最大的技术成就感是，对复杂任务、复杂场景做到了技术拆分，解决真实业务需求；也设计了 harness 工程里的记忆机制、多 Agent 模式，以及 RAG 范式。

上一段经验是在百度做搜索相关的训练优化和训练平台工作。主要职责是训练框架优化，涉及 GBDT 和 GB Rank 训练框架加速。我参考 LightGBM 做了分桶机制，做到了加速并行。第二个是了解整个模型调研平台，从数据准备、模型训练、模型分析管理到模型上线的 pipeline 搭建。

## Q2. Agent 评测体系如何构建

**问题：** 基于多 Agent 架构的商家运营智能助手里，构建 Agent 评测体系是怎么构建的？设计过程中有什么独到之处？

**回答：** 评估的话，我们认为它在迭代过程中有反馈作用，因为需要有数据反馈才能做持续优化迭代，所以这部分很早就开始做。

第一步是构建环境测试集。因为我们是复杂任务，一开始基本评测集比较缺少，所以先人工共建种子环境测试集，作为评估任务准确率和效果的环境标准。

不同任务的数据集构建方式不一样。RAG 知识查询数据相对好获取一点；text-to-SQL 因为线上之前有 BI 平台，会收录用户 query 和 SQL 对应关系，所以也稍微好构建一点。数据量大概 RAG 是 200，text-to-SQL 是 300。

复杂任务主要是诊断归因，比如广告组报量掉了，要做归因排查。这部分数据比较非结构化，所以采用运营标注的方式。运营在工作流里遇到问题，自己做好分析归因之后，再给我们标注好，大概 100 条构建成这个任务类型的环境测试集。

第二个是评测方式。不同类型评分规则不一样，所以我们用评分器组合。text-to-SQL 更偏 code generation，确定性更高，所以采用代码评分器，主要看 SQL 生成的 exact match 和执行结果一致性。

RAG 结论偏综合分析，结果比较主观，所以用客观指标和大模型主观评价结合。客观指标是对结论抽取关键词，做关键词实体匹配，用召回率、准确率和 F1 score 作为关键词维度指标；也会通过 embedding 语义相似度做语义打分。除此之外用 LLM-as-judge，通过 rubric 让大模型从结论是否正确、是否有事实依据、推理过程是否符合正常链路、检查的数据源是否完整等维度打分。

## Q3. 为什么要使用多种评分器

**问题：** 为什么从一种评分器变成三到四种评分器？凭什么认为多种评分器综合判定是合理的？

**回答：** 还是基于数据驱动。因为我们已经有 golden set，通过评分器组合能够把评分更客观地 match 到 golden answer，我们就认为这种评测方式更符合预期。

所有考量的前提是有 golden 测试集。我们在 golden 测试集上投入比较多，会保证完整性和客观性。像 RAG 评测集，不止标注答案，还会标注实体、数据源等各个维度的信息。因为这是前提，所以会尽量保证它的准确性和客观性。

## Q4. Agentic RAG 解决什么问题

**问题：** Agentic RAG 相比普通 RAG 主要解决什么问题？

**回答：** 传统 RAG 是单次检索、单次生成的范式，有几个不可避免的缺陷。

第一个是分块机制导致上下文缺失。召回排序之后，上下文会有缺失。第二个是单次检索不能很好处理多跳问题。第三个是推理逻辑都在单次检索里生成，推理能力也会受到限制。

Agentic RAG 可以通过多次检索，自主决定去完善上下文，解决碎片化问题；通过多跳多次检索，自然解决多跳问题，因为这和人类获取信息的方式类似；第三个是推理链路因为本身就是多跳，所以推理程度会比单跳更高。基于这三个方面，可以更好解决 Simple RAG 不能解决的问题。

## Q5. 上下文碎片化还有哪些解法

**问题：** 对上下文缺失或碎片化，除了 Agentic RAG 多次检索，还有别的解法吗？

**回答：** 单次检索里也可以做上下文补充。因为检索结果和真实需要的上下文有 gap，检索结果可能语义相关，但已经分块了。人获取信息也需要更大或更多块的完整信息，才能有整体判断。

可以采用细粒度 chunk 做检索，检索到相关细粒度 chunk 之后，再通过这个 chunk 做回溯。回溯就是把上下文从小块，比如 sentence，扩展到 paragraph，甚至章节。这样相当于对事情有更完整的认知。

回溯可以有两种方式。一种是硬性规则，固定做几层回溯，比如两层或三层。另一种更智能，让大模型自己判断当前上下文是否已经满足回答需要，自己控制回溯逻辑。

## Q6. ReAct 形式的 Agentic RAG 延迟问题

**问题：** 你们用 ReAct 范式做多轮 RAG，会不会带来比较大的延迟影响？有没有量化数据？

**回答：** 会有影响，所以我们做了最大搜索深度限制、最大步数限制，以及每一轮的死循环检测。

如果只是一次单轮 RAG 检索，向量检索本身很快，可能是毫秒级。引入 Agentic RAG 之后，主要耗时上升来自多步处理。本来一步检索回来让大模型生成，现在可能变成四步，重复检索、思考和生成的过程。

我们这里基本的倍数就是步数限制的设置，大概在 4 倍左右。如果看最终端到端的首 token，中间还有模型思考和推理，差距不是一个数量级，大概有 10 到 20 倍。为了缓解用户等待，我们会把 Agentic 过程中的步骤做流式展示，让用户看到它每一步在工作，不是空白等待。

这个确实是 Agentic 的缺点，它为了效果牺牲耗时。前提要求模型推理能力强，也需要通过 RL 等微调让 query 生成更精准，才能把整个环节变得更高效。

## Q7. 分层多 Agent 调度架构解决什么问题

**问题：** 分层多 Agent 调度架构主要解决什么业务场景难题？

**回答：** 主要是通过路由方式解决不同场景复杂度不同的问题。我们的场景包括知识查询、text-to-SQL、复杂归因诊断，这三个场景复杂度不一样。

知识查询和 text-to-SQL 都可以通过单 Agent 或 workflow 来做，所以我们不希望简单任务也进入 plan and execute 的复杂模式，因为会带来成本上升，效果也不一定符合业务诉求。text-to-SQL 更倾向线性职责化拆解，把每一步做到职责专用化，通过每一步优化换取 SQL 生成准确性。

所以这里的调度架构主要是基于意图识别模块做任务分发。知识查询路由到 RAG，数据查询路由到 text-to-SQL，复杂任务再进入 plan and execute。

## Q8. 复合型指令如何拆解执行

**问题：** 如果任务既需要 text-to-SQL 又需要其他 Agent，这种复合型指令简单路由搞不定，plan agent 具体怎么拆解执行？

**回答：** 复杂任务会通过 plan and execute 承接。以广告商家 ROI 下降归因为例，它会调用 plan 模型，生成一个 DAG 图的执行定义。

DAG 图里面每个节点是 subtask，包括数据拉取、用户上下文拉取、平台 context 数据拉取。RAG 能力也会开放，但具体这个场景用得比较少，因为不太需要策略背景。

拿到数据之后，会有数据分析节点。数据分析节点返回 summary 给主 plan agent，由主 agent 决定下一步是 replan，还是继续生成答案。整体是通过 task、subtask 和 tool 三层执行结构来做。

## Q9. 多 Agent 架构未来如何演进

**问题：** 面向商家的复杂指令，这套架构未来还有哪些演进点？

**回答：** 首先从能力上，商家可能需要接入更多复杂指令能力。比如广告创建时，根据目标和预算约束生成广告投放计划，里面包括素材生成、出价设置、预算设置、多广告计划组合。如果要实现，就需要接入更多工具机制，包括用户历史数据拉取、案例库数据拉取等。

第二个是提高 plan 准确度。可以通过 few-shot、提前规划好的 skills、固定流程作为上下文，供模型复用，让规划更准确。

第三个是长程任务稳定性控制。需要做任务状态持久化，任务失败后的重跑和重传机制，把任务管理做得更好；也包括整个长程任务上下文机制的优化和完善。

## Q10. 长程任务有哪些挑战

**问题：** 遇到长程任务，比普通任务会有哪些更多挑战？

**回答：** 挑战主要在稳定性。

第一个是目标稳定性。长程任务目标是远期目标，但每一步执行是近期目标。随着任务步数越来越多，上下文窗口越来越大，信息越来越杂乱，目标可能失焦。模型可能更关注当下局部目标，忘记最开始的目标。这个可以通过上下文管理和工作区记忆机制做 reminder，让它每一步都持续记住最终目标。

第二个是路径不稳定。对同一个 query，它每次可能有不同执行路径，但我们希望它能有稳定可复现的执行路径。可以通过 plan and execute、few-shot、人工案例库，让目标拆解更符合预期。

另外可以在每个执行节点中间引入验证角色，通过局部验证探测中间结果，让它做路径修正和 plan 的流畅执行。

## Q11. Verifier 是否真的有效

**问题：** 中间介入做 check 真的有效吗？用模型判断模型会不会也有幻觉？

**回答：** 这是挑战，但我认为这是一个好的范式。Agent 任务执行和人类模式很像，是开放、多步、长程搜索过程。走到中间步骤时，如果发现当前结果和预期偏差很大，理想动作就是纠偏。如果连自己结果怎么样都不知道，就更没办法反馈，所以还是需要反馈信号，让 workflow 能做纠偏和回环。

关键会变成怎么保证评判器的客观性和准确性。这个问题可以通过训练和元评测解决。比如对某一类问题做数据集上的微调，让它对这一类问题有好的判断。通过 DPO 这些训练方式，可以在某个领域有一个好的判断标准。

为什么不把源头模型直接训练好，是因为不同任务能力集成到同一个模型会有成本和效果的取舍。职责隔离可以不用考虑它对其他任务的影响，因为它职责很专一。

## Q12. 候选人提问：团队痛点和规划

**问题：** 咱们现在 Agent 团队最大的痛点和未来规划是什么？

**回答：**
