# 招商证券二面｜问答整理

## Q1. 开场和自我介绍

**问题：** 你准备就绪的话，开始做一个简短的自我介绍。

> 面试官介绍：我是第二面面试官，我叫时国忠，是AI开发团队负责人。后面面试顺利的话会加入到我的团队。现在是第二面，后面应该还有总经理的面试、人力的面试、公司总部的面试，也不排除其他中间领导想多加面。

**回答：** 好的面试官您好，然后我叫陈宏，然后我现在的话是在Shopee负责广告系统架构和AI agent架构的一个开发。然后在Shopee的话主要是两段的一个项目经验。首先第一段的话是作为核心开发者然后全程参与了广告系统从0到1的一个全电路的搭建以及它的一个持续演进。然后的话在这一段经验里面的话，我主要是对整个的一个在线的系统架构以及整个广告机制策略算法优化这一块有比较深入的一个实践和一个理解。

第二部分的话是主导了商家运营智能助手agent的项目的一个落地，然后去解决我们广告运营在知识获取，然后数据查询，然后复杂归因诊断这三个环节上的一个效率低下问题。为了去提供这三个场景能力也设计了一个混合的多级agent架构，然后通过意图识别模块来进行一个能力的路由。同时为了解决长程任务上下文膨胀以及注意力丢失的问题，设计了一套四级的记忆机制。

第三个的话就是针对这种长程任务的这样一个复杂的多部任务的场景，我们设计的这样一个planned skill的这样一个架构，然后去解决这样一个單agent的单agent的模式下面它所存在的一些任务的一个场下文的膨胀以及目标飘移的问题。上一段工作经验主要是在百度做机学习平台的工作。

## Q2. 百度、硕士和选择虾皮

**问题：** 为什么百度只待两年？硕士学什么？为什么从北京到深圳加入虾皮？

**回答：** 可能有几方面的原因吧。一个是当时团队的业务可能会有一点受限，然后当时已经进入深度学习的时代，我们所在的组当时是做机学习为主，所以我想去换一个更加在整个业务场景更空间更大的方向。

硕士内容的话跟深度学习这一块还是会强相关一点，包括云竞赛、deep learning、强化学习的一些基础课程。我在香港念的学。

选择蝦皮主要当时是考虑到它处于快速扩张阶段。第一个选择的原因就是因为它处于上升期，第二个是东南亚富德业务也处在上升阶段。加入扩张期团队整体会更有一些从零到一的机会。

## Q3. 虾皮四年的收获和错过

**问题：** 在虾皮这几年收获得失总结一下，有没有觉得错过什么？

**回答：** 收穫的話從幾個維度來講。首先第一個是技術上，全面了解了整個在線技術架構的全电路设计和细节，包括数据流建设，怎么对接在线引擎，在线引擎有哪些模块，怎么根据理线数据做算法调控。

第二部分是清楚知道2C用户APP的产品设计架构，从客户端到前端、后台，多团队多方向分工协作模式。第三部分是算法相关积累，主要在广告机制策略，包括召回、金牌、广告预算平滑、预估校准、二财期费、混牌这些机制策略。

个人收获就是思考问题和解决问题的思维模式，从解决单点问题，慢慢思考需求背后真正要解决什么业务问题，找到最本质需求，给出通用解决方案。技术上也认识到为了赶排期简单上线可能埋下技术债，未来还是要通过技术手段重新解决掉。

错过的话，可能就是当时在机器学习平台偏AI infra方向，如果投入deep learning那一块infra，后续可能转型到大模型infra。当时对大语言模型了解不是那么深入，更多了解传统GAM模型、CNN这些网络架构，对bird那一块了解比较浅，没有发现后续潜力。

## Q4. 当下技术趋势

**问题：** 你觉得当下 2026 年技术趋势是什么？

**回答：** 现在的趋势主要有几个点。第一个是依托于大模型运训练的鲜艳知识能力，在基座上做后处理的强化学习后训练。强化学习后训练带来的能力就是多个场景上得到多步骤决策、多序列决策能力，天然符合人类或者机器人真实场景的序列决策建模。

第二个方向可能会涉及世界模型。大模型这种概率模型在某一定方面还是有缺陷，它更多依赖先验数据分布，对底层物理世界的感知和逻辑符号推理比较欠缺。第三部分是多摩泰，后续肯定持续发展，希望模型不仅聚焦文本，而是具备多种表征形式的统一表征范式。

## Q5. 虾皮增长和广告指标

**问题：** 加入虾皮扩张期的期望达成了吗？广告赛道最激动人心的事情是什么？指标怎么定义？

**回答：** 有达成也有没达成的部分吧。当时确实是在扩张期，但是很紧接着经济环境发生变化，22年底开始加息，经济环境收缩，疫情影响也持续。对于我个人而言还是有机会参与广告增长赛道，所以整体五五分。

最激动人心的，一个是业务从0到1，第二个是最开始怎么把广告商家投放表现优化到合理区间，让广告主能够持续在平台留存。

比如Rose指标，它相当于是广告组投入产出比。主要市场像印尼，最开始可能只有四点多、三点多。通过两个季度持续迭代，包括排序优化、排序公式优化、预算平滑、校准这些广告机制策略算法迭代，把ros做到7到8这样的水平。Rose就是广告投放的gmb，承担的广告GMP除以广告cost，类似ROI。

## Q6. 看机会和金融证券行业

**问题：** 现在看外部机会的直接原因是什么？为什么选择金融或证券行业？

**回答：** 还是想要去做大模型和Agent相关的领域。现在已经看到模型能力从简单问答和推理能力，开始延伸到可以真的帮人类做实际工作，真的提高生产力。所以判断未来agent领域肯定会持续演进，落地在各个场景，希望更早加入这个行业和方向。

金融行业的话，一是任务复杂度比较高，数据规模大，决策炼木非常长和复杂，对任务准确性要求非常高。这个场景如果解决好，相当于agent能力实际落地。第二个原因是银行体系内实际场景比较多、比较丰富，可能给这个方向的人更多尝试场景。其他方向也有考虑，比如广告和agent结合。

## Q7. 工作内容、券商了解和 JD

**问题：** 对下份工作内容和氛围有什么想法？了解证券公司吗？JD 怎么来的，吸引你的地方是什么？

**回答：** 工作内容和氛围，我还是希望和优秀的人做优秀的事，这可能是我的个人比较强的诉求。

证券公司因为银行和证券信息比较少在网上，可能知道证券一般做投言这些工作。主要业务了解到包括券商系统维护，内部投言调研，还有内部系统建设。

JD是在boss上面看agent相关招聘发现的。吸引我的地方，一个是agent相关，第二个可能稳定性也是考量范围，第三个招商整个平台非常具有比较好的平台价值。平台价值就是相当于你能够做更多事情，稳定性就是能更加深入投入深耕某个领域。

## Q8. Text-to-SQL / Test to Circle

**问题：** 多阶段 text to circle 架构展开讲一下。上下文组装顺序怎么来的？value mismatch 怎么解决？

**回答：** test to circuit主要是解决暂缘到circuit生成的问题。最开始尝试直接通过单次推理、prompt优化来生成，发现效果不太好，会有很多幻觉，基本上生成circuit都不可用。于是把它做了多阶段拆分：query理解和改写，表照回和列照回，列探测机制。

列探测是为了解决用户query查询词和db里面实际词不匹配的问题，看某些列在数据库里面真实数据分布长什么样。通过上下文信息补全，让模型更好生成正确circle。然后再做circle生成，这里通过React反思机制，通过错误信息，如果有偶发性或者可从事解决的错误，就带着错误信息从事生成。最后通过共识机制，多次生成里取多数相同奢客结果。

上下文组装顺序，首先query理解和改写、表照回和列照回确定。后来发现查询过程中会有value mismatch，比如字段region，查询条件说新加坡，它生成Singapore，但数据库实际存SG缩写。解决就是对照回的一些关键列分类，美举类型直接通过奢客查美举值，数字类型统计数据分布，作为上下文给模型。

## Q9. AI 友好型表设计和渐进式披露

**问题：** 如果让数据库表更 AI 友好，规范里要加哪些？按 Skills 渐进式披露模式怎么设计表信息？

**回答：** 首先第一个就是基础的表介绍肯定需要。第二部分是整个字段说明，每一个字段的分布描述也需要。第三部分除了表面信息，需要给它一些表在使用情况下的背景信息，不仅知道表长什么样、业务背景是什么，还需要知道平时在哪里用、怎么用。还需要和其他表的关联关系维护。

按scale这种建议式披露，用户有数据查询任务，假如有10张表，每张表都有业务描述背景，通过LM做一次表筛选，先加载这部分。下一步再看列的基本描述，从里面选出某些列。再有使用case层级，让它自己判断是否要查看use case文件。相当于多级文件或目录形式，让大模型决定看到哪一层为止。

我感觉可行性是有的。上下文组装没问题，只要模型具备推理能力，可能就能帮你做到自组装。但最后Circle生成可能还是需要微调或者针对性的Circle生成模型。

## Q10. 让大模型设计 pipeline 和自动优化 prompt

**问题：** 如果让大模型设计高效准确流水线，要告诉它什么？Prompt 自动优化需要哪些基础设施？难点在哪里？

**回答：** 它需要一个迭代过程。不管人为给反馈，还是有环境让它跑色彩生成任务，再做结构优化。要提供的信息，第一个是任务目标，第二个是业务背景，第三个是业务约数。细分的话，业务背景包括当前数据架构、所有数据说明；约束比如sir可生成场景，希望不希望有大表直接查询、大表座椅这些。

我理解它需要一个实验环境，需要知道什么样的设计是好的，什么样设计是坏的，需要反馈才能持续迭代。现在一些Auto Research也是这种思路，通过调优参数，让模型自己做参数迭代。

Prompt自动优化需要样本回流，通过case反查发现当前系统能力不具备的能力。通过复样本case、理线环境、失败原因反馈给模型，让模型优化提示词，或者诊断到底哪一个环节出问题。还需要诊断模块知道问题在哪个环节，再进入调u模块，给下一个调u模型做优化，优化后复跑，通过LAMS加或者人工验证。

最难还是整个诊断过程和调优方法，以及模型是否具备这个能力，能不能真的把事情做成像人的水平。复杂过程应该尽量A正，而不是仅靠模型一次推理。

## Q11. 三到五年规划

**问题：** 接下来三年五年个人规划是什么？

**回答：** 规划的话就主要还是深蹲在怎么的这样一个A正领域吧，然后去成长成一个agent领域的这样一个技术专家的这样一个角色。对自己的技术要求就是能够拿到一个场景，通过需求理解和拆解能力，通过agent系统设计能够把自动化agent能力快速落地在任何一个场景。

## Q3. 虾皮四年的收获和错过

## Q8. Test to Circle / Text-to-SQL 技术细节

**问题：** 多阶段 text to circle 架构展开讲一下。上下文组装顺序怎么来的？value mismatch 怎么解决？

**回答：** 这个test to circuit的话它主要是解决这样一个暂缘到circuit生成的问题。整体的话我们最开始是尝试了直接通过单次推理，然后去做prompt优化来生成。发现它的一个效果不太好，然后它会有很多的一个幻觉，然后基本上生成circuit都不可用。

我们就去把它做了一个多阶段的一个拆分。把它拆成了一个 query的理解和改写，然后再接下来就是我们的一个表的照回和列的照回。再往下的话就是为了去解决我们这样一个用户的query的一个查询词和db里面实际词不匹配的这样一个问题，我们会有一个列的探测的这样一个机制。它的目的就是去看一下某一些列我们在数据库里面真实的一个数据分布长什么样。

基于前面的整个的背景信息上下文组装好之后，我们再去做一个circle的一个生成。这个生成的话这里也是通过React这样一个反思的机制，然后会通过他的一个错误信息的一个，如果有某些偶发信的或者说是可从事解决的错误的话，我们就去进行一次带着错误信息的一个从事。最后的话就是通过一个共识机制，通过多次生成里面取多数。

上下文组装的顺序，首先第一个我们就是把query理解和改写，然后和我们的表照回和列照回这一块确定好了。后来又发现他整个在查询过程中会出现value mismatch的这样一个问题。比如有一个字段叫region，他查询条件里面说的是新加坡，然后它就生成了一个Singapore，但是实际上在我们的数据库里面可能存的是一个SG这样的缩写。

value mismatch 通过我们已经拉出了一些列，我们已经照回了一些列，然后会每张表有一些关键列。对于这种美举类型的话我们就会直接通过奢客去查它的一个美举的一个值。对于数字类型的话我们会去统计它的一个数据的一些统计的分布。

## Q10. 用大模型设计 pipeline 和自动优化 prompt

这里这个部分还需要一个诊断的这样一个模块，他需要去知道你到底是在哪一个环节发生的问题。诊断完之后再进入调u的模块，把具体的结果以及失败的原因、失败的模块给到下一个调u的模型，然后让调阅的模型去做一个优化。优化完成之后再来去做一个复跑。

最难的话还是说整个的一个诊断的这样一个过程和那个调优的这样一个方法，然后模型是否能够具备这样一个能力。他能够去做真的能够去把这样一个事情给他做成像人的一个水平。

## Q13. Text-to-SQL 架构细节

**问题：** 你项目里提到多阶段 text-to-SQL 架构，展开讲技术细节。

**回答：** Text-to-SQL 解决自然语言到 SQL 生成。最开始尝试单次推理，通过 prompt 优化生成，但效果不好，有很多幻觉，生成 SQL 基本不可用。

我们发现 SQL 生成是多阶段步骤，如果所有步骤都融合在一次推理里，很难达到想要效果。所以拆成多阶段：query 理解和改写；表召回和列召回；列探测机制，用来解决用户 query 查询词和 DB 实际词不匹配；上下文补全后再做 SQL 生成。

生成时也通过 ReAct 反思机制，根据错误信息，如果是偶发或可重试解决的错误，就带着错误信息重试生成。最后通过共识机制，在多次生成里取相同 SQL 结果的多数作为最终结果，提高准确性。

## Q14. 上下文组装顺序怎么形成

**问题：** 上下文组装包括召回、字段对齐等，顺序是怎么来的，最终怎么形成这个逻辑？

**回答：** 首先是 query 理解和表召回。我们希望给模型看到的信息对齐查询目标，也希望把最相关的表和列抽选出来，减少无用上下文。因为上下文窗口越长、无用信息越多，推理结果质量越差。

所以先做 query 理解和改写，再做表召回、列召回。后来发现查询过程中有 value mismatch 问题，比如用户说新加坡，模型生成 Singapore，但数据库字段里存的是 SG。模型没看到字段真实值之前，不知道字段里存什么。所以基于这些 case 做了值探测机制优化。

## Q15. Value mismatch 怎么解决

**问题：** value mismatch 问题具体怎么解决？

**回答：** 我们已经召回一些列后，会对每张表的关键列做分类。对于枚举类型，直接通过 SQL 查它的枚举值。对于数字类型，会统计数据分布。通过这种方式把上下文信息给模型，让它更好生成正确 SQL。

## Q16. AI 友好型数据库表设计

**问题：** 如果要做 AI 友好型的数据库表设计，减少 AI 运行时错误，你会要求表设计规范里加哪些必须做的事情？

**回答：** 首先是基础的表介绍。第二是字段说明，以及每个字段分布描述，相当于让大模型全面看到表的基本结构。

第三是表在使用情况下的背景信息。模型不仅要知道表长什么样，还要知道业务背景是什么、平时在哪里用、怎么用。

第四是和其他表的关联关系维护。可以把表和其他库、其他表的关联结构单独抽出来作为信息维护。整体大概是表结构、业务使用背景、关联关系这几部分。

## Q17. 按 Skill 渐进式披露设计表信息

**问题：** 如果表信息也按 Skill 的渐进式披露模式，你觉得应该怎么分阶段披露？

**回答：** 可以类似 Skill。用户有一个数据查询任务，假设有 10 张表。每张表先有业务描述背景，模型先看所有表的描述，判断哪张表和用户任务 query 匹配，先完成粗排召回。

然后进一步看列的基本描述，从里面选出一些列。相当于把向量召回过程变成大语言模型自然选择的过程。之后再有 use case 层级，让模型自己判断是否查看使用 case 文件。可能按照多级文件或目录形式，让模型决定看到哪一层为止。

我觉得只要模型具备推理能力，上下文自组装是有可行性的。

## Q20. Prompt 自动优化怎么做

**问题：** 现在每个阶段的 prompt 是人迭代的，这个过程能自动化吗？需要哪些基础设施？

**回答：** 需要样本回流。要有负样本，通过 case 反查机制发现当前系统能力不具备的点。

然后需要离线环境，以及失败原因反馈给模型，让模型优化提示词，或者诊断到底是哪一环出了问题。这里需要诊断模块，知道具体失败在哪个模块。诊断完后进入调优模块，把结果、失败原因、失败模块给调优模型，让它优化。优化后再复跑，拿到结果。

结果验证可以通过 LLM judge 或人工验证。验证后形成反馈信息，再给到调优模型。不管是落成经验还是轨迹数据，用于后续训练，整体形成闭环。

## Q21. 自进化里最难解决的环节
