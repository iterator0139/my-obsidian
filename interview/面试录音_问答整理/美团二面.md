## Q1. 自我介绍

**问题：** 先自我介绍一下。

**回答：** 我叫陈宏，目前在 Shopee 负责广告系统架构开发以及 AI Agent 架构开发。

在 Shopee 主要有两段项目经验。第一段是从 0 到 1 参与广告系统全链路建设和持续演进，深度参与广告机制策略算法优化，保证高并发环境下的稳定性。这段经验让我在在线架构和广告机制策略算法上有比较深厚的实践和理解。

第二段是主导广告商家运营智能助手 Agent 落地，解决广告运营在知识获取、数据查询、归因诊断三类场景下的效率低下问题。我们设计了多级混合 Agent 架构、四级记忆机制，以及 plan and execute 多 Agent 模式，解决复杂归因诊断和长程任务上下文膨胀的问题。

上一段经历是在百度做机器学习平台相关工作，包括模型训练框架优化、模型分析体系建设，以及模型调研端到端一站式平台，提升端到端效率。

## Q2. 广告 Agent 给谁用

**问题：** 这个广告 Agent 是给谁用的？业务场景是商家在平台买流量吗？

**回答：** 主要是给商家运营使用。现在还不是投放能力，主要是做归因诊断以及决策优化。

业务背景是商家会在我们平台做广告投放，运营会 follow 广告组的投放表现。投放期间如果有一些效果问题，运营之前需要和策略、产品、研发沟通排查。这个 Agent 是给运营做广告效果归因诊断和优化建议的。

## Q3. 项目技术架构

**问题：** 介绍一下整个项目的技术架构。

**回答：** 项目主要覆盖三个场景，所以提供三个 Agent 能力。最上层是意图理解模块，做任务分发，把意图分为 unknown、闲聊、知识查询、数据查询、归因诊断五类。

unknown 意图会触发澄清机制，让用户完善 query；闲聊意图走普通大模型问答；其他三个对应三个 Agent。

第一个是知识查询 Agent，最开始是 naive RAG，单次检索、单次查询、单次生成。后来发现有上下文碎片化和多跳问题，所以升级成 Agentic RAG，通过多次检索和上下文补全生成答案，路径是先思考、执行、观察、再思考，最后自己决定什么时候停止、搜索什么。

第二个是数据查询能力，解决运营临时数据查询需求。我们做自然语言到 SQL，把 SQL 生成拆成多阶段 workflow：query 理解和改写、schema linking、table 召回、column 召回、column exploration、SQL 生成。SQL 生成阶段会先生成、看结果，再根据错误信息纠错或二次生成，也用共识机制，多次生成后取结果一致最多的 SQL，提高准确性和稳定性。

第三个是基于 plan and execute 的多 Agent 能力，解决归因诊断和决策优化场景。主 plan 模型接收 query，生成 DAG 图的 plan 定义，然后根据 DAG 派生 subagent。subagent 通过指定 role、instruction、任务、输入输出和工具候选项执行单独子任务。执行完成后把 summary 返回给主 Agent，主 Agent 根据结果 replan 或生成最终结果。

## Q4. Manus/“龙虾”出来后为什么还要做 text-to-SQL

**问题：** 现在是不是有 Manus/龙虾了，text-to-SQL 这类是不是不用自己搞了？

**回答：** 其实不是。龙虾没有直接给你带来 text-to-SQL 能力，它更多解决控制面和接入层能力。它提供很多接入口，可以从不同设备访问能力；第二个是持久化，给每个 Agent 持久化上下文和记忆，让个人助理变成常驻型 Agent。

但它没有做 harness 保障，对任务准确性和长程任务可靠性没有很多治理。所以在任务准确性上，它给不了这些需求的满足。

## Q5. 现在项目和新 Agent 形态的区别

**问题：** 现在有新的龙虾这一套，和你之前的项目有什么区别？你们是不是应该换成 skill？

**回答：** Skills 是比较好的范式，可以把固定流程固化下来，让大模型调用，比较适用于真实业务场景。我们现在也在建设这些 Skills。

之前主要是工具和 Agent 结合，没有写固定的 skills。但 DAG 可以在 skills 更上层。比如 ROI 下降的归因，可能有多个方向并行排查，每个方向的排查可以写成 skill，但仍然可以通过 DAG 把执行规划显式整理出来，让 Agent 调度。skills 相当于节点能力。

如果完全用 skills 固化流程，就失去了动态能力。我们会有模板库，也会让大模型基于工具上下文、历史案例去发挥规划能力。比较固定的流程可以做 plan 缓存或强逻辑分支，动态和静态结合。

## Q6. 如何控制规划可控性

**问题：** 你这个怎么控制输出可控性？harness 这部分有什么实践经验？

**回答：** 我们在 plan 之后的 DAG 图做多层校验。

第一层是结构性校验。DAG 图要保证格式正确、无环、无孤立节点、依赖关系正确。

第二层是语义校验。通过 LLM-as-judge 评判规划粒度是否合适、是否过细或过粗；节点是否可执行；整个规划链路效率是否合理。通过多维度 rubric 打分。

具体例子是 ROI 下降 case。第一步先生成候选原因，第二步做指标拆解。指标拆解会返回每个指标对应的子指标，候选原因节点会基于 prompt 和上下文生成多维可能原因。下一次 plan 会生成多个候选诊断分支，并行做数据拉取、归纳总结和冲突消解。

如果 plan 规划出了系统没有的能力，比如“查询用户画像”，校验过程会发现这个节点不在系统能力范围内，然后触发重新校验，把这部分信息补回到大模型请求 prompt 里，让它知道这个能力没有。规划校验通过后，再进入工具执行。工具执行靠 MCP、输入入参、超时、重试等工程治理保证稳定性。路径执行过程中如果结果和目标 gap 很大，会返回主 plan 做重规划。

## Q15. 怎么评估上下文建好了没有

**问题：** 怎么评估上下文建好了还是没建好？

**回答：** 这是比较难的点。只能通过任务完成度做评估。先补充一版上下文，基于 v1 做任务，看任务产出后的完成度和准确性。再基于准确性目标判断知识库是否足够完善，是否需要优化，或者到底是知识库问题还是 generation 幻觉问题。

## Q16. 做一个需求大概需要对话多少轮

**问题：** 你自己做一个需求，大概需要跟 AI 对话多少轮？

**回答：** 第一轮会给完整描述，包括 PRD 背景和初版技术背景。第一轮大概解决 80% 的代码生成，后续需要我自己 review，哪里不合理再让它改。整个轮次估计十轮左右肯定需要。

现在还没把 workflow 完整搭起来，所以很多还是靠人为 review。如果搭起来，可以接 Code Review 流程，有反馈信号来做修正。

## Q17. 提高广告 ROI 有哪些策略

**问题：** 从更高效获量角度，哪些策略可以提高广告 ROI？

**回答：** 对广告主来说，本质上是组合优化问题。总目标是 ROI，约束包括预算、周期，人群可能算在策略机制里。广告主可以在多个平台投放，不同平台 ROI 不一样，所以对一个广告计划来说，策略是出价、ROI、预算之间的组合。

可以把总预算拆分，设置多条广告计划在不同平台投放。因为平台策略对广告主是黑盒，所以需要先做冷启动，看各个平台广告效果，在 baseline 情况下根据广告效果 refine，优化组合。不是某一个单一策略就能让 ROI 大幅提高。

## Q18. Agent 项目如何发起

**问题：** 这个 Agent 项目内部是谁发起的？

**回答：** 是产研运三方一起做。最开始产品和运营了解整个工作流程上的效率痛点，收集痛点之后，研发根据产品痛点，从影响范围、可落地性、使用频次、效率提升收益几个维度综合考量，选出最落地可行、收益也比较可行的三个场景交付。

## Q19. 项目收益怎么算

**问题：** 这个 Agent 项目最后收益怎么算？

**回答：** 通过任务量统计。第一个看在线采纳率，第二个通过运营对比前后的效率优化提升，统计效率提升率。

## Q20. 记忆机制怎么设计

**问题：** 你这里提到的记忆系统怎么设计？

**回答：** 我们是任务类型，过程执行中会有很多工具调用日志，长程任务日志会持续累加。所以把工具调用结果存到文件系统记忆里，解决噪声和上下文膨胀问题。

第二个是工作区记忆。我们希望 Agent 像人一样有工作区，记录和管理任务规划。每个 Agent 做完规划之后写 todolist，写到文件里管理 todolist 状态、plan 和当前目标，再周期性 reminder 拼回 prompt，解决长程任务目标漂移。

短期记忆会通过上下文阈值自动触发压缩。长期记忆会沉淀任务历史经验，作为可复用能力。

## Q21. 和 Claude Code 的区别

**问题：** 这个和 Claude Code 的区别是什么？

**回答：** 和 Claude Code 整体比较像，和龙虾区别比较大。Claude Code 是 Coding Agent，也是任务类型，需要长程任务执行、很多工具调用。它主循环是单 Agent、单 ReAct Agent，也有 plan agent 作为子能力。它整个工程化做得更好，比如工具接入、工具治理、长程任务持久化和管理、上下文压缩机制都更专业。

## Q22. 怎么沉淀运营知识

**问题：** 运营的知识怎么往 Agent 里沉淀？

**回答：** 现在方案比较简单，想做 skills 编排。运营、策略、研发一起把标准归因诊断流程固定成 skills。

如果想沉淀运营投放经验，只能征集运营同学的 skills，让他们在工作流程中编写经验，并确保它是完整、可用、能够持续迭代和评估的。

## Q23. 是否可以没有商家运营角色

**问题：** 极端一点，能不能没有商家运营角色，整个算法全部托管？

**回答：** 当然可以。只要整个 workflow 搭得很完善，Agent 完全可以直接对接广告组，不需要运营。但前提是准度、可信度、稳定性要达到 2C 程度。

现在的 Agent 不是闭环，只是诊断和建议这一部分。要完全替代操盘手，需要广告计划创建、线上监控、效果回传、计划修改整个 workflow 闭环起来。

## Q24. 现在 Agent loop 的主要问题

**问题：** 你现在重点把时间花在哪些方面？在 Agent 方向主要研究什么？

## Q27. 怎么定义 Agent 项目成功

**问题：** 你们怎么评估这个东西到底行不行，是不是解决了业务问题？

**回答：** 诊断功能是解决了运营问题，因为它加速了故障和问题归因的效率。评估上包括用户端评估和系统内 Agent 评估。

我们不只关注结果准确性，也关注推理合理性、执行步骤合理性和效率。归因场景会把主因和辅因抽出来，做一些 F1、召回等量化指标；其他无法用程序定义的部分，只能通过 LLM-as-judge 或训练判别模型来评判。

给策略之后也要评估策略，不能直接用。理想方式是有环境或校验模块，但外部平台策略是黑盒，环境很难搭，只能依靠历史经验和历史轨迹做综合评估。
