# 量化指标问题与口径

> 用途：统一所有涉及数字的问题口径，避免面试中 DAU、采纳率、评测集规模、团队人数、项目周期、广告效果等数字前后不一致。  
> 统计来源：`面试录音_问答整理/` 下原始面试问答整理文件，不反向计入后生成的总结文档。

## 一、总原则

所有量化指标回答都按同一个逻辑讲：

1. **先说口径**：这个数字是什么范围、什么阶段、什么场景；
2. **再说当前数值**：给出一个稳定数字或区间；
3. **补充解释**：为什么这个数字合理，和 baseline 比有什么价值；
4. **主动讲边界**：哪些场景没覆盖，哪些数字还没稳定；
5. **给出下一步**：如何继续提升。

不要孤立抛数字。例如不要只说“采纳率 70%”，要说“复杂归因诊断在内部运营场景中约 70% 采纳，它覆盖的是结构化排查路径，不代表完全自动驾驶；知识查询和单表数据查询成熟度更高，长期策略优化仍需要人工判断”。

## 二、所有涉及量化指标的问题

### 1. 项目有没有上线？访问量多大？是不是 Demo？

**常见问法**

- 你们这个项目上线了吗？
- 访问量多大？
- 是 demo 还是正式系统？
- DAU / QPS 大概多少？

**现有数字**

| 指标 | 推荐统一口径 |
|---|---|
| 上线状态 | 已在内部广告运营场景上线使用 |
| 使用时间 | 稳定使用约 1 年 |
| 项目周期 | 从立项到多场景交付约 1.5 年 |
| DAU | 约 500，口径为内部运营及相关使用人群 |
| QPS | Agent 侧约 20+，内部工具场景，非 C 端高并发 |
| 覆盖范围 | 主要覆盖广告运营，不是全公司级 Agent 平台 |

**完整回答**

这个项目不是 demo，已经在内部广告运营场景上线使用。口径上它不是 C 端产品，而是面向广告运营、策略和相关协作同学的内部效率工具。

从时间上看，项目从立项到多场景交付大概 1.5 年，稳定使用约 1 年。使用量上，DAU 大概 500 左右，Agent 侧 QPS 大概 20+。这个 QPS 不高是因为它是内部运营工具，不是面向海量用户的在线流量入口；它的价值主要不在请求量，而在能不能减少运营查文档、查数和找研发排查的时间。

覆盖范围上，目前主要在广告运营域内使用，还没有推广成公司级通用 Agent 平台。所以我会把它定义为一个已经生产使用的垂类业务 Agent，而不是单纯 demo，但也不是完全规模化的平台产品。

### 2. 项目效果怎么样？采纳率、准确率是多少？

**常见问法**

- Agent 准确率多少？
- 采纳率多少？
- 业务效果怎么证明？
- 70% 是不是偏低？

**现有数字**

| 场景 | 推荐统一口径 | 解释 |
|---|---:|---|
| 复杂归因诊断采纳率 | 约 70% | 结构化路径明确的问题可闭环，长期策略优化仍需人工 |
| RAG / 知识查询采纳率 | 约 70% | 当前可用，但 SOP、多跳问题仍有提升空间 |
| Text-to-SQL 单表查询准确率 | 约 80% | 单表或少量 join 较稳定，复杂 join 明显更低 |
| Plan 结构正确率 | 从约 50% 提升到约 99% | 这里指结构层面，如 JSON/DAG 合法性，不等同业务采纳率 |

**完整回答**

我们不会只用一个总准确率描述，因为三个场景难度不一样。

知识查询和单表数据查询相对成熟，知识查询的线上采纳率大概 70% 左右，单表 Text-to-SQL 的准确率大概 80%。复杂归因诊断更难，因为它涉及多指标、多表、多步推理和业务判断，目前采纳率大概 70%。这个数字说明它已经能覆盖一部分结构化路径明确的问题，但还不是完全自动驾驶。

Plan 阶段还有一个单独指标：初版 DAG 规划的结构正确率大概只有 50% 左右，后来通过结构化 schema、few-shot、DAG 校验和 verifier，把结构层面的正确率提升到接近 99%。但我会明确区分，结构正确不代表最终业务结论一定正确，所以最终还要看采纳率、主因命中率、转人工率和 bad case 回流。

如果面试官问 70% 是否偏低，我会说要看任务类型和 baseline。复杂归因过去很多需要研发或策略同学人肉排查，Agent 能自动覆盖结构化问题已经有价值；但这个数字也说明下一阶段要继续通过 evidence 约束、Golden Set 扩充和高频诊断 Skill 化来提升稳定性。

### 3. 你们怎么定义项目成功？ROI 怎么算？

**常见问法**

- 项目收益怎么算？
- 怎么定义成功？
- 是否真的解决业务问题？

**推荐指标体系**

| 层级 | 指标 |
|---|---|
| 北极星指标 | 任务采纳率、人工节省时长 |
| 业务效率 | 平均处理时长、转人工率、重复提问率、二次修改率 |
| 结果质量 | 知识答案正确率、SQL execution accuracy、归因主因命中率 |
| 过程质量 | 无效工具调用数、checkpoint 命中率、replan 成功率 |
| 使用规模 | DAU、任务数、QPS、场景覆盖数 |

**完整回答**

我们定义成功不是单看模型准确率，而是看运营能不能少找研发、少手工查数，并且最终结果能不能被采纳。

北极星指标是任务采纳率和人工节省时长。分场景看，知识查询关注答案正确率、引用证据和复问率；数据查询关注 SQL execution accuracy、查询成功率和结果是否被运营使用；复杂归因诊断关注主因命中率、路径完整性、运营采纳率和是否减少研发介入。

ROI 上最理想的算法是：原来人工处理耗时减去 Agent 辅助后的耗时，再乘以任务频次和覆盖人数。我们当前已经有采纳率、任务完成情况和部分效率提升口径，但还需要继续把“平均节省时长”和“转人工减少比例”做得更系统。下一步我会把线上任务按类型分桶，分别统计 before/after 时长、人工介入比例和 bad case 原因，这样 ROI 会更扎实。

### 4. 评测集多大？怎么标注？

**常见问法**

- Golden Set 多大？
- 数据怎么收集？
- 人工标注还是模型生成？
- 为什么这么少？

**推荐统一口径**

| 评测集 | 数量 | 来源 | 说明 |
|---|---:|---|---|
| 复杂归因诊断 | 约 100 条 | 运营和业务专家人工构造/标注 | 成本高，要求标注主因、辅因和路径 checkpoint |
| RAG / 知识查询 | 约 300 条 | 真实用户问题 + 运营标注 | 覆盖 FAQ、SOP、多跳知识查询 |
| Text-to-SQL | 约 200 条 | 历史 DI 查询日志 + 人工校验 | 包含 query 与 SQL / 执行结果 |
| 意图识别 SFT | 3K～4K 条 | 历史 query 与人工标签 | 用于小模型五分类 |

**注意**

之前不同面试里出现过 RAG 200 / SQL 300 的口径，后续建议统一成：**复杂任务 100、RAG 300、SQL 200**。如果不确定，可以说“量级上分别是一百、两三百左右”，避免硬背错。

**完整回答**

我们的 Golden Set 是按场景拆的，不是一个混在一起的总集合。

复杂归因诊断大概 100 条，这类样本标注成本最高，因为不只是标答案，还要标主因、辅因、关键排查路径和中间 checkpoint。RAG/知识查询大概 300 条，主要来自真实用户问题和运营标注，覆盖 FAQ、SOP、多跳知识查询。Text-to-SQL 大概 200 条，主要来自历史 DI 查询日志，包含自然语言 query、对应 SQL 或执行结果。意图识别单独有 3K～4K 条样本，用来训练或微调小模型做分类。

为什么复杂任务只有 100 条？主要是因为高质量标注成本高，而且复杂诊断本身需要业务专家参与，不能完全用模型生成。我的做法是先保证核心高频 case 的质量，再通过线上 bad case 持续回流，而不是一开始追求很大的弱标注数据集。

### 5. 评测指标有哪些？schema linking 怎么评估？

**常见问法**

- RAG 怎么评估？
- SQL 怎么评估？
- schema linking 召回率和准确率多少？
- LLM judge 不稳定怎么办？

**推荐指标体系**

| 场景 | 离线指标 | 在线指标 |
|---|---|---|
| RAG | recall@k、NDCG、实体 F1、引用完整率、LLM judge | 采纳率、复问率、点赞/点踩、转人工率 |
| Text-to-SQL | exact match、execution match、schema recall、schema precision | 查询成功率、结果被使用率、重试率 |
| 复杂归因 | 主因/辅因 F1、checkpoint 命中率、路径完整性 | 采纳率、人工修改率、转研发率 |
| Agent 过程 | 无效工具调用数、循环次数、replan 成功率 | 平均完成时长、失败率、用户中断率 |

**现有数字**

| 指标 | 推荐口径 |
|---|---|
| schema linking 召回率 | 80%+ |
| schema linking 准确率 | 70%+ |
| Text-to-SQL 单表准确率 | 约 80% |

**完整回答**

评测上我会分成结果、过程和线上三层。

RAG 离线看 recall@k、NDCG、实体 F1、引用完整率和 LLM judge；线上看采纳率、复问率、点赞点踩和转人工率。Text-to-SQL 离线看 exact match 和 execution match，同时拆 schema linking 的 recall 和 precision。我们更重视 recall，因为关键表或关键列没召回，后面 SQL 生成基本没机会补救；当前 schema linking 召回大概 80% 以上，准确率大概 70% 多。复杂归因看主因/辅因 F1、checkpoint 命中率、路径完整性和最终采纳率。

LLM judge 我不会当唯一指标。能规则化的尽量规则化，比如 SQL execution match、引用是否存在、实体是否命中、工具调用次数。开放问题才用 LLM judge，并且固定 judge 版本、rubric、few-shot 和人工锚点样本，避免评测漂移。

### 6. 团队规模多少？投入多久？你是什么角色？

**常见问法**

- 项目谁发起？
- 投入多少人？
- 做了多久？
- 你在里面是什么角色？

**推荐统一口径**

| 指标 | 推荐表述 |
|---|---|
| 项目周期 | 约 1.5 年 |
| 稳定使用 | 约 1 年 |
| 产品 | 1 人 |
| 研发投入 | 8～10 人左右，非全员长期 100% 投入 |
| 投入强度 | 核心阶段约 50%～60% 精力 |
| 角色 | 工程 Owner / Agent 架构主导 / 后端核心负责人 |
| 职级 | Senior Engineer，约对标 P6～P7 |

**完整回答**

这个项目从立项到多场景交付大概 1.5 年，稳定使用大概 1 年。团队不是一个完全独立的 100% 全职 Agent 团队，而是在广告工程和算法团队里抽核心人力共同推进。

人力口径上，产品大概 1 人，研发和算法合计 8～10 人左右，核心阶段大家大概 50%～60% 精力投入。不同阶段人数会变化，比如 RAG、Text-to-SQL、复杂归因诊断不是完全同一批人同时满负荷做，所以我后续会统一说“8～10 人左右，非全职投入”，避免听起来像十几个人完整投入 1.5 年只做一个内部工具。

我自己的角色是工程 Owner 和 Agent 架构主导，主要负责整体架构设计、意图路由、多 Agent 调度、Plan/Execute、上下文管理、评测和后端工程落地，同时也会和算法、产品、运营一起定义评测和 bad case 迭代。

### 7. 广告系统做了多久？是不是从 0 到 1？

**常见问法**

- 在 Shopee 做广告多久？
- 是不是一直做这个系统？
- 你说 0 到 1，规模有多大？

**推荐统一口径**

| 指标 | 推荐表述 |
|---|---|
| Shopee 总经历 | 约 4 年左右，按实际简历口径对齐 |
| 广告系统 | 接近 3 年，参与垂类广告系统 0 到 1 |
| Agent 项目 | 最近约 1.5 年 |
| 业务边界 | 垂类广告，不是 Shopee 主站最大广告系统 |

**完整回答**

我在 Shopee 的经历可以切成两个阶段。前面接近 3 年主要做垂类广告系统，从 0 到 1 参与在线引擎、数据流、计费链路和广告机制策略建设。后面约 1.5 年更多投入到商家运营智能助手 Agent 项目。

这里的 0 到 1 需要说明边界：它是 Shopee 内部一个垂类广告系统，不是整个 Shopee 主站最大规模的广告系统。所以我会说我深度参与了垂类广告系统从 0 到 1 的建设，而不是夸大成全公司广告主系统。

这个阶段对我的价值是，我既理解广告业务指标，比如 ROAS、预算、出价、消耗节奏，也理解在线系统工程，比如召回、排序、特征、数据同步和计费可靠性。后续做 Agent 项目时，这些业务和工程经验能帮助我判断 Agent 的诊断结果是否真的合理。

### 8. 广告系统规模和性能指标是多少？

**常见问法**

- 候选量多少？
- 广告库多大？
- 在线链路延迟多少？
- 表有多少张？

**推荐统一口径**

| 指标 | 推荐表述 |
|---|---|
| 单路召回候选 | 约 500～600 |
| 在线广告商家 ID | 主要市场 20 万+ |
| Text-to-SQL 涉及表 | 约 50+ 张 Hive 表 |
| 召回延迟 | 约 100ms |
| 排序延迟 | 约 200ms+ |
| 全链路延迟 | 约 600ms |

**完整回答**

广告系统规模要先说明是垂类场景，不是主站全量广告。以我们负责的主要市场和垂类业务为例，在线广告商家 ID 大概 20 万+，单路召回候选大概 500～600。Text-to-SQL 里涉及的离线分析表大概 50+ 张 Hive 表。

在线链路延迟上，召回大概 100ms，排序因为涉及多路模型和特征计算，大概 200ms+，全链路大概 600ms。这里我会说明这是业务链路的大致量级，具体 P95/P99 要看市场、流量和链路配置。

如果面试官追问为什么候选量不大，我会解释这是垂类广告业务，候选空间和主站搜索推荐不同；系统设计上仍然包含召回、过滤、预估、排序、混排、计费等完整广告链路，只是规模和主战系统不在一个量级。

### 9. 广告业务指标怎么提升？ROAS 怎么算？

**常见问法**

- 广告赛道最激动人心的事情是什么？
- ROAS / ROI 怎么定义？
- 你们做了哪些策略提升广告效果？

**现有数字**

| 指标 | 推荐口径 |
|---|---|
| ROAS 定义 | 广告 GMV / 广告 cost |
| 印尼市场早期 ROAS | 约 3～4 |
| 两个季度后 ROAS | 约 7～8 |
| 贡献方式 | 排序、预算平滑、校准、机制策略持续迭代，注意不要把全部提升归因给个人 |

**完整回答**

广告里我最关注的指标之一是 ROAS，也可以理解成广告投入产出比，公式是广告 GMV 除以广告 cost。

在早期阶段，像印尼这类主要市场，部分广告投放的 ROAS 大概只有 3～4，广告主的持续投放意愿不够稳定。后续通过大概两个季度的持续迭代，包括排序公式优化、CTR/CVR 预估校准、预算平滑、出价和消耗节奏优化，把 ROAS 做到 7～8 的水平。

这里我会谨慎表达，这不是我一个人的贡献，而是整个广告工程、算法和策略团队共同迭代的结果。我个人参与的部分主要是在线工程链路、数据流和部分机制策略落地。这个经历让我理解广告系统不是只追求点击率，而是要在平台收入、广告主 ROI、预算消耗节奏和用户体验之间做平衡。

### 10. Agent 链路时延是多少？多轮 ReAct 会不会太慢？

**常见问法**

- Agentic RAG 多轮检索会不会延迟很大？
- Text-to-SQL 一次要多久？
- ReAct 链路性能怎么样？

**推荐统一口径**

| 链路 | 推荐表述 |
|---|---|
| Text-to-SQL | 约 10～20 秒 |
| ReAct / Agentic RAG | 复杂问题约 30 秒量级 |
| 相对单次 RAG | 约 4 倍以上，取决于步数和是否流式展示 |
| 上下文压缩 | 70% 窗口阈值触发，保留前 10% + 后 10% |

**完整回答**

多轮 Agent 链路确实比单次检索生成慢，所以我们不会让所有请求都走 ReAct。

口径上，Text-to-SQL 因为涉及多轮 LLM 调用、schema linking、列值探测和执行纠错，一般在 10～20 秒量级。Agentic RAG 或复杂 ReAct 链路，如果是多跳检索，可能在 30 秒量级，相对单次 RAG 大概会有 4 倍以上开销，具体取决于最大步数、模型速度和是否流式展示中间过程。

我们的取舍是按任务类型分流。简单 FAQ 和事实查询走低延迟路径；SOP、多跳问题、复杂归因才走多轮。对于复杂任务，用户本来可能要花几分钟甚至按小时找研发或数据同学，所以 10～30 秒是可以接受的。但从体验上仍然要做三件事：限制最大步数，流式展示中间进度，对高频固定路径沉淀成 Skill 或 workflow，降低不必要的开放式推理。

### 11. 上下文压缩和记忆有没有量化阈值？

**常见问法**

- 什么时候压缩？
- 怎么保留上下文？
- 长程任务怎么避免上下文爆炸？

**推荐统一口径**

| 指标 | 推荐表述 |
|---|---|
| 压缩触发 | 上下文达到 70% 窗口阈值 |
| 保留策略 | 前 10% + 后 10%，中间摘要并外置 |
| 外置内容 | 大工具结果、SQL 结果、日志、报告草稿 |

**完整回答**

我们会在上下文使用量达到大约 70% 阈值时触发压缩。策略上不是简单保留最近 N 轮，而是保留开头 10% 和最近 10%，中间部分做摘要并外置。

保留开头是因为里面通常有用户原始目标、系统约束和最初计划；保留最近部分是因为它包含当前状态和最新 observation；中间大量工具结果、SQL 返回、日志片段会放到文件系统记忆里，prompt 里只保留摘要和引用。

这个机制解决的是上下文窗口和注意力问题，但它不是完美的。摘要可能丢信息，所以关键 evidence、最终结论、重要 checkpoint 不能只靠摘要，要结构化写入工作区或文件系统，并能在需要时重新读取原始结果。

### 12. AI Coding 效率有没有量化？

**常见问法**

- 公司 AI Coding 推得怎么样？
- 实操效率提升多少？
- 你自己用 AI 写代码有多少产出？

**现有情况**

| 指标 | 当前情况 |
|---|---|
| 公司推广 | Cursor / Codex 等工具额度充足 |
| 统计 | 有使用率/统计率指标，但你没有稳定数值 |
| 个人体感 | 可完成大量代码初稿，人负责 review、上下文、方案判断 |
| 风险 | 缺少 PR 周期缩短、代码接受率等硬数字 |

**完整回答**

AI Coding 这块我们公司推得比较积极，Cursor、Codex 这类工具都有比较充足的额度，也会统计使用情况。但如果说严格量化，比如 PR 周期缩短多少、代码接受率多少，我目前没有一个可以准确对外复述的数字，所以我不会硬编。

从个人实践看，它对有明确上下文和边界的开发任务帮助很大，能完成大量代码初稿、测试补充和重构建议，人更多负责需求澄清、方案判断、上下文补充和 code review。真正的瓶颈不只是模型写代码能力，而是 PRD 是否清楚、代码库上下文是否完整、已有规范和测试是否能被模型读取。

如果要系统化评估 AI Coding，我会看几个指标：需求从 PRD 到技术方案的耗时、代码初稿采纳率、人工 review 修改比例、缺陷率、测试补全率和 PR lead time。这样比单纯说“效率提升很多”更可信。

## 五、面试中推荐主动抛出的“指标包”

### 1. 项目概览指标包

> 这个项目从立项到多场景交付大概 1.5 年，稳定使用约 1 年，主要服务内部广告运营场景。使用量上 DAU 大概 500，Agent 侧 QPS 大概 20+。团队是产品 1 人加研发/算法 8～10 人左右，核心阶段大概 50%～60% 精力投入。我主要负责工程架构和 Agent 调度、记忆、评测等核心模块。

### 2. 效果指标包

> 分场景看，知识查询采纳率大概 70%，单表 Text-to-SQL 准确率大概 80%，复杂归因诊断采纳率大概 70%。Plan 阶段结构合法率从初版约 50% 提升到接近 99%。但我会区分结构正确和业务正确，最终还是看采纳率、主因命中率、转人工率和 bad case 回流。

### 3. 评测指标包

> Golden Set 按场景拆，复杂归因约 100 条，RAG 约 300 条，Text-to-SQL 约 200 条，意图识别另有 3K～4K 条样本。RAG 看 recall@k、NDCG、实体 F1 和引用完整率；SQL 看 exact match、execution match 和 schema linking；归因看主因/辅因 F1、checkpoint 命中和线上采纳率。

### 4. 性能指标包

> Text-to-SQL 一般 10～20 秒，复杂 ReAct / Agentic RAG 大概 30 秒量级，比单次 RAG 慢几倍，所以我们不会所有请求都走多轮。简单 FAQ 走低延迟路径，复杂 SOP、多跳检索和归因诊断才走多轮。广告在线链路上，召回约 100ms，排序约 200ms+，全链路约 600ms。

### 5. 广告业务指标包

> 广告效果里我比较关注 ROAS，也就是广告 GMV / 广告 cost。早期部分主要市场 ROAS 大概 3～4，经过两个季度排序、预算平滑、校准等机制策略迭代后能做到 7～8。这里我会强调这是团队共同结果，我个人主要参与在线链路、数据流和机制策略工程落地。
