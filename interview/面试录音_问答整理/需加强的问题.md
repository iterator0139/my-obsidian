# 需加强的问题：深入版回答

> 口径建议：这些问题不要只答“我们有一个机制”，要把**触发时机、数据结构、准入标准、评估指标、失败处理、边界**讲出来。面试官追问这些点，本质是在判断这个 Agent 项目是不是一个可观测、可治理、可迭代的生产系统。

## 1. 经验记忆怎么抽取的？怎么使用？有例子吗？

### 答题要点

经验记忆不是简单把聊天记录存起来，而是从一次任务执行轨迹里抽取可复用的“过程知识”。我会把它理解成一种 task-level procedural memory，重点记录某类任务怎么拆、调用哪些工具、哪些证据是关键、失败原因是什么。

### 深入回答

我们长期记忆主要沉淀的是任务经验，不是原始对话。一次复杂归因任务结束后，会触发一个 memory extraction 流程，把完整执行轨迹作为输入，包括用户原始 query、最终 plan、每个 DAG 节点的执行状态、工具调用摘要、关键 evidence、最终结论、用户是否采纳、失败节点和失败原因。

抽取时不会把这些原始内容直接写进长期记忆，而是要求模型输出结构化字段，大概包括：

```json
{
  "task_type": "ad_performance_diagnosis",
  "trigger_pattern": "曝光下降/消耗异常/ROI下降等问题模式",
  "preconditions": ["需要广告组ID", "需要时间窗口", "需要对比基线"],
  "successful_steps": [
    "确认异常指标和时间范围",
    "拉取曝光、点击、消耗、转化等核心指标",
    "拆分预算、出价、定向、人群、素材、竞价环境等维度",
    "定位主因并给出证据"
  ],
  "key_evidence": ["某指标环比下降超过阈值", "预算未消耗完/出价低于竞争水平"],
  "failure_modes": ["缺少广告组ID", "查询窗口过短", "表字段口径不一致"],
  "reuse_instruction": "下次遇到同类问题，优先按指标漏斗做逐层排查"
}
```

使用时是在任务开始阶段做检索。用户输入进来后，我们会先做意图识别和 query embedding，然后从长期记忆里召回相似的任务经验。召回后不会原样塞给模型，而是拼到 planner 的 prime 里，告诉它“过去类似任务中有效的拆解方式”和“需要避免的失败模式”。这样长期记忆影响的是 plan 和工具选择，而不是直接替代当前证据。

举个例子，运营问“某广告组这两天曝光突然下降，帮我看原因”。如果长期记忆里有类似曝光下降 case，planner 会优先复用一个诊断模板：先确认异常是否真实存在，再看预算是否耗尽、出价是否低、定向是否变窄、素材审核状态是否异常、竞价环境是否变化。它不会直接套用上一次的结论，而是复用排查路径，并要求每一步重新查当前广告组的数据。

这里的关键边界是：长期记忆只能提供经验先验，不能作为事实证据。最终结论必须来自本次工具查询、RAG 证据或业务数据。

## 2. 怎么避免长期记忆污染？

### 答题要点

长期记忆污染的风险主要有三类：错误事实被复用、偶发经验被过度泛化、过期规则继续影响新任务。治理上要从准入、结构化、冲突检测、版本和回滚四层做。

### 深入回答

我们不会让所有任务结束后都写长期记忆，而是有一个准入链路。第一步是抽取，把原始执行日志压缩成结构化经验；第二步是 judge 打分；第三步是去重、冲突检测和写入。只有高置信、有复用价值、证据完整的经验才会写入。

judge 的 rubric 主要看几类指标：

1. 任务是否成功，比如最终结果是否被用户采纳，或者离线评估是否命中 ground truth。
2. 过程是否完整，比如有没有覆盖必要 checkpoint，是否存在关键证据缺失。
3. 结论是否有 evidence 支撑，不能只是模型主观推理。
4. 泛化价值是否足够，不能是只对某个非常特殊 case 有效的偶发细节。
5. 是否包含噪声或敏感信息，比如完整 SQL 结果、大段日志、用户隐私、临时 token 等。

为了避免“错误经验越用越强”，长期记忆读取时也会控制权重。它只是作为 planner 的候选参考，不允许直接覆盖当前任务的证据。如果长期记忆和当前 RAG 文档、实时查询结果冲突，以当前权威数据源为准，并且把这次冲突记录成 memory conflict case，后续可以对旧记忆降权或删除。

如果是广告规则、SOP 这类有时效性的内容，还要给 memory 加 metadata，比如创建时间、适用业务线、市场、版本号、数据源、置信度。召回时不仅看语义相似度，也要看时间有效性和业务范围匹配。否则很容易出现“旧规则在新政策下继续生效”的污染。

## 3. 长期记忆写入比例有多少？

### 答题要点

不要给一个听起来拍脑袋的绝对数字。可以说设计原则是“宁缺毋滥”，写入比例会远低于任务总量，并按任务类型区分。

### 深入回答

长期记忆的写入比例我们会控制得比较低，因为它会影响后续任务，污染成本比少写一条更高。我的设计原则是宁缺毋滥：短期和工作区记忆可以多记一点，长期记忆只写高价值、高置信、可复用的经验。

如果按任务类型看，简单知识问答和一次性闲聊基本不写长期记忆，因为它们没有太多过程复用价值。Text-to-SQL 如果只是普通取数，也不一定写；只有当它暴露出稳定的 schema mapping、指标口径、字段枚举映射时，才可能沉淀成经验。复杂归因诊断的写入比例会相对高，因为它有明确的任务路径和失败模式。

口径上可以说：我们会把候选经验先进入候选池，再经过 judge 过滤。真正写入长期记忆的大概是完成任务中的一小部分，通常只保留 4 分、5 分这类高质量样本。低分样本不会进入长期记忆，但会进入 bad case 池，用于评测集扩充和后续优化。

这个数字本身不是越高越好。更重要的是监控写入后的有效性，比如 memory hit rate、hit 后任务成功率提升、memory conflict rate、用户纠错率。如果写入比例升高但冲突率也升高，说明准入门槛有问题。

## 4. 达不到准入标准的怎么处理？

### 答题要点

不要只说“丢弃”。低质量样本不能写长期记忆，但它对调试和评测很有价值。

### 深入回答

达不到准入标准的样本会分流处理，而不是直接全部丢弃。

第一类是纯噪声样本，比如任务中断、用户没有给足信息、工具服务超时导致没有有效结果。这类不会写长期记忆，只保留必要的运行日志用于排查稳定性。

第二类是失败但有价值的样本，比如 plan 漏了关键步骤、SQL 字段匹配错、RAG 召回到了过期文档。这类不写长期记忆，但会进入 bad case pool。后续可以把它变成 Golden Set 的一部分，用来回归评测 planner、retriever 或 Text-to-SQL 链路。

第三类是可修复样本，比如摘要抽取格式不对、字段缺失、包含过多工具原始输出。这类可以进入 pending 状态，经过二次抽取、规则清洗或者人工确认后再重新 judge。

所以长期记忆准入不是一个简单的 yes/no，而是一个数据治理流程：高质量样本写入长期记忆，中低质量样本沉淀到评测和 debug，敏感或无效样本直接过滤。

## 5. 抽取摘要和 judge 用哪个模型？为什么选千问3？

### 答题要点

核心不是“千问3好”，而是说明任务需要什么能力：中文理解、结构化抽取、长上下文、推理判断、私有化部署和成本。

### 深入回答

摘要抽取和 judge 当前可以用同一个强模型，例如 Qwen3 系列的大参数模型。原因是这两个任务都不是简单分类，而是需要比较强的中文业务语义理解和结构化推理能力。

摘要抽取要求模型从长执行轨迹中提取 task type、成功步骤、失败节点、关键 evidence 和复用建议。这里容易出的问题是把工具日志原样抄进去，或者把偶发现象总结成通用规律，所以需要模型有较好的信息压缩和泛化能力。

judge 则要求模型按 rubric 判断这条经验是否可写入长期记忆。它要识别过程是否完整、证据是否充分、结论是否过度泛化、是否存在冲突或敏感信息。这也需要较强的推理能力。

选择 Qwen3 主要基于几个考虑：

1. 中文业务场景适配较好，广告运营和 SOP 文档里有大量中文表达。
2. 开源生态成熟，便于私有化部署和版本固定，避免线上评测受外部 API 版本变化影响。
3. 结构化输出能力和推理能力相对稳定，适合做 JSON 抽取和 rubric judge。
4. 成本和可控性比闭源强模型更适合内部批处理链路。

但这里要补一句：judge 模型不能只凭主观感觉选。我们会构建一小批人工标注样本，比如 50 到 100 条任务轨迹，让不同模型做摘要和准入判断，再看和人工标注的一致性、结构化输出成功率、漏判/误判情况。最终选型看的是稳定性、成本和可部署性综合结果。

## 6. 上下文腐烂怎么观测？

### 答题要点

上下文腐烂不是单纯 token 多，而是“模型对早期目标、关键约束和证据的注意力下降”。要从行为指标、过程指标和结果指标观测。

### 深入回答

我会把上下文腐烂定义成：随着上下文变长，模型开始忽略早期目标、误用旧信息、重复调用工具、偏离原始任务，最终导致结果质量下降。它不能只靠体感，需要做可观测指标。

第一类是行为指标。比如平均工具调用次数、重复工具调用率、无效工具调用率、replan 次数、任务执行步数。如果上下文变长后，这些指标明显上升，说明模型可能在丢目标或者无法利用已有结果。

第二类是过程指标。我们可以在 DAG 任务里定义 checkpoint，比如曝光下降诊断必须经过“异常确认、指标拆解、预算检查、出价检查、定向检查、素材/审核检查”等节点。线上执行轨迹可以和黄金路径对齐，计算 checkpoint recall、path similarity、关键 evidence 命中率。如果上下文变长后路径偏离变多，就是上下文腐烂的信号。

第三类是结果指标。比如归因主因 F1、最终采纳率、人工修正率、LLM judge 的 reasoning quality score。还可以做分桶分析，把任务按上下文 token 数分成 0-8k、8-16k、16-32k、32k+，观察随着 token 增长，准确率、工具效率和采纳率是否下降。

更细一点，还可以做“needle in haystack”类探针：在早期上下文里放关键约束，比如“只能使用新加坡市场数据”或“以最新 SOP 为准”，看长链路后模型是否仍然遵守。这个能更直接验证模型对早期约束的保持能力。

## 7. Memory 方案：我们的方案和业界方案有什么区别？

### 答题要点

可以对比 Zep、MemGPT/Letta、LangGraph checkpoint、Claude Code/Cursor 的上下文管理。重点讲：我们的方案更贴近广告运营 Agent 的任务状态和工具结果治理。

### 深入回答

业界 memory 方案大概有几类。Zep 更偏应用层长期记忆，强调从对话中抽取事实、事件、偏好，并做 summary、搜索和部分冲突处理。MemGPT/Letta 更像把内存分成核心上下文、归档记忆和外部存储，让 Agent 学会在上下文窗口和外部记忆之间搬运信息。LangGraph checkpoint 更偏执行状态持久化，用于恢复图执行过程。Claude Code、Cursor 这类 coding agent 则在实践上大量使用 todo、文件引用、工具结果外置和上下文压缩。

我们的四层记忆借鉴了这些思想，但出发点更业务化。短期记忆解决 session 连续性；工作区记忆解决长程归因任务的目标和 plan 状态；文件系统记忆解决 SQL 结果、日志、报表这类大工具结果外置；长期记忆解决成功诊断路径和失败模式复用。

最大的区别有三个：

第一，我们不是只记用户偏好，而是重点记 procedural memory，也就是某类广告诊断任务应该怎么拆、哪些指标要查、哪些路径容易失败。

第二，我们把 memory 和 DAG 执行结合起来。工作区记忆里保存 plan、todo、节点状态和 evidence，所以失败后可以做局部 replan，而不是让模型从一大段聊天历史里自己找状态。

第三，我们对长期记忆做准入和降权。不是所有历史都可复用，只有通过 judge 的经验才写入；召回后也只作为先验，不能替代本次实时数据。

边界上，我们当前方案如果要进一步生产化，还需要加强跨机器持久化、memory 版本管理、冲突自动解决和人工审核后台。

## 8. 开发一个功能的流程是什么？怎么评估、优化？

### 答题要点

按“问题定义 -> 数据和指标 -> 离线开发 -> 离线评测 -> 灰度上线 -> 线上反馈 -> bad case 回流”讲，体现工程闭环。

### 深入回答

我开发 Agent 功能不会先从 prompt 开始，而是先定义任务边界和评价方式。比如要优化复杂归因诊断，第一步要明确它解决哪类问题：曝光下降、ROI 下降、消耗异常，还是预算未消耗。每类问题需要哪些输入、调用哪些工具、最终输出什么结构化结论。

第二步是准备评测集。我们会从历史工单、运营问答、线上 bad case 中构建 Golden Set。每条 case 不只标最终答案，还要尽量标关键路径，比如主因、辅因、必须经过的检查节点、关键证据。这样才能评估 Agent 的过程，而不是只看最后一句话。

第三步是实现功能，比如改 planner prompt、增加工具参数校验、引入 RAG verifier 或优化 Text-to-SQL schema linking。开发完先离线回放 Golden Set，对比 baseline。

离线评估会看三类指标：

1. 结果指标：主因 F1、SQL execution accuracy、RAG answer correctness。
2. 过程指标：checkpoint recall、无效工具调用率、平均工具调用次数、replan 次数。
3. 成本指标：平均延迟、token 消耗、失败重试次数。

如果离线优于 baseline，再做灰度或 AB。线上看运营采纳率、二次追问率、人工修改率、转人工比例和平均处理时长。上线后最重要的是 bad case 回流，把线上失败样本继续加到评测集里，下一轮优化再回归，避免只对少数样本过拟合。

## 9. 能不能把观测性和评测流程自动化串起来？

### 答题要点

可以，而且这是 Agent 工程化的关键。但要分阶段建设：先有 trace，再有自动评测，再有自动诊断，最后才是自动优化。

### 深入回答

理论上可以串起来，我会把它设计成一个 eval-observe-optimize loop。

第一层是全链路 trace。每次 Agent 执行都记录 task id、用户意图、planner 输出、DAG 节点、工具调用参数、工具返回摘要、错误、重试、replan、最终答案、用户反馈。这是后续自动评测和诊断的基础。如果没有结构化 trace，后面只能靠人工看日志。

第二层是自动离线评测。新功能合并前自动回跑 Golden Set，输出不同维度的 score，比如结果正确率、路径命中率、工具效率、成本和延迟。这个可以接到 CI 或 nightly pipeline 里，防止 prompt 或工具改动造成回归。

第三层是线上观测。线上 trace 可以自动聚合成 dashboard，比如各意图流量、成功率、采纳率、平均步数、失败原因分布、工具错误率、memory hit rate、RAG 无证据回答率。发现某个指标劣化后，自动采样 case。

第四层是自动诊断。诊断 Agent 或规则系统读取失败 trace，判断问题来自 planner、retriever、tool、SQL generator、memory 还是 final answer。例如：如果正确证据没进 top k，是检索问题；证据在上下文里但答案错，是生成或引用问题；工具参数缺字段，是 planner 或参数校验问题。

第五层才是自动优化。比如自动生成 prompt patch、补充 few-shot、调整检索参数、生成新的评测样本。但这一步要谨慎，生产系统里建议先 human-in-the-loop，自动给建议，不直接自动上线。

所以答案是可以串起来，但成熟路径应该是：trace 标准化 -> eval 自动化 -> dashboard 观测 -> 自动归因 -> 半自动优化。

## 10. RAG 有没有做数据清洗？数据冲突怎么处理？

### 答题要点

RAG 数据清洗要讲 ingestion pipeline：解析、去重、chunk、metadata、质量过滤、版本管理。冲突处理要讲权威源、时间、业务范围和答案提示。

### 深入回答

RAG 的效果很大程度取决于知识入库质量，所以我们会做基础的数据清洗。文档进入知识库前先做解析，把 Markdown、飞书/Confluence 页面、SOP 文档等统一成结构化文本，保留标题层级、章节路径、更新时间、作者、业务线、市场、文档类型等 metadata。

然后做去噪和规范化，比如去掉导航栏、页脚、重复目录、无意义模板文本；对表格做结构化保留；对过长段落按标题和语义边界切 chunk；对 SOP 类文档保留父子 chunk 关系，避免只召回一个孤立步骤。

冲突主要有几类：

1. 时间冲突：旧政策和新政策同时存在。处理方式是 chunk 加版本和更新时间，召回和生成时优先使用最新有效版本。
2. 业务范围冲突：不同市场、不同广告产品规则不同。处理方式是 metadata filter，比如 region、product、scenario 必须匹配。
3. 权威性冲突：FAQ、聊天记录和正式 SOP 说法不一致。处理方式是给数据源设优先级，正式 SOP 高于临时问答。
4. 内容语义冲突：两个文档都像权威但结论不同。处理方式是答案里提示冲突，不强行合并，并给出引用来源，必要时转人工确认。

生成答案时也会要求模型基于引用证据回答。如果检索到的证据不足或者互相冲突，不允许编一个确定结论，而是输出“不确定原因”和“需要确认的文档/负责人”。

## 11. LLM Wiki 和传统 RAG 的区别？

### 答题要点

传统 RAG 更像 query -> topK chunk -> answer；LLM Wiki 更像结构化知识导航和渐进式阅读。差异在知识组织、检索路径、证据粒度和交互成本。

### 深入回答

传统 RAG 的核心是相似度检索。用户给一个 query，系统用 embedding 或 BM25 找 topK chunk，然后让模型基于这些 chunk 回答。它的优点是简单、延迟低、工程成熟；缺点是语义相似不等于任务相关，尤其在 SOP、多跳问题、长文档和概念层级复杂时，容易召回碎片化证据。

LLM Wiki 或 AI Wiki 更强调把知识组织成可导航、可递进展开的结构。它不像传统 RAG 一上来就拿几个 chunk 回答，而是先理解知识库的目录、主题、实体关系、章节层级，再像人读文档一样逐层定位：先找相关主题，再进入子章节，再展开具体证据。

举例来说，问“预算分配为什么没生效”，传统 RAG 可能召回几个包含“预算分配”的段落，但漏掉上级章节里的适用条件。LLM Wiki 会先定位到“广告预算机制”这个主题，再看“预算分配策略”“生效条件”“异常排查”几个子模块，最后组合回答。

它的优势是证据更完整、适合复杂知识库和多跳问答；代价是工程复杂度高、token 和延迟更大，还需要维护目录、实体、关系和文档版本。我的判断是：高频简单事实查询用传统 RAG 就够；复杂 SOP、跨文档归因、需要逐层解释的知识，更适合 LLM Wiki 或 Agentic RAG。

## 12. 知识工程的发展怎么看？

### 答题要点

可以从“人工知识库 -> 检索增强 -> Agentic Knowledge -> 可执行知识”讲。重点是知识不再只是给人读，而是给 Agent 执行和验证。

### 深入回答

我理解知识工程正在从静态文档管理，走向面向 Agent 的动态知识系统。

第一阶段是传统知识库，核心是把文档存好、分类好、能搜索。这个阶段主要服务人，问题是知识更新慢、结构不统一、很难直接驱动自动化。

第二阶段是 RAG，把非结构化文档接到大模型上，让模型可以基于文档回答问题。这个阶段解决了“找得到、答得出”的问题，但仍然依赖 chunk 召回，容易受文档质量、切分和冲突影响。

第三阶段是 Agentic Knowledge。知识不仅是被检索，还会参与任务规划。比如 SOP 不只是文本，而是可以转成 checklist、decision tree、tool schema、workflow。Agent 读到一个诊断 SOP 后，不只是总结给用户，而是能按步骤调用工具验证。

第四阶段我觉得会走向可执行知识。也就是把知识、工具和评测连接起来：规则可以被版本化，SOP 可以被编译成 workflow，指标口径可以绑定 SQL/API，执行结果可以反向更新知识库。知识系统不再是文档仓库，而是 Agent 的操作系统之一。

所以我看知识工程的关键趋势是：从“人读的知识”变成“模型可检索、可推理、可执行、可验证的知识”。

## 13. 哪些 Agent 产品比较好？

### 答题要点

不要只说“Claude Code 很强”。要讲它们强在哪里，以及能借鉴什么。

### 深入回答

我会分几类看 Agent 产品。

编码 Agent 里，Claude Code 和 Cursor 是很好的标杆。Claude Code 的优势是长程任务执行稳定，工具调用和代码理解能力强，尤其擅长在大型代码库里规划、编辑、测试、修复。Cursor 的优势是 IDE 集成做得好，能把上下文、文件编辑、diff、终端、用户交互结合起来，产品体验更完整。

通用任务 Agent 里，Manus、ChatGPT Agent、Gemini 这类产品展示了浏览器、文件、工具和多步任务结合的方向。它们的价值不只是模型聪明，而是把任务环境搭出来，让模型能持续观察、执行、修正。

知识和企业场景里，Glean、Perplexity、Notion AI、Dust 也有参考价值。它们不是完全自动执行型 Agent，但在企业知识连接、权限控制、引用证据和搜索体验上做得比较实用。

我最关注的不是 UI，而是几类底层能力：第一是上下文管理，长任务过程中如何压缩、引用和恢复；第二是工具治理，参数校验、权限、失败重试、幂等；第三是可观测性，用户能否看到执行路径和证据；第四是评测闭环，线上失败能否回流优化。

对我们广告运营 Agent 的启发是：不要只追求模型回答更聪明，而要把工具调用链路、计划可视化、证据引用、失败恢复和评测体系做扎实。

## 14. 怎么理解 Agent 开发的壁垒？

### 答题要点

Agent 壁垒不是单个 prompt，也不是单纯模型能力，而是“模型理解 + 工具系统 + 业务建模 + 评测治理 + 数据闭环”的综合工程能力。

### 深入回答

我理解 Agent 开发的壁垒有五层。

第一层是模型边界理解。要知道模型擅长什么、不擅长什么。模型擅长语义理解、规划草案、非结构化总结，但不擅长可靠计算、权限判断、事实保证和稳定执行。所以能用代码、规则、workflow 固化的部分，不应该都交给模型。

第二层是任务建模能力。Agent 不是把用户话术直接丢给模型，而是要把业务问题拆成意图、状态、工具、约束、证据和输出格式。比如广告归因不是“问模型为什么下降”，而是拆成指标漏斗、预算、出价、定向、素材、竞价环境等可验证节点。

第三层是工具和执行系统。生产 Agent 的核心是能安全、稳定地调用工具。这里包括工具 schema、参数校验、权限控制、超时重试、幂等、副作用隔离、执行 trace 和错误恢复。

第四层是记忆和上下文管理。长程任务如果没有工作区状态、文件外置、压缩和长期经验准入，很快会上下文膨胀、目标漂移、错误经验污染。

第五层是评测和数据闭环。Agent 不可能一次设计就完美，必须有 Golden Set、线上 trace、bad case 回流、自动回归和业务指标，否则无法判断一次改动到底变好了还是变差了。

所以我的判断是，Agent 工程师的壁垒不是会不会调 API，而是能不能把不稳定的大模型能力放进一个可控的业务系统里，让它可观测、可评估、可恢复、可持续优化。
