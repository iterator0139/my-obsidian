# 需加强的问题：深入版回答

> 口径建议：这些问题不要只答“我们有一个机制”，要把**触发时机、数据结构、准入标准、评估指标、失败处理、边界**讲出来。面试官追问这些点，本质是在判断这个 Agent 项目是不是一个可观测、可治理、可迭代的生产系统。

## 1. 经验记忆怎么抽取的？怎么使用？有例子吗？

### 答题要点

经验记忆不是简单把聊天记录存起来，而是从一次任务执行轨迹里抽取可复用的“过程知识”。我会把它理解成一种 task-level procedural memory，重点记录某类任务怎么拆、调用哪些工具、哪些证据是关键、失败原因是什么。

### 深入回答

我们长期记忆主要沉淀的是任务经验，不是原始对话。一次复杂归因任务结束后，会触发一个 memory extraction 流程，把完整执行轨迹作为输入，包括用户原始 query、最终 plan、每个 DAG 节点的执行状态、工具调用摘要、关键 evidence、最终结论、用户是否采纳、失败节点和失败原因。

抽取时不会把这些原始内容直接写进长期记忆，而是要求模型输出结构化字段，大概包括：

```json
{
  "task_type": "ad_performance_diagnosis",
  "trigger_pattern": "曝光下降/消耗异常/ROI下降等问题模式",
  "preconditions": ["需要广告组ID", "需要时间窗口", "需要对比基线"],
  "successful_steps": [
    "确认异常指标和时间范围",
    "拉取曝光、点击、消耗、转化等核心指标",
    "拆分预算、出价、定向、人群、素材、竞价环境等维度",
    "定位主因并给出证据"
  ],
  "key_evidence": ["某指标环比下降超过阈值", "预算未消耗完/出价低于竞争水平"],
  "failure_modes": ["缺少广告组ID", "查询窗口过短", "表字段口径不一致"],
  "reuse_instruction": "下次遇到同类问题，优先按指标漏斗做逐层排查"
}
```

使用时是在任务开始阶段做检索。用户输入进来后，我们会先做意图识别和 query embedding，然后从长期记忆里召回相似的任务经验。召回后不会原样塞给模型，而是拼到 planner 的 prime 里，告诉它“过去类似任务中有效的拆解方式”和“需要避免的失败模式”。这样长期记忆影响的是 plan 和工具选择，而不是直接替代当前证据。

举个例子，运营问“某广告组这两天曝光突然下降，帮我看原因”。如果长期记忆里有类似曝光下降 case，planner 会优先复用一个诊断模板：先确认异常是否真实存在，再看预算是否耗尽、出价是否低、定向是否变窄、素材审核状态是否异常、竞价环境是否变化。它不会直接套用上一次的结论，而是复用排查路径，并要求每一步重新查当前广告组的数据。

这里的关键边界是：长期记忆只能提供经验先验，不能作为事实证据。最终结论必须来自本次工具查询、RAG 证据或业务数据。

## 2. 怎么避免长期记忆污染？

### 答题要点

长期记忆污染的风险主要有三类：错误事实被复用、偶发经验被过度泛化、过期规则继续影响新任务。治理上要从准入、结构化、冲突检测、版本和回滚四层做。

### 深入回答

我们不会让所有任务结束后都写长期记忆，而是有一个准入链路。第一步是抽取，把原始执行日志压缩成结构化经验；第二步是 judge 打分；第三步是去重、冲突检测和写入。只有高置信、有复用价值、证据完整的经验才会写入。

judge 的 rubric 主要看几类指标：成功/完整/忠实/泛化/噪声

1. 任务是否成功，比如最终结果是否被用户采纳，或者离线评估是否命中 ground truth。
2. 过程是否完整，比如有没有覆盖必要 checkpoint，是否存在关键证据缺失。
3. 结论是否有 evidence 支撑，不能只是模型主观推理。
4. 泛化价值是否足够，不能是只对某个非常特殊 case 有效的偶发细节。
5. 是否包含噪声或敏感信息，比如完整 SQL 结果、大段日志、用户隐私、临时 token 等。

为了避免“错误经验越用越强”，长期记忆读取时也会控制权重。它只是作为 planner 的候选参考，不允许直接覆盖当前任务的证据。如果长期记忆和当前 RAG 文档、实时查询结果冲突，以当前权威数据源为准，并且把这次冲突记录成 memory conflict case，后续可以对旧记忆降权或删除。

如果是广告规则、SOP 这类有时效性的内容，还要给 memory 加 metadata，比如创建时间、适用业务线、市场、版本号、数据源、置信度。召回时不仅看语义相似度，也要看时间有效性和业务范围匹配。否则很容易出现“旧规则在新政策下继续生效”的污染。

## 3. 长期记忆写入比例有多少？

### 答题要点

不要给一个听起来拍脑袋的绝对数字。可以说设计原则是“宁缺毋滥”，写入比例会远低于任务总量，并按任务类型区分。

### 深入回答

长期记忆的写入比例我们会控制得比较低，因为它会影响后续任务，污染成本比少写一条更高。我的设计原则是宁缺毋滥：短期和工作区记忆可以多记一点，长期记忆只写高价值、高置信、可复用的经验。

如果按任务类型看，简单知识问答和一次性闲聊基本不写长期记忆，因为它们没有太多过程复用价值。Text-to-SQL 如果只是普通取数，也不一定写；只有当它暴露出稳定的 schema mapping、指标口径、字段枚举映射时，才可能沉淀成经验。复杂归因诊断的写入比例会相对高，因为它有明确的任务路径和失败模式。

口径上可以说：我们会把候选经验先进入候选池，再经过 judge 过滤。真正写入长期记忆的大概是完成任务中的一小部分，通常只保留 4 分、5 分这类高质量样本。低分样本不会进入长期记忆，但会进入 bad case 池，用于评测集扩充和后续优化。

这个数字本身不是越高越好。更重要的是监控写入后的有效性，比如 memory hit rate、hit 后任务成功率提升、memory conflict rate、用户纠错率。如果写入比例升高但冲突率也升高，说明准入门槛有问题。

## 4. 达不到准入标准的怎么处理？

### 答题要点

不要只说“丢弃”。低质量样本不能写长期记忆，但它对调试和评测很有价值。

### 深入回答

达不到准入标准的样本会分流处理，而不是直接全部丢弃。

第一类是纯噪声样本，比如任务中断、用户没有给足信息、工具服务超时导致没有有效结果。这类不会写长期记忆，只保留必要的运行日志用于排查稳定性。

第二类是失败但有价值的样本，比如 plan 漏了关键步骤、SQL 字段匹配错、RAG 召回到了过期文档。这类不写长期记忆，但会进入 bad case pool。后续可以把它变成 Golden Set 的一部分，用来回归评测 planner、retriever 或 Text-to-SQL 链路。

第三类是可修复样本，比如摘要抽取格式不对、字段缺失、包含过多工具原始输出。这类可以进入 pending 状态，经过二次抽取、规则清洗或者人工确认后再重新 judge。

所以长期记忆准入不是一个简单的 yes/no，而是一个数据治理流程：高质量样本写入长期记忆，中低质量样本沉淀到评测和 debug，敏感或无效样本直接过滤。

## 5. 抽取摘要和 judge 用哪个模型？为什么选千问3？

### 答题要点

核心不是“千问3好”，而是说明任务需要什么能力：中文理解、结构化抽取、长上下文、推理判断、私有化部署和成本。

### 深入回答

摘要抽取和 judge 当前可以用同一个强模型，例如 Qwen3 系列的大参数模型。原因是这两个任务都不是简单分类，而是需要比较强的中文业务语义理解和结构化推理能力。

摘要抽取要求模型从长执行轨迹中提取 task type、成功步骤、失败节点、关键 evidence 和复用建议。这里容易出的问题是把工具日志原样抄进去，或者把偶发现象总结成通用规律，所以需要模型有较好的信息压缩和泛化能力。

judge 则要求模型按 rubric 判断这条经验是否可写入长期记忆。它要识别过程是否完整、证据是否充分、结论是否过度泛化、是否存在冲突或敏感信息。这也需要较强的推理能力。

选择 Qwen3 主要基于几个考虑：

1. 中文业务场景适配较好，广告运营和 SOP 文档里有大量中文表达。
2. 开源生态成熟，便于私有化部署和版本固定，避免线上评测受外部 API 版本变化影响。
3. 结构化输出能力和推理能力相对稳定，适合做 JSON 抽取和 rubric judge。
4. 成本和可控性比闭源强模型更适合内部批处理链路。

但这里要补一句：judge 模型不能只凭主观感觉选。我们会构建一小批人工标注样本，比如 50 到 100 条任务轨迹，让不同模型做摘要和准入判断，再看和人工标注的一致性、结构化输出成功率、漏判/误判情况。最终选型看的是稳定性、成本和可部署性综合结果。

## 6. 上下文腐烂怎么观测？

### 答题要点

上下文腐烂不是单纯 token 多，而是“模型对早期目标、关键约束和证据的注意力下降”。要从行为指标、过程指标和结果指标观测。

### 深入回答

我会把上下文腐烂定义成：随着上下文变长，模型开始忽略早期目标、误用旧信息、重复调用工具、偏离原始任务，最终导致结果质量下降。它不能只靠体感，需要做可观测指标。

第一类是行为指标。比如平均工具调用次数、重复工具调用率、无效工具调用率、replan 次数、任务执行步数。如果上下文变长后，这些指标明显上升，说明模型可能在丢目标或者无法利用已有结果。

第二类是过程指标。我们可以在 DAG 任务里定义 checkpoint，比如曝光下降诊断必须经过“异常确认、指标拆解、预算检查、出价检查、定向检查、素材/审核检查”等节点。线上执行轨迹可以和黄金路径对齐，计算 checkpoint recall、path similarity、关键 evidence 命中率。如果上下文变长后路径偏离变多，就是上下文腐烂的信号。

第三类是结果指标。比如归因主因 F1、最终采纳率、人工修正率、LLM judge 的 reasoning quality score。还可以做分桶分析，把任务按上下文 token 数分成 0-8k、8-16k、16-32k、32k+，观察随着 token 增长，准确率、工具效率和采纳率是否下降。

更细一点，还可以做“needle in haystack”类探针：在早期上下文里放关键约束，比如“只能使用新加坡市场数据”或“以最新 SOP 为准”，看长链路后模型是否仍然遵守。这个能更直接验证模型对早期约束的保持能力。

## 7. Memory 方案：我们的方案和业界方案有什么区别？

### 答题要点

可以对比 Zep、MemGPT/Letta、LangGraph checkpoint、Claude Code/Cursor 的上下文管理。重点讲：我们的方案更贴近广告运营 Agent 的任务状态和工具结果治理。

### 深入回答

业界 memory 方案大概有几类。Zep 更偏应用层长期记忆，强调从对话中抽取事实、事件、偏好，并做 summary、搜索和部分冲突处理。MemGPT/Letta 更像把内存分成核心上下文、归档记忆和外部存储，让 Agent 学会在上下文窗口和外部记忆之间搬运信息。LangGraph checkpoint 更偏执行状态持久化，用于恢复图执行过程。Claude Code、Cursor 这类 coding agent 则在实践上大量使用 todo、文件引用、工具结果外置和上下文压缩。

我们的四层记忆借鉴了这些思想，但出发点更业务化。短期记忆解决 session 连续性；工作区记忆解决长程归因任务的目标和 plan 状态；文件系统记忆解决 SQL 结果、日志、报表这类大工具结果外置；长期记忆解决成功诊断路径和失败模式复用。

最大的区别有三个：

第一，我们不是只记用户偏好，而是重点记 procedural memory，也就是某类广告诊断任务应该怎么拆、哪些指标要查、哪些路径容易失败。

第二，我们把 memory 和 DAG 执行结合起来。工作区记忆里保存 plan、todo、节点状态和 evidence，所以失败后可以做局部 replan，而不是让模型从一大段聊天历史里自己找状态。

第三，我们对长期记忆做准入和降权。不是所有历史都可复用，只有通过 judge 的经验才写入；召回后也只作为先验，不能替代本次实时数据。

边界上，我们当前方案如果要进一步生产化，还需要加强跨机器持久化、memory 版本管理、冲突自动解决和人工审核后台。

## 8. 开发一个功能的流程是什么？怎么评估、优化？

### 答题要点

按“问题定义 -> 数据和指标 -> 离线开发 -> 离线评测 -> 灰度上线 -> 线上反馈 -> bad case 回流”讲，体现工程闭环。

### 深入回答

我开发 Agent 功能不会先从 prompt 开始，而是先定义任务边界和评价方式。比如要优化复杂归因诊断，第一步要明确它解决哪类问题：曝光下降、ROI 下降、消耗异常，还是预算未消耗。每类问题需要哪些输入、调用哪些工具、最终输出什么结构化结论。

第二步是准备评测集。我们会从历史工单、运营问答、线上 bad case 中构建 Golden Set。每条 case 不只标最终答案，还要尽量标关键路径，比如主因、辅因、必须经过的检查节点、关键证据。这样才能评估 Agent 的过程，而不是只看最后一句话。

第三步是实现功能，比如改 planner prompt、增加工具参数校验、引入 RAG verifier 或优化 Text-to-SQL schema linking。开发完先离线回放 Golden Set，对比 baseline。

离线评估会看三类指标：

1. 结果指标：主因 F1、SQL execution accuracy、RAG answer correctness。
2. 过程指标：checkpoint recall、无效工具调用率、平均工具调用次数、replan 次数。
3. 成本指标：平均延迟、token 消耗、失败重试次数。

如果离线优于 baseline，再做灰度或 AB。线上看运营采纳率、二次追问率、人工修改率、转人工比例和平均处理时长。上线后最重要的是 bad case 回流，把线上失败样本继续加到评测集里，下一轮优化再回归，避免只对少数样本过拟合。

## 9. 能不能把观测性和评测流程自动化串起来？

### 答题要点

可以，而且这是 Agent 工程化的关键。但要分阶段建设：先有 trace，再有自动评测，再有自动诊断，最后才是自动优化。

### 深入回答

理论上可以串起来，我会把它设计成一个 eval-observe-optimize loop。

第一层是全链路 trace。每次 Agent 执行都记录 task id、用户意图、planner 输出、DAG 节点、工具调用参数、工具返回摘要、错误、重试、replan、最终答案、用户反馈。这是后续自动评测和诊断的基础。如果没有结构化 trace，后面只能靠人工看日志。

第二层是自动离线评测。新功能合并前自动回跑 Golden Set，输出不同维度的 score，比如结果正确率、路径命中率、工具效率、成本和延迟。这个可以接到 CI 或 nightly pipeline 里，防止 prompt 或工具改动造成回归。

第三层是线上观测。线上 trace 可以自动聚合成 dashboard，比如各意图流量、成功率、采纳率、平均步数、失败原因分布、工具错误率、memory hit rate、RAG 无证据回答率。发现某个指标劣化后，自动采样 case。

第四层是自动诊断。诊断 Agent 或规则系统读取失败 trace，判断问题来自 planner、retriever、tool、SQL generator、memory 还是 final answer。例如：如果正确证据没进 top k，是检索问题；证据在上下文里但答案错，是生成或引用问题；工具参数缺字段，是 planner 或参数校验问题。

第五层才是自动优化。比如自动生成 prompt patch、补充 few-shot、调整检索参数、生成新的评测样本。但这一步要谨慎，生产系统里建议先 human-in-the-loop，自动给建议，不直接自动上线。

所以答案是可以串起来，但成熟路径应该是：trace 标准化 -> eval 自动化 -> dashboard 观测 -> 自动归因 -> 半自动优化。

## 10. RAG 有没有做数据清洗？数据冲突怎么处理？

### 答题要点

RAG 数据清洗要讲 ingestion pipeline：解析、去重、chunk、metadata、质量过滤、版本管理。冲突处理要讲权威源、时间、业务范围和答案提示。

### 深入回答

RAG 的效果很大程度取决于知识入库质量，所以我们会做基础的数据清洗。文档进入知识库前先做解析，把 Markdown、飞书/Confluence 页面、SOP 文档等统一成结构化文本，保留标题层级、章节路径、更新时间、作者、业务线、市场、文档类型等 metadata。

然后做去噪和规范化，比如去掉导航栏、页脚、重复目录、无意义模板文本；对表格做结构化保留；对过长段落按标题和语义边界切 chunk；对 SOP 类文档保留父子 chunk 关系，避免只召回一个孤立步骤。

冲突主要有几类：

1. 时间冲突：旧政策和新政策同时存在。处理方式是 chunk 加版本和更新时间，召回和生成时优先使用最新有效版本。
2. 业务范围冲突：不同市场、不同广告产品规则不同。处理方式是 metadata filter，比如 region、product、scenario 必须匹配。
3. 权威性冲突：FAQ、聊天记录和正式 SOP 说法不一致。处理方式是给数据源设优先级，正式 SOP 高于临时问答。
4. 内容语义冲突：两个文档都像权威但结论不同。处理方式是答案里提示冲突，不强行合并，并给出引用来源，必要时转人工确认。

生成答案时也会要求模型基于引用证据回答。如果检索到的证据不足或者互相冲突，不允许编一个确定结论，而是输出“不确定原因”和“需要确认的文档/负责人”。

## 11. LLM Wiki 和传统 RAG 的区别？

### 答题要点

传统 RAG 更像 query -> topK chunk -> answer；LLM Wiki 更像结构化知识导航和渐进式阅读。差异在知识组织、检索路径、证据粒度和交互成本。

### 深入回答

传统 RAG 的核心是相似度检索。用户给一个 query，系统用 embedding 或 BM25 找 topK chunk，然后让模型基于这些 chunk 回答。它的优点是简单、延迟低、工程成熟；缺点是语义相似不等于任务相关，尤其在 SOP、多跳问题、长文档和概念层级复杂时，容易召回碎片化证据。

LLM Wiki 或 AI Wiki 更强调把知识组织成可导航、可递进展开的结构。它不像传统 RAG 一上来就拿几个 chunk 回答，而是先理解知识库的目录、主题、实体关系、章节层级，再像人读文档一样逐层定位：先找相关主题，再进入子章节，再展开具体证据。

举例来说，问“预算分配为什么没生效”，传统 RAG 可能召回几个包含“预算分配”的段落，但漏掉上级章节里的适用条件。LLM Wiki 会先定位到“广告预算机制”这个主题，再看“预算分配策略”“生效条件”“异常排查”几个子模块，最后组合回答。

它的优势是证据更完整、适合复杂知识库和多跳问答；代价是工程复杂度高、token 和延迟更大，还需要维护目录、实体、关系和文档版本。我的判断是：高频简单事实查询用传统 RAG 就够；复杂 SOP、跨文档归因、需要逐层解释的知识，更适合 LLM Wiki 或 Agentic RAG。

## 12. 知识工程的发展怎么看？

### 答题要点

可以从“人工知识库 -> 检索增强 -> Agentic Knowledge -> 可执行知识”讲。重点是知识不再只是给人读，而是给 Agent 执行和验证。

### 深入回答

我理解知识工程正在从静态文档管理，走向面向 Agent 的动态知识系统。

第一阶段是传统知识库，核心是把文档存好、分类好、能搜索。这个阶段主要服务人，问题是知识更新慢、结构不统一、很难直接驱动自动化。

第二阶段是 RAG，把非结构化文档接到大模型上，让模型可以基于文档回答问题。这个阶段解决了“找得到、答得出”的问题，但仍然依赖 chunk 召回，容易受文档质量、切分和冲突影响。

第三阶段是 Agentic Knowledge。知识不仅是被检索，还会参与任务规划。比如 SOP 不只是文本，而是可以转成 checklist、decision tree、tool schema、workflow。Agent 读到一个诊断 SOP 后，不只是总结给用户，而是能按步骤调用工具验证。

第四阶段我觉得会走向可执行知识。也就是把知识、工具和评测连接起来：规则可以被版本化，SOP 可以被编译成 workflow，指标口径可以绑定 SQL/API，执行结果可以反向更新知识库。知识系统不再是文档仓库，而是 Agent 的操作系统之一。

所以我看知识工程的关键趋势是：从“人读的知识”变成“模型可检索、可推理、可执行、可验证的知识”。

## 13. 哪些 Agent 产品比较好？

### 答题要点

不要只说“Claude Code 很强”。要讲它们强在哪里，以及能借鉴什么。

### 深入回答

我会分几类看 Agent 产品。

编码 Agent 里，Claude Code 和 Cursor 是很好的标杆。Claude Code 的优势是长程任务执行稳定，工具调用和代码理解能力强，尤其擅长在大型代码库里规划、编辑、测试、修复。Cursor 的优势是 IDE 集成做得好，能把上下文、文件编辑、diff、终端、用户交互结合起来，产品体验更完整。

通用任务 Agent 里，Manus、ChatGPT Agent、Gemini 这类产品展示了浏览器、文件、工具和多步任务结合的方向。它们的价值不只是模型聪明，而是把任务环境搭出来，让模型能持续观察、执行、修正。

知识和企业场景里，Glean、Perplexity、Notion AI、Dust 也有参考价值。它们不是完全自动执行型 Agent，但在企业知识连接、权限控制、引用证据和搜索体验上做得比较实用。

我最关注的不是 UI，而是几类底层能力：第一是上下文管理，长任务过程中如何压缩、引用和恢复；第二是工具治理，参数校验、权限、失败重试、幂等；第三是可观测性，用户能否看到执行路径和证据；第四是评测闭环，线上失败能否回流优化。

对我们广告运营 Agent 的启发是：不要只追求模型回答更聪明，而要把工具调用链路、计划可视化、证据引用、失败恢复和评测体系做扎实。

## 14. 怎么理解 Agent 开发的壁垒？

### 答题要点

Agent 壁垒不是单个 prompt，也不是单纯模型能力，而是“模型理解 + 工具系统 + 业务建模 + 评测治理 + 数据闭环”的综合工程能力。

### 深入回答

我理解 Agent 开发的壁垒有五层。

第一层是模型边界理解。要知道模型擅长什么、不擅长什么。模型擅长语义理解、规划草案、非结构化总结，但不擅长可靠计算、权限判断、事实保证和稳定执行。所以能用代码、规则、workflow 固化的部分，不应该都交给模型。

第二层是任务建模能力。Agent 不是把用户话术直接丢给模型，而是要把业务问题拆成意图、状态、工具、约束、证据和输出格式。比如广告归因不是“问模型为什么下降”，而是拆成指标漏斗、预算、出价、定向、素材、竞价环境等可验证节点。

第三层是工具和执行系统。生产 Agent 的核心是能安全、稳定地调用工具。这里包括工具 schema、参数校验、权限控制、超时重试、幂等、副作用隔离、执行 trace 和错误恢复。

第四层是记忆和上下文管理。长程任务如果没有工作区状态、文件外置、压缩和长期经验准入，很快会上下文膨胀、目标漂移、错误经验污染。

第五层是评测和数据闭环。Agent 不可能一次设计就完美，必须有 Golden Set、线上 trace、bad case 回流、自动回归和业务指标，否则无法判断一次改动到底变好了还是变差了。

所以我的判断是，Agent 工程师的壁垒不是会不会调 API，而是能不能把不稳定的大模型能力放进一个可控的业务系统里，让它可观测、可评估、可恢复、可持续优化。


## 15. 文件系统记忆的写入时机、同步/异步、摘要和信息损失

### 答题要点

文件系统记忆的核心不是"存文件"，而是"在不阻塞 Agent 执行的前提下，把大体积工具结果从 prompt 里移出去，同时保留可用的引用和关键证据"。要讲清楚写入时机、同步异步选择、摘要策略和信息损失的治理边界。

### 深入回答

**写入时机**上，文件系统记忆是在每次工具调用返回结果后触发的，不是在任务结束后统一写。原因是工具结果体积一旦过大（比如 SQL 返回几千行、日志几十 KB），就会迅速挤占上下文窗口，必须立即外置。触发条件是结果大小超过阈值时才外置，小结果（比如单个数值、短 JSON）直接保留在 prompt 里，不需要走文件系统。

**同步还是异步**，我倾向于异步写入，但不是纯异步。具体的做法是：工具调用返回后，先在内存里做一个 fast path 判断——结果是否超过阈值、是否包含关键结构化字段。如果超过阈值，立刻做一个轻量摘要（比如提取行数、列名、关键聚合值、是否有空结果），把摘要和文件路径注入到当前轮次的上下文里，然后异步把完整结果写入文件系统。下一个推理轮次时，文件已经写完了，模型如果需要细节，可以通过文件引用去读取。这样做的好处是当前轮次不阻塞，后续轮次数据已经就位。

**怎么使用**上，prompt 里不会塞完整结果，而是注入三样东西：一个结果摘要（比如"查询返回 342 行，包含 campaign_id、impressions、clicks、cost 四列，其中 impressions 列在最近 7 天下降 42%"）、一个文件路径引用（比如 `/tasks/task_123/results/sql_001.json`）、以及一个读取指令（告诉模型如果需要对细节做进一步分析，可以再次调用 read_file 类型的工具去读完整结果）。这样模型在需要做二次分析时仍然能获取原始数据，但日常推理不受大结果干扰。

**摘要时间长的处理**上，有两层机制。第一，摘要不是用强模型做全文精读，而是用规则 + 轻量模型做结构化抽取——比如 SQL 结果只抽取列名、行数、聚合统计和异常标记，不需要理解每一行的业务含义；日志类结果只抽取错误码、时间范围和关键关键词。这个抽取在毫秒到秒级就能完成。第二，如果摘要本身也很耗时（比如结果体量确实巨大），就用截断 + 采样的方式——先写文件，再对前 N 行做摘要，标注"完整结果共 X 行，以下为前 N 行摘要"。极端情况下，甚至可以标记为"结果过大，不建议直接传入上下文，请通过文件引用按需读取"。

**信息损失怎么处理**上，我的立场是：文件系统记忆一定会损失信息，但损失可控。控制方式有三层。第一层是摘要模板，不同工具类型有不同的摘要 schema——SQL 类必须保留列名、行数、聚合值、空值标记；日志类必须保留错误码和时间；RAG 检索结果必须保留 chunk id、来源文档和相关性分数。第二层是完整性标记，摘要里会显式标注"完整结果包含 X 行/条记录"，让模型知道摘要只是摘要，它在需要时可以请求完整数据。第三层是证据溯源，任何从文件系统记忆里抽取出来用于最终结论的证据，必须能通过文件引用的路径追溯到原始结果。评测时也会检查最终结论中的关键数据点是否和原始文件一致。

边界上，这套方案适合工具结果体积大但结构相对固定的场景。如果结果本身需要模型完整理解每一行才能做推理（比如逐行分析用户评论情感），那文件外置和摘要就有实质损失，需要更强的分阶段处理机制，而不是简单摘要。

## 16. 任务中断和记忆恢复：分布式、远端存储、机器挂了

### 答题要点

这是你的"短板题"，要诚实区分当前现状和生产化演进。核心逻辑是：当前是单机进程级方案，不具备生产级高可用；但你理解从"能跑"到"能恢复"需要做哪些事——状态持久化、checkpoint、task 路由、幂等。

### 深入回答

首先要分当前现状和生产化演进来讲。

**当前项目现状**是，文件系统记忆和工作区状态主要存在执行机器的本地磁盘上，没有做跨机器的状态同步。如果一个长程任务在机器 A 上跑了一半，机器 A 挂了，这个任务确实就丢失了，需要用户重新发起。当前项目更多是"运营 Copilot"阶段，任务大多是几分钟到十几分钟的短会话，机器故障概率相对可控，所以没有优先投入分布式状态管理。但我也清楚，如果要把它做成生产级系统，这个问题必须解决。

**如果可以演进成生产化方案**，我的设计思路是三层改造。

第一层是**状态持久化**。把 task id、session id、plan DAG、todo 状态、每个节点的执行状态和文件系统引用，从进程内存落到持久化存储里。存储选型上，高频读写的工作区状态（plan、todo）可以用 Redis 或类似 KV 存储，因为它读写频繁、体积小、需要低延迟；文件系统记忆（工具结果）可以用 S3 或 HDFS 这类对象存储，体积大、读频次低。每次 DAG 节点执行完成后，异步写一次 checkpoint，记录当前节点 ID、执行状态、输出文件引用和下游依赖节点的状态。

第二层是**任务恢复**。当任务中断后重新调度时，系统根据 task id 从持久化存储里加载最新的 checkpoint，重建 plan、todo、已完成节点的结果引用和受影响节点列表。恢复后不是从头重新执行，而是从第一个未完成且前置依赖都满足的节点继续。关键设计是：已完成节点的输出文件引用仍然有效（因为存在远端对象存储），planner 只需要判断是否有节点需要 replan，而不是重跑一切。

第三层是**分布式路由和幂等**。同一个 task 的后续请求，通过 task id 做一致性哈希或路由表，保证请求打到持有该 task 状态的机器或能从远端加载状态的机器上。工具调用必须有 request id 和幂等设计——如果恢复后重跑了某个节点，对应工具调用不会因为重复执行产生副作用（比如重复发通知、重复创建广告计划）。

**远端存储实时写的处理**上，不需要每个工具调用都同步写远端，那样延迟太高。策略是：工具结果先写本地，摘要注入上下文，异步批量上传到对象存储。只有在上传确认完成后，checkpoint 才标记该节点为"远端已完成"。如果机器在上传完成前挂了，这个节点的结果丢失，但可以从 checkpoint 里看到该节点"本地已完成，远端未上传"，恢复后重新执行该节点即可。

**机器本地挂了怎么办**，分了两个维度。如果是临时任务、用户在线等待，挂了就是任务失败，需要用户重新发起——当前方案是这个状态。如果是生产化方案，挂了一台机器，调度层检测到心跳丢失，会把这个 task 重新调度到另一台机器，新机器根据 task id 从远端加载 checkpoint 恢复执行。这里依赖的是"状态在远端、执行可迁移"的设计。

边界上，这套方案解决的是"任务中断后可恢复"，但还没有解决"状态强一致性跨机器共享"和"多机器并行执行同一个任务的不同节点"这类更复杂的问题。下一步如果要支持更大规模并发，还需要引入分布式锁、任务分片和状态版本控制。

## 17. 规划注入 prompt、目标漂移和短期记忆重复问题

### 答题要点

三个问题是同一个主线：如何在长程任务里让模型始终记得"我要干什么、干到哪了"。核心答案是：plan 和 todo 在工作区记忆里是结构化的、可更新的状态，不是简单拼对话历史；目标漂移用工作区定期注入来解决；重复问题用语义去重和状态替换来解决。

### 深入回答

**任务规划怎么注入 prompt**，不是简单的"把 plan JSON 拼到 system prompt 里"。我采用的是分层注入、按阶段变化。

在 Plan 阶段，会给强模型一个专门的 plan prompt。这个 prompt 里包含几个部分：（1）用户原始 query 和已提取的约束条件（时间范围、业务线、市场、必要输入）；（2）系统可用的工具清单，包括工具描述、参数 schema、返回格式和典型使用场景；（3）从长期记忆里召回的相关任务经验（主要是过去类似任务的成功步骤和失败模式）；（4）相关 SOP 文档的关键步骤摘要；（5）few-shot 规划样例，帮助模型理解 DAG 节点的输出格式；（6）明确的输出 schema 要求，包括每个节点的 role、instruction、input、output、dependency、expected evidence。

在 Execute 阶段，调度器把 plan 从工作区记忆里读出来，每次调用 subagent 时，不会把整个 plan 都塞进去。subagent 的 prompt 里只包含：（1）它负责的当前节点的 instruction 和 expected evidence；（2）该节点前置依赖节点产出的关键结果摘要；（3）它有权使用的工具。这样 subagent 的上下文是干净的，不会因为看到其他节点的目标而混淆。

同时，工作区记忆里维护的 plan DAG 状态（哪些节点完成、哪些失败、哪些等待）会定期以一段简洁的状态摘要形式注入到主 Agent 的上下文里，让主 Agent 在汇总和决策时知道全局进度。

**什么情况会出现目标漂移**，我遇到过四类典型情况。

第一类是上下文膨胀导致注意力衰减。随着工具调用的历史结果越积越多，模型在处理第 8 步时可能已经"忘记"第 1 步设定的原始目标。比如原本是要诊断"曝光下降"，执行到一半模型开始分析"为什么 CTR 也偏高"，偏离了原始问题。

第二类是执行器选错了 subagent 或工具。比如 planner 规划的节点是"检查预算消耗情况"，但执行时 subagent 发现预算数据表没有权限，它可能自作主张去查了另一个不相关的表，产出了偏离目标的结果。

第三类是 replan 时信息丢失。如果某个节点失败了需要 replan，但传给 planner 的失败上下文不完整，planner 可能生成一个和原始目标有偏差的新 plan。

第四类是记忆注入策略不当。如果工作区记忆更新不及时，或者把过期的 todo 重复注入，模型会以为某些已经完成的步骤还没做，进入死循环。

**如果每次调用都写到短期记忆最后不会重复多次吗**，这是个很好的工程问题。解决方式不是不写，而是"写了之后做语义去重和状态替换"。

首先，不是每次调用都把完整结果追加到短期记忆。我们的工作区记忆维护的是一个有状态的数据结构，而不是一个只追加的日志。todo 列表里的每一项有唯一 ID 和状态（pending/in_progress/completed/failed）。当一个节点执行完成后，不是新增一条"节点 X 完成了"，而是把对应 todo 项的 status 从 in_progress 更新为 completed，work_summary 字段写入该节点的结果摘要。

其次，发送到模型的上下文里，工作区记忆会先做一次"组装"——把当前所有 todo 项的状态、已完成节点的关键 summary、待执行节点的依赖关系，拼成一段紧凑的状态描述，而不是把历史 todo 列表的所有中间版本都塞进去。比如模型看到的是"当前进度：Step 1（确认异常）已完成，Step 2（检查预算）已完成，Step 3（检查出价）执行中"，而不是"Step 1 开始 -> Step 1 完成 -> Step 2 开始 -> Step 2 完成 -> Step 3 开始"的全量日志。

最后，短期记忆的对话历史部分也会做压缩。当上下文达到阈值时，会触发压缩：保留初始系统 prompt 和用户原始 query，保留最近 N 轮对话，中间部分用 LLM 做摘要后替换原文。摘要会提取关键决策点、已确认的事实和当前状态，而不是逐轮保留。

所以整个设计里，工作区记忆承担了"状态管理"的职责，短期记忆的对话历史承担了"连续性"的职责，两者配合，既不会让 todo 重复注入，也不会丢失任务进度。

## 18. todo list 的协调、串并行、结果对应和按计划执行

### 答题要点

todo list 不是独立的列表，而是 DAG 的有向无环图。协调靠拓扑排序 + 依赖调度，并行靠入度为 0 的节点并发执行，结果对应靠节点 ID 绑定，按计划执行靠结构校验 + 语义校验 + 执行时 checkpoint。

### 深入回答

**todo list 是怎么协调的——串行还是并行？**

我们的 todo list 本质是一个 DAG（有向无环图），不是线性列表。每个节点通过 dependency 字段声明它依赖哪些前置节点。执行器在调度时，先计算 DAG 的拓扑关系，找出所有入度为 0（即没有未完成的前置依赖）的节点，这些节点可以并发执行。

举个例子，诊断"曝光下降"的 DAG 可能有五个节点：A 确认异常是否真实、B 检查预算消耗、C 检查出价、D 检查定向、E 检查素材审核状态。A 没有前置依赖，先执行；B、C、D、E 都依赖 A 的结果（因为需要先确认异常的时间窗口和指标范围），但 BCDE 之间没有相互依赖，所以 A 完成后 BCDE 可以同时并发执行。

所以整体是"以 DAG 依赖为调度依据，无依赖的节点并行，有依赖的节点串行等前置完成"。

**怎么控制生成的工具调用结果一定对应到 todo list？**

有三层约束。第一层是节点 ID 绑定。每个 subagent 在执行时，调度器会给它分配当前节点的唯一 ID，它的工具调用和返回结果都挂在这个节点 ID 下。工具调用日志、结果摘要和文件引用都带有 node_id，不会混淆。

第二层是 expected evidence 校验。DAG 节点在规划时会声明 expected evidence，比如"预算消耗情况检查"节点的 expected evidence 是"预算总量、已消耗量、消耗比例、是否有预算撞顶"。subagent 完成执行后，会用一个小模型或规则检查返回结果是否覆盖了 expected evidence 里要求的字段。如果缺了关键 evidence，会标记为 incomplete，触发补查或重试。

第三层是工具调用边界隔离。subagent 只拿到它当前节点需要的工具，不会拿到其他节点的工具。比如"检查预算"的 subagent 只能调用预算相关的查询工具，不能调用出价或定向的工具。这样即使模型产生幻觉，也跳不出当前节点的工具范围，天然隔离了跨节点混淆。

**怎么保证 todo list 按计划执行？**

这里分事前校验、事中监控和事后治理三层。

事前校验有两层。第一层是结构校验：DAG 生成后先做 schema 检查——JSON 字段是否完整、dependency 引用是否形成环、是否有孤立节点、节点数量是否超出上限、是否有必填字段缺失。结构不通过就直接打回 replan，并告诉 planner 具体哪里不符合要求。第二层是语义校验：用一个 LLM judge 按 rubric 判断 DAG 是否合理——任务拆分粒度是否合适（不能一个节点包罗万象，也不能拆得太碎）、每个节点是否在系统能力范围内（不能要求工具做它做不到的事）、是否遗漏了关键检查步骤（比如诊断曝光下降却没检查预算）。语义校验不通过也会触发 replan。

事中监控靠执行器维护的 DAG 状态追踪。每个节点执行完后，执行器更新该节点的状态并重新计算可执行节点集合。如果某个节点超过最大重试次数仍然失败，会标记为 FAILED，并把所有依赖它的下游节点标记为 BLOCKED。然后触发局部 replan，将失败信息、已有 evidence 和当前进度返回给 planner 重新规划。关键设计是：已经成功的节点结果保留不变，replan 只针对失败节点和受影响的下游节点。

事后治理靠执行轨迹和 Golden Set 对标。每条任务的完整执行轨迹（包括 DAG 结构、每个节点的状态、工具调用、最终结果）会被记录下来。离线评测时，会比较实际执行的路径和黄金路径的差异——比如哪些节点被跳过了、哪些节点被重复执行了、哪些节点的 expected evidence 没被满足。这些差异反馈到 planner 的 few-shot 和 prompt 优化中，逐步提高规划的稳定性。

## 19. 怎么保证规划的准确性？

### 答题要点

规划准确性不能靠"模型更聪明"解决，要靠"约束 + 校验 + 反馈"三层体系。Planner 输出的是 DAG，那就必须让 DAG 是可验证的——结构可校验、语义可评估、执行可追踪、失败可归类。

### 深入回答

我把规划准确性拆成四个环节：生成前的约束、生成后的校验、执行中的验证、执行后的反馈。

**生成前的约束**是第一道防线。plan prompt 里不只是告诉模型"请帮我规划"，而是给了非常具体的约束：（1）必须使用的 checkpoints——对于每类任务，prompt 里预置了必须覆盖的检查节点，比如曝光下降必须包含"异常确认 → 预算 → 出价 → 定向 → 素材审核"这条主线；（2）工具的边界声明——每个工具能做什么、不能做什么、输入参数限制；（3）从长期记忆召回的相关任务经验——过去同类任务中有效的拆解路径和已知的失败模式；（4）few-shot 精标样例——不是通用样例，而是从广告运营的真实归因 case 中选的，覆盖不同路径复杂度。这些约束的目的是缩小模型的生成空间，让它在一个"对的路"附近生成，而不是在一个开放空间里随机探索。

**生成后的校验**是第二道防线，也是最重要的。校验分结构校验和语义校验。

结构校验是规则化的、确定性强的：检查 JSON schema 是否符合要求、dependency 引用是否存在、是否形成循环依赖、是否有孤立节点、节点粒度是否在合理范围（比如不允许一个节点包含"完成整个诊断"这种粒度）。这些校验是纯工程代码实现，不需要 LLM 参与，判断标准清晰无歧义。

语义校验需要用 LLM judge，但做了几件事降低不确定性。第一是 rubric 明确：判断维度包括——节点拆分是否合理（过粗/过细）、是否遗漏关键检查步骤、是否规划了系统能力范围外的操作、节点之间的依赖关系是否符合业务逻辑。每个维度有 1-5 分的评分标准和典型样例。第二是 few-shot 锚定：给 judge 提供正确 DAG 和错误 DAG 的标注样例，帮助 judge 做对比判断。第三是投票机制：对关键任务的 DAG，可以让同一个 judge 跑多次或让不同 judge 交叉判断，取多数结论。第四是失败回写：语义校验不通过时，不直接丢弃，而是把不通过的具体原因（比如"缺少定向检查节点"）回传给 planner，让它在已有 DAG 的基础上做定向修正，而不是从零重新规划。

**执行中的验证**是第三道防线。每个节点执行完成后，不只看"执行是否成功"，还看"产出是否满足 expected evidence"。测试方法是把节点返回的 summary 和该节点的 expected evidence 做对比，检查关键 evidence 字段是否被覆盖。如果覆盖不全，标记为 incomplete，触发补查或重试。如果某个节点的执行结果和预期严重不符，还会触发局部 replan。

**执行后的反馈**是持续提高规划准确性的关键。每条任务结束后，执行轨迹会被记录到 bad case 分析系统。如果任务最终失败或被用户不采纳，会把这条轨迹做归因：是 planner 的 DAG 就缺了关键步骤，还是某个节点的执行出了问题，还是最终汇总时推理错误，还是工具本身返回了错误数据。如果是 planner 的问题，就把这个 case 加工成评测样本，加入 Golden Set。下次优化 planner 时，这个样本就会被回放验证。同时，这类规划失败的模式（比如"某种任务经常漏掉出价检查节点"）也会标注到长期记忆里，下次同类任务时作为"需要避免的失败模式"传递给 planner。

所以总结一句：规划准确性不是一次 prompt 工程解决的问题，而是通过"约束输入空间 → 结构化校验 → 执行时证据验证 → 失败归因回流"构成的持续优化闭环来保证的。

边界上，这套方案对"业务路径结构化程度高"的场景效果好（比如广告诊断有明确的排查 checklist）；对"高度开放、没有成熟分析范式的探索性任务"，planner 的准确性仍然依赖模型本身的推理能力，校验也更难做，因为缺乏明确的 golden path 做参照。

## 20. 追问：轻量摘要具体怎么做的？怎么保证信息准确性？

### 答题要点

"轻量摘要"这个说法容易让人误以为是让模型对结果做文本摘要，但实际上对工具返回的结构化/半结构化数据，摘要不应该依赖模型生成，而应该走**程序化结构化抽取**。只有对完全非结构化的文本才需要模型介入，且介入方式也是抽取式（extractive）而非生成式（abstractive）。准确性是从"不做模型推理"里面保证的。

### 深入回答

先纠正一个容易产生的误解：我前面说的"轻量摘要"不是"让一个小 LLM 把 SQL 结果写成一段文字总结"。LLM 做摘要一定会引入幻觉风险和延迟，在生产链路里不应该作为工具结果外置的第一步。

我们实际的"轻量摘要"是按数据类型走不同路径的**程序化结构化抽取**：

**第一类：SQL 查询结果（结构化数据）——纯代码抽取，零模型参与**

SQL 返回的是行列结构，这是最容易做无损抽取的数据类型。具体做法是直接用代码（Python/pandas）做：

- 元数据抽取：列名列表、行数、列的数据类型
- 基础统计：数值列的 min/max/mean/median/null_count，分类列的 distinct_count、top_k 值和占比
- 异常标记：null 比例超过阈值的列、数值突变超过阈值的列、结果为空或结果行数异常的标记
- 业务维度标注：如果能识别出时间列，标注时间范围；如果能识别出业务列（如 campaign_id、region），标注涉及的业务实体列表

举个例子，一个 SQL 查了某广告组过去 7 天的曝光和点击数据，返回 50 行。轻量摘要的输出是：

```json
{
  "type": "sql_result",
  "row_count": 50,
  "columns": ["date", "campaign_id", "impressions", "clicks", "cost", "ctr"],
  "null_counts": {"impressions": 0, "clicks": 0, "cost": 0, "ctr": 0},
  "date_range": "2024-01-10 ~ 2024-01-16",
  "anomalies": [
    {"column": "impressions", "signal": "从 01-14 开始连续下降，累计降幅 42%", "pct_change": -0.42}
  ],
  "aggregates": {
    "impressions": {"total": 234500, "avg_per_day": 33500},
    "clicks": {"total": 3450, "avg_per_day": 493},
    "cost": {"total": 12340.5, "avg_per_day": 1763}
  }
}
```

**这个摘要是 100% 准确的**，因为它不是模型"理解"后生成的——它是代码对原始数据做统计计算的结果，不存在幻觉。唯一可能出错的是异常判定阈值设置不合理（比如 5% 的波动被误标为异常），这是阈值调优问题，不是准确性问题。

**第二类：日志/API 返回（半结构化数据）——规则 + 模式匹配**

对日志类、API 返回的 JSON、错误堆栈这类半结构化数据，用正则和路径表达式做抽取。比如：

- 错误码：按已知的错误码正则提取（如 `ERROR_CODE: (\w+)`）
- 时间戳：按 ISO 8601 或已知格式提取起止时间
- 关键字段：按 JSONPath 或字段路径提取业务相关字段
- 异常信号：匹配已知的错误模式（如 timeout、connection refused、permission denied）

这个层级的抽取也是确定性的——正则匹配到了就是匹配到了，不存在"模型可能看错"的问题。

**第三类：RAG 检索到的文档片段（非结构化文本）——抽取式，非生成式**

这是唯一需要模型介入的场景，但有三个约束：

- 只做抽取（extractive），不做生成（abstractive）。模型从 chunk 中抽取关键实体、指标数值、条件约束的原文片段，而不是用自己的话重写
- 抽取结果后做原文回溯校验。比如模型抽出了"预算必须在 campaign 级别设置"，就去原文里做字符串匹配确认这句话确实存在
- 如果原文匹配不上，标记为"抽取不置信"，宁可少摘要也不产生幻觉

**准确性保证的总结**：结构化数据用代码统计（100% 准确），半结构化数据用规则匹配（100% 准确），非结构化数据用抽取式模型 + 原文回溯校验（高置信）。只有在对数据做了完整理解性摘要时才存在准确性问题，而我们的轻量摘要刻意避开了这种场景。

## 21. 追问：采样不会影响效果吗？还有别的快速摘要技术吗？

### 答题要点

采样确实可能遗漏信息，所以采样只用于"第一轮上下文注入让模型知道大致情况"，完整数据始终保留在文件里，模型可以在后续轮次按需读取。同时，除了采样，还有几种更好的摘要技术适用于不同数据类型。

### 深入回答

**采样会不会影响效果？**

会的，所以采样不是"一采了之"，而是设计了几层保护：

第一，采样只用于注入到当前轮次上下文的那一段摘要，完整原始数据始终保留在文件系统里。模型如果判断现有摘要信息不足以做决策，可以调用 read_file 工具去读完整结果。所以采样影响的是"第一眼看到的信息是否足够判断下一步"，而不是"最终分析是否基于完整数据"。

第二，采样策略不是简单截取前 N 行，而是按数据类型做**智能采样**：

- SQL 结果：头尾采样（前 10 行 + 后 10 行），因为很多异常出现在数据尾部（比如最新的时间窗口），只看前几行容易遗漏趋势变化
- 时间序列数据：按时间分桶采样，每个时间桶取代表行，确保时间维度的覆盖
- 分类数据：按分类列分层采样，确保每个 category 至少有一行代表
- 日志数据：优先采样包含 ERROR/WARN 级别的行，降级采样 INFO 行

第三，采样结果会标注"覆盖率信息"。比如"以下为从 342 行中采样的 20 行（覆盖全部 4 列和 3 个时间桶），完整结果可通过文件引用读取"。让模型明确知道它看到的是子集。

**还有别的快速摘要技术吗？**

有几种比采样更优的技术，适用于不同场景：

**1. 列级聚合（Column-level Aggregation）**

适用于 SQL 结果。不采样任何行，而是对每一列计算统计摘要（distinct count、null ratio、min/max/mean、分布形态）。模型拿到的是"这个结果里有什么"的完整画像，但没有任何一行具体数据。需要看具体行时，再通过文件引用或工具调用去读。这是信息密度最高、损失最小的一种摘要方式——相当于给模型看 `df.describe()` 而不是 `df.head()`。

**2. Schema + 样例（Schema + Exemplars）**

适用于大规模重复结构化数据。摘要里只放：列名和类型、总行数、每列的 distinct 值数量和 top 值、以及 3-5 条代表性样例行。模型通过 schema 和样例理解数据结构和内容特征，通过统计数字感知规模。对于"这个结果里有没有包含某类数据"的判断来说，这比采样更有效。

**3. 索引目录（Data Index）**

适用于超大规模结果（几万行以上）。不传送数据也不传样例，而是生成一个数据索引——相当于给结果建一个"目录"。比如 SQL 结果按日期分组，索引就是"2024-01-10: 50 行 / 2024-01-11: 48 行 / ..."。模型先看目录，确定自己需要哪个子集，然后通过工具调用精确读取那个子集。

**4. 渐进式展开（Progressive Disclosure）**

最灵活但也最复杂的一种。第一轮只给最基础的元数据（行数、列数、是否有空结果）。模型根据自己的推理需要，通过工具调用逐层获取更多信息——先要列统计，再要特定行的数据，再要特定列和时间段的交叉分析。这相当于把"读数据"本身也变成了 Agent 的一个推理循环。

**实际选择上**，我们当前对不同场景采用不同策略：

| 数据场景 | 推荐技术 | 原因 |
|---|---|---|
| SQL 单表查询 (< 1000行) | 列级聚合 + 头尾采样 | 体积可控，兼顾统计和样例 |
| SQL 单表查询 (> 1000行) | Schema + 索引目录 | 体积大，模型不需要看全部 |
| 多表 join / 复杂分析 | 渐进式展开 | 模型需要按维度逐步探索 |
| 日志/堆栈 | 错误优先采样 + 错误码聚合 | 错误比正常日志重要 |
| RAG 检索结果 | 全量保留前 K 条+相关性分+来源标注 | 体积通常不大，全文更重要 |

## 22. 追问：单 Agent 里的 todo list 怎么保证执行顺序？（不用 DAG 的情况）

### 答题要点

要区分两个层面：主 Agent 跨 subagent 的调度用 DAG（有向无环图），但单个 subagent 内部执行自己的子任务时，用的是更简单的线性 todo list，不走 DAG。在没有 DAG 拓扑调度的情况下，保证顺序靠的是：**prompt 注入的状态标记 + 系统层的顺序闸门 + 工具可见性控制**。

### 深入回答

先澄清一个容易混淆的点。在我前面的回答 §18 里，讲的是主 Agent 对整个复杂任务做 DAG 规划，执行器按拓扑调度 subagent——这是跨 subagent 层面的调度。但在我们的项目里，subagent 被分配了一个节点任务后，它自己内部可能也需要拆成更细的步骤（比如"检查预算消耗"这个 subagent 可能要：查预算总量 → 查已消耗量 → 计算消耗比例 → 判断是否撞顶），这时候 subagent 内部没有一个 mini-DAG，而是一个更简单的线性 todo list。

那么**在单 agent（subagent）内部，不用 DAG，怎么保证执行顺序？**

**机制一：状态标记注入 prompt**

每个 todo 项有状态字段：`pending / active / completed / failed`。每次调用 subagent 时，它的 system prompt 或上下文里会注入一段这样的内容：

```
当前任务：检查预算消耗情况

Todo 进度：
[X] 1. 查询广告组当日预算总量 —— 已完成
[X] 2. 查询当日已消耗预算 —— 已完成
[>] 3. 计算消耗比例，判断是否撞顶 —— 执行中
[ ] 4. 汇总检查结果，输出 evidence —— 等待中

规则：
- 只处理标记为 [>] 的当前项
- 当前项完成后，在你的回复中明确声明 "TODO_ITEM_3_COMPLETED"
- 不要跳到后续项目
```

模型看到的是有明确"当前光标"的列表。它被显式告知"你只处理打了 `[>]` 标记的那一项"。这是靠 prompt 约束来控制注意力的。

**机制二：系统层顺序闸门**

不能只靠 prompt，因为模型可能不遵守。系统层会做两层闸门：

1. **输出解析与状态推进**：subagent 返回结果后，系统解析输出，检查是否包含完成声明（如 `TODO_ITEM_3_COMPLETED`）。如果包含，系统把 todo 列表里第 3 项的状态从 active 更新为 completed，第 4 项从 pending 更新为 active，然后发起下一次调用。如果模型返回了结果但没有完成声明，或者声明要跳到当前项之外，系统会拒绝状态变更，并在下一次调用的 prompt 中提醒模型回到当前项。

2. **工具可见性控制**：每个 todo 项只暴露它需要的工具。比如第 1 项"查预算总量"暴露的是 budget_query 工具，第 2 项"查已消耗量"暴露的是 consumption_query 工具。如果模型跳过第 1 项直接尝试调用第 2 项的工具，工具调用会因为不在白名单里而失败。这从能力层面阻止了跳步。

**机制三：完成校验 + 闸门放行**

每个 todo 项有 expected output 定义。比如"查询广告组当日预算总量"的 expected output 是 `{budget_total: number, currency: string, budget_type: string}`。系统在推进状态前会校验：模型返回的结果是否包含这些字段？如果不包含，标记为 incomplete，不推进到下一步，让模型补充。

**那为什么 subagent 内部不用 DAG？**

因为 subagent 的任务粒度已经比较细了（单个诊断检查步骤），它的内部步骤通常是线性的、依赖关系是天然串行的——必须先查到预算总量才知道消耗比例，必须先查完所有维度才能汇总。在这种情况下引入 DAG 的拓扑调度是过度设计，一个有序的 todo list + 顺序闸门就足够了。

DAG 解决的是"多个相对独立的大步骤之间哪些能并行、哪些必须等待"的问题，适合主 Agent 层面的跨节点调度；todo list 解决的是"单个步骤内部的几件小事按什么顺序做"的问题，适合 subagent 内部的执行控制。

**边界上**，如果 subagent 的任务变得足够复杂（比如一个 subagent 内部需要同时查 3 张表、做交叉验证、中间步骤有分支逻辑），那它内部也值得升级为 mini-DAG。判断标准是：内部步骤之间有非线性的依赖关系吗？有的话就该用 DAG；全是线性串行的话，todo list + 闸门就够了。
