# 美团三面｜问答整理

## 开场

> 面试官补充：开头确认声音后直接进入面试。

## Q1. 自我介绍

**问题：** 先做个简单介绍吧。

**回答：** 我叫陈鸿门，现在在 Shopee 做广告系统架构以及 AI Agent 架构后端开发。

在 Shopee 主要有两段项目经验。第一段是作为核心开发者，从 0 到 1 参与广告系统全链路平台搭建以及持续演进。这段经历让我对在线架构以及广告机制策略算法有比较深入的实践和理解。

第二段是作为主导者落地商家广告运营智能助手 Agent 项目，解决广告运营在知识获取、数据查询、归因诊断这些复杂决策优化环节的效率低下问题。我们通过混合多级 Agent 架构分发不同任务，同时通过四级记忆机制管理长程任务上下文膨胀。

上一段工作经验是在百度做机器学习平台相关内容，包括模型训练框架优化、模型分析体系搭建，以及模型调研端到端一站式平台。整体来说，我聚焦在线 AI 架构，具备算法和工程两个视角，对在线侧和模型侧都有比较深入的实践。

## Q2. Agent 项目背景、目标和问题

**问题：** 刚才提到 AI Agent 架构，展开讲讲背景、目标，做的过程中碰到哪些问题，怎么解决的。

**回答：** 背景是广告系统从 0 到 1 过程中越来越复杂，数据越来越多。广告运营日常工作中有几类效率低下的问题，耗费很多人工精力，所以希望借助大模型能力解决这些常问又耗时的问题。

我们和 local 运营沟通，收集他们从广告创建、效果 follow、问题诊断到优化几个环节里的效率痛点。然后按照可落地性、收益大小和影响范围，第一期抽取了知识获取、数据查询、归因诊断和智能优化三个环节。

整体架构上，通过意图理解模块把三个环节拆成三个 Agent 能力来做路由。单 Agent 没法很好处理所有场景，因为每个场景适合的 workflow 不一样。

text-to-SQL 是比较线性的过程，我们拆成 query 理解和改写、表召回、列召回、列探索、SQL 生成等多阶段 workflow，用职责划分换取 SQL 准确性。

RAG 最开始也是传统 workflow，分块、召回、排序、结果生成。但后来发现上下文碎片化问题，比如用户问搜索广告和推荐广告在冷启动效果上的差异，单次查询可能只搜到搜索文案，没有覆盖推荐，导致生成幻觉。所以后来升级成 Agentic RAG。

归因诊断最开始用单 Agent 做，但它是长程、多目标场景。要做异常诊断、判断可能原因、指标拆解、多维异常诊断。单 Agent 会把中间信息和目标混在同一个上下文窗口，导致效果下降、注意力丢失和目标漂移。后来引入 plan and execute，做任务拆解，主 Agent 和子 Agent 通过任务委派、summary 返回来做信息交互，解决上下文耦合和干扰。

## Q3. 怎么评估效果

**问题：** 怎么评估效果？效果是不是符合预期？除了大的架构优化，还做过哪些地方优化效果？

**回答：** 不同场景不一样，也分端到端和分阶段评估。

RAG 端到端评估会有量化指标和 LLM-as-judge。量化指标是回答结果和 ground truth 的相关性分数，以及关键词、关键实体抽取后的 F1、recall、NDCG 等。LLM-as-judge 会通过 rubric 评估结果是否忠实、是否有 evidence 支撑、推理逻辑是否合理、是否有幻觉。

中间阶段会评估 chunk 召回、chunk 精准度、排序 NDCG 等。

text-to-SQL 有黄金测试集，主要看 exact match 和 execution match，也就是 SQL 是否一致、执行结果是否一致。

归因诊断和 RAG 类似，有主因、辅因、逻辑推理描述、证据结构化输出。通过结构化输出计算归因的 F1、recall，也通过 LLM-as-judge 评判推理合理性。

在线上会做 AB 实验，统计端到端用户采纳率，以及用户平均几轮结束等用户体验指标。

## Q4. Plan 阶段如何优化准确率

**问题：** 找一个系统讲，比如归因系统刚上线时准确率怎么样，哪些问题解决不了，除了多 Agent 上下文拆分，还做过哪些优化？

**回答：** 引入 plan and execute 之后，很重要的是保证系统准确性，尤其 plan 阶段。最开始没有约束也没有优化，plan 阶段生成准确率大概只有 50%，系统不可用。

我们做了几个优化。第一个是后校验模块，包括结构化校验和语义校验。结构化校验包括 schema 是否符合生成规范、依赖关系是否符合、是否有环、固定节点校验等。基于结构化错误信息再 replan，可以针对性改正。

第二个是在 prompt 里引入 few-shot，包括正例和负例，让模型看到不同情况，提升结构生成准确性。最后结构化输出准确性做到 99% 左右。

语义准确性上，希望它符合系统能力，也希望效率尽量高。我们通过 LLM-as-judge 判断节点能力目标是否在系统能力范围内、是否存在重复节点、链路是否过长等，低于阈值就重新生成。

## Q5. 规划失败的具体例子

**问题：** 能举一个真实例子吗？比如规划不准或工具执行不了的情况。

**回答：** 比如排查 CPA 异常上升。预期应该先做指标拆解，把 CPA 拆成 CPC 和 CVR，再分别做 CPC 和 CVR 维度的异常诊断。

但实际规划里，它可能丢失最重要的指标拆解节点，直接去排查素材维度异常、操作日志异常、转换订单异常。最后发现某个素材 CPC 上升，就直接得出 CPA 上升是因为大盘 CPC 上升，但真实维度没有排查到。

还有 ROS 下降的例子。它应该拆成 GMV 和 Cost，再做 GMV 排查。但中间某个维度排查失败了，模型没有把失败信息记录在 evidence 里，反而拿一些不重要的异常做最后判断。

后来我们做了优化：失败会有有限次重试；如果真的失败，会做失败传播，一方面传播到下一个节点，另一方面把失败结果返回给主 plan agent，让它知道这个节点已经失败，不会编造事实做归因。

## Q6. 系统面向运营还是商家

**问题：** 你们这个系统是面向运营还是面向商家的？当初怎么考虑定位？

**回答：** 现在面向运营。运营日常 follow 广告组，做广告创建、设计、广告主入驻、盯盘、归因诊断和数据分析优化。他们经常需要找产研排查问题，而且 local 和 regional 异地分工，效率比较低。

所以我们先从运营工作 pipeline 里做 Agent 试点，希望通过 Agent 能力推广到业务场景。选了比较符合当前情况、落地性较好的场景来做。

## Q7. 实际使用效果

**问题：** 实际使用结果怎么样？多少任务还要找研发排查，多少任务 Agent 可以搞定？

**回答：** 归因诊断这部分，大概 70% 的任务已经能在运营和 Agent 之间直接解决。

还剩一些长尾问题，比如多因素组成、主因和辅因难以区分的 case；第二类是当前系统能力没有覆盖的数据背景知识，比如外部情况导致商家投放大盘变化，但我们没有接入这些数据源。

现在 DAU 大概 500。归因诊断采纳率大概 70%。text-to-SQL 会低一点，因为复杂查询准度还没解决特别好，单表查询做到 80% 左右。RAG 准度会比较好。

## Q8. 没有 Agent 之前问题怎么处理

**问题：** 过去没有 Agent 的时候，这些问题都要找研发人肉排查吗？

**回答：** 包括两个部分。运营自己可以看一些数据、做一些分析。如果缺数据，又要找数据团队提需求，让数据团队拉数据出来。整体就是运营、数据、产研互相排查。

## Q9. 运营反馈的最大痛点

**问题：** 从运营实际反馈看，现在比较大的痛点是什么？

**回答：** 比较大的痛点是整个工作流程还没有全自动化。现在是他们看到问题，再利用 Agent 诊断，诊断完还要 check，因为准确率没做到那么高，还要看一下事情是不是真的是这样。

所以流程还是割裂的，只是单点提升。期望是有在线监控，监控之后自动触发诊断，再引入 review 机制，计算可靠性或置信度，再让人工 review。人工只需要看结论和数据是否符合正常逻辑推理，然后确认。

## Q10. 项目发起和投入

**问题：** 项目是谁发起的？投入大概多少人？

## Q11. 团队分工和项目性质

**问题：** 你们是广告引擎团队吗？这个项目是专门团队还是项目制？

**回答：** 我们是广告引擎，有广告散发，我本身做广告引擎。这个项目是拉取一些人过来做，有商家端的人，也有广告引擎的人，一起来做运营团队工具建设。可以理解为偏项目制。

## Q12. 相比其他团队做得好的地方

**问题：** 公司内也有很多 AI workflow 项目，你们在哪些认知或实践上做得比较好？

**回答：** 我觉得我们这个场景天然是任务类型，需要考虑任务稳定性和准确度。我们在长程任务这一块做了一些深入工作。

包括规划准确性、长程任务准确性、失败处理机制、有限次重试、失败传播、重规划、任务持久化。我们吸收了开源经验，像 Claude Code 的 ReAct、工具治理、持久化、上下文管理和 harness 工程，再结合自己的场景开发。

其他团队可能更聚焦 workflow 串联和搭建，场景更确定性，只要每个步骤能做成就可以。归因诊断有更多不确定性挑战。

## Q13. AI Coding 实践

**问题：** 你们日常开发会用 AI Coding 吗？讲讲实践经验。

**回答：** 会用，而且基本上大部分都用了。公司最开始给 Cursor，现在转到 Codex。之前一直是 IDE 编程模式，还没有做到 Coding Agent，更多是人作为中间环节串联信息，在 IDE 里完成编码。

实践上，我们会有 PRD，再加代码 context、project overview、数据流 overview、业务背景 overview。服务级别有这三层 context。更上一层是当前服务和其他服务的架构关系、调用关系。再往上是产品线整体 overview。

基于这些上下文，先生成 Tech Design。我们有 Tech Design 约束和 guideline，让它按准则做设计。拿到 Tech Design 后，再基于上下文和编码约束生成代码。

实际使用中，Tech Design 过程可能还是有幻觉和上下文缺失，需要人为补充信息，让它针对性修改。循环下来，Tech Design 底稿能达到可用程度。

## Q14. AI Coding 的上下文维护痛点

**问题：** 这个流程有什么痛点？

**回答：** 编码之后代码会变更，上下文也要随之变更。现在上下文都是 markdown 格式，这部分还没解决。我觉得需要维护统一知识库，做版本管理和内容更新，像管理代码一样管理知识库内容，做到动态更新和实时获取。

后续链路里，diff、单元测试、deploy、CICD 这些环节也在做 skills 和 spec 开发，但整体链路还没打通。

## Q16. AI Coding 上下文建设有哪些坑

**问题：** 做知识库或 workflow，有没有碰到哪些坑？哪种方法一定不对？

**回答：** 第一个，不分层肯定不对。上下文不分层的话，整个脉络完全耦合在一起，效果会打折扣。

第二个，上下文一定要全。如果不全，生成质量就不可用。模型不知道你要什么、不知道你有什么，只能通过幻觉告诉你它能做到什么。

第三个，需要引入检索机制。如果全量上下文都加载进去，会有注意力缺失问题，也会影响效果。

## Q18. 是否应该主动投入 AI Coding 基建

**问题：** 广告工程架构复杂，上下游链路也多。你怎么看是主动投入搞 AI Coding 上下文，还是等别人搞出来再 copy？

**回答：** 我觉得应该尽可能多投入到这个模式的构建。

第一，构建过程中会加深对大模型边界的理解，以及对上下文构建的认知。模型能力本质上需要我们管理上下文，给它最佳信息密度的上下文，才能更大提升模型能力。

第二，在 pipeline 搭建过程中会遇到很多 harness 工程问题，需要管理 Agent workflow 的不稳定性和准确性。沉淀出对模型、workflow 和业务知识的认知之后，可以迁移到各个业务领域，更快适应大模型技术发展。

## Q20. 和 Manager 意见不一致的案例

**问题：** 能举一两个你和 manager 在架构设计或方案判断上存在差异，怎么配合协作的 case 吗？

**回答：** 印象比较深的是 RAG 升级到 Agentic 的那次。

最开始我们是单次检索，发现上下文缺失、多跳任务等问题后，也尝试了一些单次检索解法。后来我想升级到 Agentic RAG，但它会带来长链路耗时和准确性问题。

我和 manager 同步时，把优劣势分析好，包括单次检索不可避免的问题，Agentic RAG 更符合人类获取信息的模式，以及耗时评估和模型选型。manager 判断 Agentic 成本可能过大，更倾向 simple RAG。

我的判断是 Agentic 是最终形态，所以提出路由模式：简单问题走 Simple RAG，复杂问题走 Agentic RAG。这样能力覆盖到，基础准确度和成本也不丢。通过这种方式最后说服他做这个事情。
