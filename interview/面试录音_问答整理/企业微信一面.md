# 企业微信一面｜问答整理

## 开场

> 整理备注：源文件开头直接从候选人回答 Agent 记忆机制开始，缺少完整开场和前置问题，边界可能需要回听确认。

## Q1. 短期、工作区、文件系统和长期记忆分别做什么

**问题：** 你们 Agent 里的短期记忆、工作区记忆、文件系统记忆、长期记忆这些分别是怎么设计的？

**回答：** 开发的话我们现在主要语言还是 Python，因为整个 Python 生态会比较好一点。

工作区记忆这块有两个比较创新、比较跟前沿的点。因为我们这个场景是任务类型的，任务类型要解决两个问题：一个是怎么做上下文管理，第二个是怎么保证整个执行的稳定性，以及整个过程结构的管理和存储。

我们这里引入了工作区记忆和文件系统记忆。工作区记忆解决长程任务执行时上下文越来越膨胀、目标失焦的问题。我们通过工作区记忆把规划和代办事项做存储和管理，持续注入到短期上下文里，让它在任务执行过程中不丢失主要目标。

文件系统记忆主要解决上下文膨胀问题。工具调用结果内容需要外置存储，同时做压缩，在短期上下文里只保留摘要和文件引用，解决工具调用以及多步执行之后上下文膨胀的问题。

## Q2. 文件系统记忆存在哪里，什么时候写入

**问题：** 文件系统记忆是存在哪里，什么时候做？

**回答：** 每一次工具调用的时候，我们都会做一次文件的外置，把工具结果外置。主要存在机器的一个目录里面。

这块现在没有做持久化的平台类型的东西，所以它还是一个临时任务型的概念。

## Q3. 这种任务是不是分布式，机器挂了怎么办

**问题：** 这个其实算分布式吗？如果机器挂了，记忆是不是就全部丢失了？怎么保证同一个用户走到同一个机器，或者恢复他的记忆？

**回答：** 这个其实也应该算是分布式的吧。整体是一个进程的概念，你只要创建一个任务，它就给你新建一个 Agent，然后做独立任务。

如果机器挂了，那台机器可能暂时就恢复不了了。这个任务的执行进度文件还是保存在我们的任务里面，但是存在机器磁盘上。机器都挂了的话，这部分数据可能就丢失了。

如果要解决用户和记忆匹配的问题，可以做一层远端存储机制，把内容通过用户 ID 存到远端。每次需要做任务恢复时，通过用户 ID 做数据查询。相当于可以有一张 task 的 DB 表，把所有任务信息和记忆目录存起来。下一次 resume 时，通过 task ID 进行任务加载，相当于中间状态 reload 的机制，让它续跑。

## Q4. 广告系统主要做了什么

**问题：** 你给我讲一下广告系统主要的工作。

**回答：** 好的。广告系统这块，我是从项目创立期最开始进入项目组，参与了从 0 到 1 的搭建以及持续演进。

整体包括几个部分：第一个是数据流搭建，第二个是引擎 pipeline 搭建，第三个是广告机制策略算法的迭代和优化。

## Q5. 广告系统的数据流怎么搭建

**问题：** 广告系统的数据流这块是怎么做的？

**回答：** 数据流搭建包括倒排索引和正排索引两部分。

正排主要是同步广告库表，通过 GDS 和 CDC 的数据传播，把数据同步到 CC 集群，通过 CC 作为正排数据的存储方式。

倒排主要通过 ES 存储，通过 Flink 任务把 DB 和其他所有数据做 join，最后落到宽表，再从宽表同步到 ES 文档。

## Q6. 在线引擎 pipeline 怎么设计

**问题：** 在线引擎 pipeline 是怎么搭建的？

**回答：** 在线这块基于 process 预定义接口，不同模块的算子继承 process 接口，实现 data in、data out 的统一编排模式，做成流水线形式的算法 pipeline。这样可以快速接入场景，也比较方便维护。

整体广告引擎和传统搜索广告 pipeline 一致，从召回、出牌、过滤、排序、精排，再到混排。

## Q7. 广告系统里有哪些广告独有机制

**问题：** 广告这块和普通推荐、搜索相比，有哪些广告独有机制策略？

**回答：** 广告这块会有一些广告独有的机制策略，包括预算平滑、CTR/CVR 校准，还有流控和平控机制。

预算平滑是为了保证广告主每天的投放尽可能触达更多优质流量。他不希望某一天 10 点以前预算就消耗完，所以需要把预算平滑地花在每天不同流量时间带上，根据预算消耗情况拟合每天的流量波动。

CTR/CVR 校准是因为广告不只关心 item 的序关系，还关心 CTR 预估准不准。广告计费会通过 CTR、CVR 做实时计算。如果预估 CTR 偏高，透出去了但没有点击，平台收了钱但广告主没有得到相应点击转化，ROI 就下降了；偏高或偏低分别会损害广告主和平台利益。所以需要通过校准机制，让 CTR、CVR 的预估值更贴近后验统计值。

## Q8. 流控和平控怎么做

**问题：** 你们怎么稳定大盘的 AD load？

**回答：** 我们会用 PID 控制策略，根据实时 AD load 和目标 target AD load 做误差计算。

通过每个时间窗口的误差，在每个调节时刻计算微分误差、积分误差和当前窗口误差。通过这三个维度的误差做 PID 稳态调控。PID 可以调节广告系统里任意影响因子的稳态。

现在接入的包括 AD load 稳态、target ROAS 稳态，还有 ECPC/CPC 出价稳态。

## Q9. 广告系统工程优化有哪些

其他还包括整体稳定性、监控、告警这方面的建设和机制。

主要做了全链路监控搭建，多阶段异步削峰机制建设，同时通过预写日志的方式做系统故障可恢复机制。我们会保存每条日志处理到的某个阶段，可以从任意阶段重新消费，做到系统容错和稳态建设。
