# 面试问题聚类总结

> 基于 `面试录音_问答整理/` 下 20 份问答整理文件梳理。统计时将 `得物三面.md` 与 `得物三面 (30-May-2026_10-29-57).md` 视为同一轮；同一文件中重复的“原始整理/优化整理”不重复计数。口径为“独立面试轮次中是否被追问”，共约 19 轮独立面试。

## 一、总体结论

当前面试问题高度集中在一条主线：**你能否把 Shopee 广告业务中的 Agent 项目讲成一个真实落地、可评估、可演进、可迁移的工程系统**。

最高频问题不是单点技术八股，而是以下组合反复出现：

1. 你是谁、做过什么、为什么现在找机会；
2. 为什么这个业务场景适合 Agent；
3. 为什么要用多 Agent、Plan/Execute、记忆、RAG、Text-to-SQL；
4. 系统效果怎么评估，70%/80% 的准确率和采纳率是否足够；
5. 项目是否真的落地，业务 ROI 如何证明；
6. 与新范式如 Claude Code、Skills、MCP、AI Coding 的关系；
7. 基础工程能力是否扎实，尤其是高可用、分布式、性能排查和算法题。

你的优势很明确：项目主线完整、Agent 工程概念覆盖面广、能把业务痛点和架构模块串起来。主要风险也很集中：表达上“然后/这个/这样一个”过多，答案容易铺概念；部分关键指标和系统边界不够稳定；在被追问“为什么这样做、怎么证明有效、失败怎么办”时，常常从架构描述退回到经验判断。

## 三、高频问题答题思路、评审与最佳表述

### 1. 自我介绍 / 项目背景

**你的当前思路**

以 Shopee 两段项目为主：广告系统 0 到 1 + 商家运营 Agent，再补百度机器学习平台经历。强调在线 AI 架构、算法和工程双视角。

**口语和答案评审**

优点是主线稳定，能让面试官快速进入 Agent 项目。问题是信息密度不均：前 30 秒会出现大量“负责架构”“参与搭建”“持续演进”等抽象词，但缺少一句可记住的结果。口语上“然后”“这样一个”“整体来说”过多，会削弱 senior 感。

**最佳答题思路**

用 90 秒讲清：角色定位、两个项目、关键指标、你要被面试官记住的标签。

**建议表述**

> 面试官您好，我叫陈宏，目前在 Shopee 做广告系统和 Agent 架构相关工作。我的经历可以概括成两条主线：第一条是广告系统工程，我作为核心开发参与了垂类广告系统从 0 到 1 的搭建，包括在线引擎、数据流、计费链路以及预算平滑、校准、排序等广告机制策略，目标是把系统稳定性和广告投放效果做起来。第二条是商家运营智能助手，我主导了一个面向广告运营的 Agent 系统，解决知识查询、数据查询和复杂归因诊断三个场景，系统里做了意图路由、多 Agent 调度、四层记忆、Agentic RAG 和 Text-to-SQL。这个项目让我比较系统地沉淀了 Agent 从 demo 到真实业务落地所需要的工程能力，包括可控性、评测、上下文管理和失败处理。更早之前我在百度做机器学习平台和模型调研平台，所以整体上我比较擅长在线 AI 系统里算法、工程和业务之间的结合。

### 2. 求职动机 / 职业规划

**你的当前思路**

强调想更聚焦 Agent，希望加入资源更多、方向更主线的团队；部分轮次提到地域和家庭因素。

**口语和答案评审**

方向是对的，但容易显得“只要是 Agent 就行”。金融、券商、游戏、企业协作等行业的回答需要体现你对场景的理解，否则动机会像泛泛投递。不要把“容易被新挑战吸引”当核心缺点，会让面试官担心稳定性。

**最佳答题思路**

动机分三层：技术判断、过往积累、目标岗位匹配。地域/家庭因素放在补充，不放在主叙事。

**建议表述**

> 我现在看机会的核心原因是，希望把过去一年多在业务 Agent 落地里的经验继续往更深处做。我的判断是，Agent 接下来真正有价值的地方不是简单问答，而是能在复杂业务系统里完成可验证、可追踪、可迭代的工作流。我之前做的广告运营助手已经覆盖了知识、数据和归因诊断，但还受限于团队资源和业务边界，所以我希望加入一个把 Agent 作为主线能力建设的团队。对我来说，下一阶段目标是成为 Agent 工程方向的技术专家，能把一个复杂业务场景拆成任务建模、工具体系、记忆系统、评测闭环和线上治理，并真正交付可用的生产系统。

### 3. 多 Agent 架构与选型

**你的当前思路**

单 Agent 容易上下文膨胀、目标失焦、职责混乱，所以用意图路由 + 专门 Agent + Plan/Execute subagent。

**口语和答案评审**

回答覆盖点全，但“为什么多 Agent”经常停留在概念层。面试官真正想听的是：业务复杂性如何映射到架构拆分，什么时候不用多 Agent，拆分后如何证明更好。

**最佳答题思路**

先给判断标准，再讲系统拆分，最后讲效果和边界。

**建议表述**

> 我们不是为了追概念才做多 Agent，而是因为三个场景的任务形态差异很大。知识查询更像检索增强生成，适合 Agentic RAG；数据查询链路相对固定，适合 workflow 化的 Text-to-SQL；复杂归因诊断是长程任务，需要多步规划、工具调用、结果校验和局部重试。如果把这些都塞进一个 Agent，prompt 会越来越大，工具集合过宽，模型容易目标漂移，也不利于评测。  
> 所以我们先用意图识别做一级路由，把固定链路和开放链路分开；对于复杂诊断，再由主 Agent 做 plan，把任务拆成 DAG 节点，委派给不同 subagent 执行。subagent 只拿到自己的目标、必要上下文和工具，执行后把 summary 和 evidence 回传给主 Agent。这样做的收益是职责清晰、上下文隔离、可并行执行，也更容易在节点级别做失败定位和 replan。边界上，如果任务是强流程、强约束、步骤稳定的，我会优先用 workflow 或 Skill，而不是上来就多 Agent。

### 4. 记忆 / 上下文管理

**你的当前思路**

四层记忆：短期、工作区、文件系统、长期。短期承接 session，工作区维护 plan/todolist，文件系统外置大结果，长期沉淀用户画像和任务经验。

**口语和答案评审**

这是你的高频核心卖点，但风险也最大。企业微信等面试中一追问分布式、机器挂了、持久化、同用户路由，答案会暴露“还没做”。建议把“已落地”和“演进设计”明确拆开，不要让面试官以为你在包装。

**最佳答题思路**

先解释每层解决什么问题，再说读写时机，再诚实说明生产化高可用演进。

**建议表述**

> 我们把记忆拆成四层，是为了分别解决上下文窗口、工具结果、任务状态和长期经验四类问题。短期记忆就是当前 session 的对话和推理历史，用于保证连续性；工作区记忆保存当前任务的 plan、todo、关键中间状态，主要用于长程任务防目标漂移；文件系统记忆用于外置大工具结果，比如 SQL 查询结果、日志片段、报告草稿，prompt 里只保留摘要和引用；长期记忆则沉淀用户偏好和成功任务经验，下一次通过 query 检索后拼进 prime。  
> 读写时机上，任务开始时会检索长期记忆并组装 prime；执行中工作区定期回写；上下文达到阈值后做压缩，保留开头目标和最近上下文，中间摘要并外置；任务结束后再做一次经验抽取。当前项目里这套机制主要解决单任务长上下文问题，分布式恢复和跨机器持久化还不是最完善的部分。如果要生产化到更高可用，我会把工作区和文件系统记忆迁到持久化存储，用 session/task id 做状态恢复，并把长期记忆准入、回滚和污染检测作为独立治理链路。

### 5. Plan / Execute / DAG 调度

**你的当前思路**

强模型生成 JSON DAG，节点包含任务、输入输出、依赖；执行时按拓扑并发，失败时做重试或局部 replan。

**口语和答案评审**

架构描述较完整，但“plan 为什么可靠”“失败如何不污染后续”“如何知道缺节点”容易被继续追问。建议把校验分成结构、语义、执行三层。

**最佳答题思路**

目标：把不可控生成变成“可校验的计划 + 可观测的执行”。

**建议表述**

> Plan/Execute 的核心不是让模型随便规划，而是把复杂任务转成一个可校验、可调度、可回放的 DAG。Plan 阶段我们会给模型任务目标、业务边界、工具能力、few-shot 和 SOP 样例，要求输出结构化 JSON：每个节点包含 role、instruction、input、output、dependency 和 expected evidence。  
> 生成后先做结构校验，包括字段完整性、依赖关系、是否有环、是否有孤立节点；再做语义校验，用 rubric 判断节点是否可执行、粒度是否合理、是否越过系统能力。执行阶段按入度做并发调度，每个节点只拿必要上下文和工具。失败时先分类：偶发工具错误做有限重试；结构性失败标记当前节点和下游依赖节点失败，再把失败 evidence 返回给 planner 做局部 replan，而不是整条链路重跑。这样可以把长程任务的不可控性限制在节点级别。

### 6. RAG / Agentic RAG

**你的当前思路**

naive RAG 会因为 chunk 切分导致 SOP 前置条件缺失，多跳问题召回不全，所以升级 ReAct 多轮检索和父子 chunk。

**口语和答案评审**

“为什么升级”讲得比较清楚，但对延迟、收益量化、GraphRAG/AI Wiki/单次检索替代方案的比较不够主动。要从“我们用了 ReAct”变成“我们按问题类型选择检索策略”。

**最佳答题思路**

用 bad case 引入，再给分层解法和取舍。

**建议表述**

> naive RAG 最大的问题不是不能搜，而是对 SOP、多跳问题和条件链条不稳定。比如一个预算分配 SOP，关键前置条件可能在相邻段落或上级章节里，单次向量召回只命中操作步骤，没有命中约束条件，模型就会生成一个看似合理但实际跑不通的答案。  
> 我们的改造分两类：第一类是索引侧，用父子 chunk、相邻窗口和章节回溯解决上下文碎片化；第二类是推理侧，用 Agentic RAG 让模型基于 observation 决定是否继续检索、换 query、扩大范围或停止。不是所有问题都走多轮，简单事实问答仍走低延迟路径；只有 SOP、多跳诊断、信息不完整的问题才走 ReAct 多轮。后续更理想的是加后置 verifier，如果答案证据不足或引用冲突，再触发二次检索，而不是固定多轮。

### 7. Agent 评测体系

**你的当前思路**

按场景拆评测：RAG 用关键词/LLM judge，Text-to-SQL 用 exact/execution match，归因诊断用主因辅因和路径 checkpoint。

**口语和答案评审**

这是很容易区分候选人成熟度的主题。你现有回答有框架，但经常被追问“为什么多评分器合理”“LLM judge 不稳定怎么办”“GoldenSet 怎么持续建设”。需要更像一个评测系统，而不是一组指标列表。

**最佳答题思路**

讲清“分层评测 + 多评分器 + 数据闭环 + 评测漂移治理”。

**建议表述**

> 我会把 Agent 评测分成三层。第一层是任务结果是否对，比如 Text-to-SQL 看 execution match，RAG 看关键实体和引用证据，归因看主因/辅因是否命中；第二层是过程是否可靠，比如有没有无效工具调用、是否漏关键 checkpoint、是否越权查询；第三层是线上业务指标，比如运营采纳率、人工二次修改率、平均处理时长。  
> 多评分器的原因是不同任务的可判定性不同。SQL 可以用代码和执行结果判定，开放问答只能部分用实体 F1，复杂诊断需要 LLM judge 和人工抽检结合。为降低 LLM judge 漂移，我们会固定 judge 模型版本、用 rubric 和 few-shot 约束、保留人工标注锚点样本，并持续把线上 bad case 回流到 Golden Set。这样评测不是一次性打分，而是一个离线回归 + 在线反馈的闭环。

### 8. Text-to-SQL

**你的当前思路**

query 改写、表列召回、列值探测、SQL 生成、反思纠错、多次生成共识。

**口语和答案评审**

多阶段流程讲得熟，但复杂 join、schema linking 评估、value mismatch 和 prompt 自动优化被深挖时，容易变成“我们可以做”。建议明确当前边界：单表/少表好，多表复杂 join 是难点。

**最佳答题思路**

按“为什么不能直接生成 SQL -> 拆阶段 -> 核心难点 -> 边界和演进”回答。

**建议表述**

> 我们没有直接让模型一次性生成 SQL，因为业务表名、字段名和用户表达之间存在明显 gap，直接生成容易幻觉。链路上先做 query 理解和改写，再做 table recall 和 column recall，召回后用 LLM 做语义 selection；对于容易 value mismatch 的列，比如 region、campaign type，会做 column exploration，把枚举值或数值分布补进上下文；最后再生成 SQL，并基于执行错误做反思纠错，多次生成结果一致时采用共识结果。  
> 这套方案对单表和少量 join 比较有效，主要收益来自 schema linking 和列值探测。当前难点是复杂多表 join，尤其是隐含关联关系和业务口径不一致时，光靠 prompt 不够，需要更强的表关系建模、查询日志样本、甚至针对 SQL 生成做 SFT。我的边界判断是：高频固定指标可以沉淀成 Skill 或指标 API；临时分析类需求再走 Text-to-SQL。

### 9. 业务效果 / ROI / 落地数据

**你的当前思路**

回答 DAU、采纳率、准确率、效率提升，但有时比较分散。

**口语和答案评审**

这是当前最需要强化的部分。多轮面试都在问“到底有没有用”。如果你只说 70% 采纳率，面试官会觉得不够；你需要解释任务类型、上线阶段、人工 baseline 和下一步提升路径。

**最佳答题思路**

用“北极星指标 + 分场景指标 + 当前阶段解释 + 提升计划”。

**建议表述**

> 我们定义成功不是单看模型准确率，而是看运营能不能少找研发、少手工查数，并且最终结果可采纳。北极星指标是任务采纳率和人工节省时长，分场景看：知识查询看答案正确率和引用证据，数据查询看 SQL execution accuracy，复杂归因看主因命中率、路径完整性和运营采纳率。  
> 当前系统已经在线给内部运营使用，知识查询和单表数据查询相对成熟，复杂归因诊断还处在 70% 左右采纳率的阶段。这个数字不能简单说高或低，因为复杂归因本来需要研发/策略同学人肉排查，Agent 能覆盖结构化路径比较明确的部分，但对长期优化建议、策略型诊断还不够。下一步我会优先补三件事：bad case 回流评测集、plan 阶段 evidence 约束、把高频固定诊断沉淀成可复用 Skill，提高可控性和稳定性。

### 10. MCP / Skills / 工具治理

**你的当前思路**

知道 MCP、Skills、工具注册、参数预填、鉴权，但项目里落地不深。

**口语和答案评审**

不要把未落地的东西说成已落地。最佳策略是承认项目当时主要是自研 tool registry/workflow，但说明如果重构，会如何接 MCP/Skills。

**最佳答题思路**

区分 Tool、MCP、Skill、Workflow、Agent 的边界。

**建议表述**

> 在我的项目里，当时主要是自研工具注册和 workflow，没有大规模基于 MCP/Skills。但我理解它们的边界是：Tool 是最小可调用能力；MCP 是工具协议和外部能力接入方式；Skill 更像把一类稳定任务的说明、资源和执行入口封装成可复用能力；Agent 则负责在开放任务里规划和选择。  
> 如果今天重构，我会把稳定、高频、强约束的链路沉淀成 Skill，比如固定口径的数据报表、标准 SOP 排查；把外部系统能力通过 MCP 接入，并在网关层做鉴权、参数预填、schema 校验和限流；复杂诊断仍由 Agent 做 plan，但它调用的是更受控的 Skill/MCP 能力，而不是裸工具集合。

## 四、口语表达专项评审

### 主要问题

1. **填充词过多**：高频出现“然后”“这个”“这样一个”“整体来说的话”，会拉长答案并削弱判断感。
2. **句子过长**：一个句子里包含背景、方案、原因、结果，面试官很难抓重点。
3. **抽象名词堆叠**：如“架构的设计”“能力的落地”“效率低下的问题”，缺少具体对象和动作。
4. **指标表述不稳定**：DAU、团队规模、准确率、采纳率在不同回答中边界不完全一致。
5. **被追问时容易 defensive**：例如采纳率 70%、不用 MCP、没做分布式持久化时，容易解释现状，而不是主动给出边界和演进。

### 推荐表达原则

1. 每个回答先给一句结论：**“我的判断是……”**
2. 再给三点结构：**“第一，第二，第三。”**
3. 必须带一个例子或指标：**“比如我们遇到过……”**
4. 最后补边界：**“这套方案适合……不适合……”**

### 需要替换的口头禅

| 原表达 | 建议替换 |
|---|---|
| 然后我们做了这样一个架构 | 所以架构上我拆成三层 |
| 这个问题的话主要是 | 这个问题的核心是 |
| 整体来说的话 | 总结一下 |
| 可能还是需要 | 下一步我会优先 |
| 我理解是这样 | 我的判断是 |
| 做一个能力的落地 | 把能力接到真实业务流程里 |

## 五、答案思路专项评审

### 做得好的地方

1. **主线统一**：所有面试都能回到广告系统 + Agent 落地。
2. **技术面覆盖广**：多 Agent、RAG、SQL、评测、记忆、工具治理都有经验。
3. **能讲工程取舍**：知道 workflow、Agent、Skill 的适用差异。
4. **有真实业务场景**：不是纯 demo，有运营、广告、数据查询、归因诊断上下文。

### 最需要补的地方

1. **从“架构有什么”升级为“为什么这样设计”**：每个模块都要能讲清原始 bad case、替代方案、取舍和收益。
2. **从“模型能力”升级为“系统治理”**：强调评测、回滚、权限、限流、审计、状态恢复。
3. **从“准确率数字”升级为“业务闭环”**：采纳率、人工节省、二次修改率、任务覆盖率要组合讲。
4. **从“未来可以做”升级为“当前边界 + 下一步优先级”**：承认没做的部分，但给出清晰演进方案。

## 六、优先优化建议

### P0：准备 8 个标准答案

必须背到自然，不是逐字背，而是固定结构。

1. 90 秒自我介绍；
2. 为什么离职 / 为什么看 Agent 机会；
3. 商家运营 Agent 项目背景与架构；
4. 为什么多 Agent，而不是单 Agent / workflow / Skill；
5. 四层记忆怎么设计，机器挂了怎么办；
6. Plan/Execute 如何保证可控，失败怎么处理；
7. Agent 评测体系怎么做，LLM judge 不稳定怎么办；
8. 项目效果如何证明，70% 采纳率怎么解释。

### P1：补强三个硬伤

1. **分布式与高可用**：准备 session/task 状态持久化、恢复、幂等、checkpoint、同用户路由的标准答案。
2. **评测科学性**：准备 Golden Set 构建、bad case 回流、judge 漂移、人工锚点样本、线上指标闭环。
3. **Text-to-SQL 复杂 join**：准备表关系图谱、查询日志挖掘、业务口径治理、SFT/微调、固定指标 Skill 化。

### P2：补基础题

1. Linux `top`：load average、CPU us/sy/id/wa、内存、swap、进程排序；
2. TCP `TIME_WAIT`：为什么主动关闭方等待 2MSL、如何处理大量 TIME_WAIT；
3. Go `sync.Pool` 和内存池：对象生命周期、归还前 reset、分片、并发安全；
4. 常见算法：三数之和、LCS、背包、二叉树层序/DFS。

### P3：建立问题-证据卡片

每个核心主题准备一张卡片，包含：

1. 原始 bad case；
2. 方案；
3. 替代方案为什么没选；
4. 指标收益；
5. 当前边界；
6. 下一步计划。

## 七、下一轮面试建议打法

开场时主动建立人设：**“我不是只做 prompt 或 demo，我更关注 Agent 在复杂业务里的工程落地：任务建模、工具体系、记忆、评测和线上治理。”**

被问架构时，不要先画一堆模块，先说业务任务形态：

> 知识查询是检索问题，数据查询是结构化查询问题，复杂归因是长程诊断问题。三类任务形态不同，所以我没有用一个 Agent 兜所有能力，而是用路由、workflow 和多 Agent 分别处理。

被问缺点时，不要说“容易被新挑战吸引”。建议说：

> 我过去有时会先从技术架构完整性出发，后来在 Agent 项目里意识到，生产落地更重要的是先定义可验证的业务指标和失败边界。现在我会先把目标、评测和 bad case 闭环定清楚，再推进架构演进。

被问项目不够成熟时，主动承认边界：

> 这个系统不是完全自动驾驶，当前更像运营 Copilot。它在结构化路径明确的归因诊断、知识查询、单表数据查询上效果更好；对长期策略优化、多表复杂分析、跨系统自动执行还需要更强的工具化和评测闭环。这也是我下一阶段最想继续深挖的方向。
