第二个项目的话就是主导了商家运营助手agent的一个落地。这个项目主要是为了解决商业运营在知识获取和数据查询以及我们的一个综合决策分析的这样一个三个环节的效率低下问题。然后设计了像混合的多级 agent 架构，然后包括像上下文的一个四层记忆机制，然后以及一个 plan and execute这样一个多智能体的一个工作的范式。

## Q2. 商家运营助手项目

**问题：** 可以介紹一下你在 Shopee 这个多 A 准的商家运营助手吗？

**回答：** 这个项目的话就跟刚刚提到的，它主要是解决三个痛点。随着我们广告系统持续的一个演进，业务也越来越复杂，策略也越来越复杂。商家运营它在知识查询、数据查询以及综合决策分析这三环节存在痛点问题。

知识查询，它因为是整个我们的一个知识库它是散落在多个文档之间的，包括我们的一些策略机制也都是分布在各个文档的。运营同学想要做知识查询，他们之前的方法就是自己去人工的看文档，然后再去理解吸收。

数据查询，他们的数据需求主要是用来去follow他们广告组的一个投放表现，会涉及到诊断广告组表现有异常的一些情况，比如广告组的一个曝光下降。以往更多的是向数据团队去做提需求，拉出一版数据，然后让他们自己分析。

归因诊断以及决策优化建议，相当于需要定位广告投放为什么有问题，哪里有问题，怎么解决。以前大量依赖人工处理，跟产品和策略同学沟通对齐。

技术架构的话就是基于意图理解作为路由，分发到下游不同能力的agent。意图理解分成五个类别，包括知识查询意图、数据查询意图、归因诊断和角色优化意图、闲聊意图、unload意图。

## Q3. RAG/IG 切分、存储和选型

**问题：** IG 是你们自己做的吗？文件怎么切？文本片段怎么存？为什么用 ES 和 Qdrant？

**回答：** 我们自己做的。切分文件的话我们也是有多种策略都尝试过。最开始通过普通固定大小的长度做切分，但是一个大小不好控制，切小力度特别细，切大力度特别粗；第二个是一开始没有做overlap，上下文缺失比较严重。

后来的话我们采用这种父子结构，通过细粒度做照回，再通过细粒度回溯到负力度的chunk，扩充它的上下纹。我们有句子级别、paragraph级别、章节级别。句子按标点符号以及空格，段落在页面文档里有固定抽取格式。构件的话是从小往上走，先做最小力度切分，再回溯到上一层次。

文件主要是网页文档，然后我们自己转录下来的。网页是HTML，但是有做清洗和转录，通过HTML变成只有文本的PDF。最终做切分是针对纯文本的PDF文件。

文本片段主要存在限量数据库还有ES里面。ES是做混合检索，提高召回率。限量数据库用Quadrant。调研了Mirrors、ES和Quadrant。Miverse是完整生产级项目，但运维复杂、成本高。ES是非原生相量检索，分段查询和合并效果不是全局相量索引库。Quadrant是原生相较水平，开源轻量级。

## Q4. Agentic RAG

**问题：** Agentic RAG 除了 ReAct，还有其他功能吗？会不会判断回答不好再扩大范围重新搜？

**回答：** 它会根据query先思考，再做行动，行动完拿到结果反馈observation之后，再重新做反思，再做新一轮思考。它也许选择直接停止或者输出答案，也可能继续选择其他工具执行这样的 gigantic 多轮搜索范式。

您说的这里确实我们也有考虑，但是现在还没有做。比如后置Verify这样一个角色，给结构做评判，通过大模型LAM judge方式做多维度标准评判。如果不满足条件，就基于反馈信号给到read角色中心模型，让他再决定要不要做新的检索。

## Q5. Plan Execute 拆任务和失败处理

**问题：** Plan Execute 怎么拆任务？计划是什么格式？子 agent 失败怎么办？拆分不合理怎么办？

**回答：** 规划主要针对复杂任务，比如归因诊断，用户需要问广告主曝光下降原因或者IoR下降原因。我们会给它一个生成规划的DAG图格式、FuseShort样例、标准化SOP规划流程作为样例安利库，再补全系统工具能力，调用Plam Agent生成DAG图式规划定义。

系统根据DAG图定义做执行调度，每一步可以并发执行当前没有入度依赖的节点。整个graph执行完成之后，把所有subtask结果汇总到主agent里面，再决定下一轮replan还是回答用户。

计划是json格式的DAG定义。每个节点包括role、决策、任务instruction、input和output、前续依赖节点list。通过dependency字段表达前续依赖和后续输出关系。

子agent执行失败，会先对失败分类。如果是某个工具电容失败，定义为偶发的时代失败，可以通过从事解决，就直接工具从事。节点完全失败时，判断是不是影响后续流程推进，不影响就继续执行；影响的话做局部replan，把失败状态标记成失败，下游节点标记成失败，再返回给主agent plan做replan。

拆分力度、合理性、结构正确性，DAG规划生成之后有后置verifier。先教验结构正确性，包括字段完整、依赖关系、有无缓、孤立节点。如果有问题就基于错误重新生成。质量教验通过LIMI judge判断plan合理性、节点是否可执行、路径是否高效、是否有无效调用、规划力度是否合适。

## Q6. 四层记忆和压缩

**问题：** 四层记忆每层存什么，怎么用？压缩除了摘要还有什么方式？

**回答：** 短期记忆就是subtask或者agent在任务执行过程中积累的绘画history。文件系统记忆保存工具调用结果以及大文件读取数据。工作区记忆是为了解决长程任务上下文持续膨胀导致多阶段目标飘移，把最开始的plan写到功能区记忆里面，有一个文件维护它，还有todolist记录状态。长期记忆保存两个维度，一个是用户画像，第二个是任务经验，每个session结束后抽取写入长期记忆。

每个query过来之后有动态prime拼装过程。创建任务后，先拼接sys prompt、用户query、长期记忆检索结果，进行第一次推理。plan会把计划和tool list写到文件里。工作区记忆会在设定步数预值后做心跳，把当前目标和2d list回写到prompt最后。

短期上下文在70%预值会做压缩。策略是保留前10%和后10%，中间结果做大模型摘要以及原始内容外置，外置到文件系统记忆，再把摘要回补到短期上下文。

除了摘要，减少上下文体积可以保留最近N轮历史消息，也可以整体summary，但信息丢失密度可能偏高。还可以保留前10%后10%，中间压缩。外置则是工具结果外置和上下文信息外置。

## Q7. Text-to-SQL / Test2Circle

**问题：** Test2Circle 怎么生成？怎么找到目标表和列？schema linking 怎么评估？

**回答：** 我们是把一次性生成circle的过程拆成多阶段。包括快速改写，然后schema linking，包括table record和column record，然后column exploration做劣值探测，解决circle语用户query里面查询条件和数据库真实字端案不匹配的问题。再基于上下文做大模型circle生成，通过反思机制根据错误信息做纠错多次生成。最后有consensus共识机制，并行取比如五次生成，多数相同结果就采用那一条。

表整个表征成占用员形式，会有业务应用场景、字段说明、表的应用视力。列也是基于这三层业务拼装上下文表真成向量形式。通过query改写之后做表照回和列照回，过滤到topk，再过大模型做语意selection。

schema linking 假阳性和假阴性，录选重要的表更严重，因为后面有LMS Selection做语意金牌，如果表没有照回，后面生成完全没办法。照轨率应该80%以上，准确率低一点70%多。现在主要针对简单单表查询，复杂查询会拖准确率和召回率。

## Q8. 测评数据集

**问题：** 测评数据集怎么收集标注？多大？

**回答：** 主要还是通过运营人工编造。因为这块数据很精确，不太希望黄金测试机通过种子黄金测试机用大模型生成，那样可靠性差一点。IG部分通过用户真实日常提问，再由运营人工标注。Test2Circle通过之前DI查询入口的query日志捞出来，有query和circle匹配关系。复杂任务类型大概100条，IG大概300条，text to circle大概200条。

## Q9. LLM API 网关

**问题：** 如果设计 LLM API 网关，接 OpenAI、Claude、Gemini、千问等模型，除了路由还考虑什么？

**回答：** 先从兼容性考虑。给用户统一入口，让他不关心后面的provider是谁。需要做适配层，提供通用模型服务接口，定义好模型请求。网关这一层适配不同模型接入能力，把它们API实现成我们自己的能力API，做到统一接口面和实际服务路由。

其他就是工程问题，包括稳定性、超时、线流、熔断、传统RPC请求治理。还有权限和安全性账户问题，每个用户对哪些模型有访问权限。成本管理也需要，内部用户有限额和计费，没额度时正常拦截。格式不一样就做协议转发，把内部维护的History、System Prompt拼到不同模型协议对应位置。

provider限流的话，我们内部也要有限流处理，最好能获取下游provider限流并对齐。不能的话做手动降级限流调整，避免用户请求白白打过去。恢复没法控制，只能提示用户切换模型。

## Q4. Agentic RAG 和后置 verify

**问题：** Agentic RAG 除了 ReAct，还有做其他功能吗？比如最后生成效果不好打回重新搜？

**回答：** 它会去根据你的 query然后去做一个先思考，然后再去做行动。行动完之后它拿到一个结果的反馈 observation 之后，然后它再去重新的做一个反思，再去做一个新的一轮思考。它可能这一轮思考它也许会选择直接停止或者输出答案，也可能去继续选择其他的工具去执行这样的一个 gigantic 多轮的一个搜索的一个范式。

您说的这里确实我们也有考虑，但是现在还没有做。比如您刚说做到一个后置的Verify这样一个角色，就去给它的结构做一个评判，然后去通过这种大模型LAM judge的方式去给它做一个多维度的标准评判。如果它不满足我们条件，我们可能就是能够基于这个反馈信号给到我们作为read的这样一个角色中心的这个模型一个新的反馈，然后让他再去决定要不要去做新的检索。

## Q5. Plan Execute 怎么拆任务

**问题：** Plan Execute 是怎么拆分任务的？计划是什么形式？子 agent 失败怎么处理？如果拆分不合理怎么办？

**回答：** 我们的一个规划的话主要是针对我们这样一个复杂任务，包括像比如这种归因的诊断，比如用户需要去问一下这个广告主它的一个曝光下降的一个原因是什么或者IoR下降的一个原因是什么。这个时候我们其实就是通过这样一个prompt的一个优化，包括我们会给它一个生成的一个规划的DAG图的一个格式，第二个的话是一个我们的一个FuseShort的一个样例，第三个就是我们会积累一些这种标准化的一个SOP的这种规划流程。

去调用我们的Plam Agent让它去生成一个我们这种DAG图示的这样一个规划的定义，然后我们的系统再根据这样一个DAG图的定义去做一个DAG图的一个执行调度。每一步它都可以并发的去执行当前部没有入度依赖的这些节点。等到整个的一个graph执行完成之后呢，它再把所有的subtask这样一个结果汇总到我们的这样一个主agent里面。

计划是一个json格式的这样一个DAG的定义。它包括每个节点的定义，每个节点里面的内容它包括它的一个role，然后它的决策，它的一个任务的instruction，第三个的话就是它的一个input和output，第四个的话就是它的一个前续的依赖的节点的一个list。

某一个子agent执行失败的话，我们会首先是对这个失败做一个分类。比如他如果是某一个工具电容失败了，它就是我们这里定义的是一个偶发的时代失败，就是它可以通过从事去有可能解决的，我们就会直接进行一个这种工具的一个从事。第二个的话就是我们的一个节点节点是完全失败了，这个时候的话我们会判断它是不是会影响我们的这样一个后续的流程的推进。如果它不影响的话我们就会继续往下去做一个执行；如果影响的话我们就会进行一个局部的这样一个replan。

拆分的力度、合理性、结构正确性这三个维度的话，我们在整个的DHT图它的规划生成之后有一个后置的verifier这样一个教验模块。它会去教验结构的正确性，包括字段是不是完整，依赖关系是不是正确，有没有缓，孤立节点这些。如果有问题的话就会直接基于这些错误让它再去重新生成。

## Q6. 四层记忆架构和压缩

**问题：** 四成机翼架构每一层存什么？怎么用？短期到一定程度变长期怎么处理？压缩除了摘要还有其他方法吗？

**回答：** 首先的话就是我们的一个短期记忆，短期记忆的话就是我们一个subtask或者一个agent他在整个任务执行的过程中他所积累的这些绘画的history。

文件系统的话就是去保存它的一个工具调用的结果以及它的一个整个的一个一些大文件的这样一些读取的数据也是在文件系统记忆里面。工作区记忆主要是为了去解决它的一个随着长程任务它的一个上下文持续膨胀，然后导致它的一个多阶段的这样一个目标是飘移的问题。我们去通过它的一个最开始的一个会有一个plan，然后去把它的一个先思考的这样一个plan给它写到我们的一个功能区记忆里面，有一个文件来维护它，然后包括我们还会有一个todolist这样一个文件。

长期记忆的话主要就是保存两个维度的事情。我们这里把长期记忆分成两种类型，一种就是用户的一个画像，第二个的话就是任务的经验。通过每一个session结束之后会去做这两种记忆的一个抽取，然后去写到我们的一个长期记忆里面。

短期上下文的话我们会在70%的这样一个预值的话我们就会去做一个压缩的执行。压缩的话它的一个整体的策略就是保留前10%和保留后10%，对中间的结果就做一个大模型的一个摘要，然后以及它原始内容的一个外置，外置之后也就是放在我们刚刚那个文件系统记忆里面，然后再把摘要给回补到我们的一个短期上下文。

除了摘要，减少上下文体积的话它有不同的策略，包括保留最近的N轮的一个历史消息，或者做一个阶段，这是直接丢弃的方式。第二个的话就是你对整体做一个summary，但整体summary有一个缺点，就是信息丢失的密度可能就会偏高。第三个就是保留前百分之十保留后百分之十，中间的信息把它给做压缩。外置的话就是把工具的结果去做一个外置，以及把整个上下文的信息也做到一个外置。

## Q7. Text-to-SQL / Test2Circle

**问题：** Text2SQL 怎么生成 SQL？怎么根据自然语言找到目标表和列？Schema linking 召回怎么评估？

**回答：** 这个的话我们是把一次性生成circle的这样一个过程把它拆成一个多阶段了。用多阶段的这样一个每一个环节的确定性去优化它整体的这样一个circle生成的准确率。我们会包括像快速改写，然后再是schema的linking，包括你的table record和你的column record，然后再包括你的column exploration去做一个劣值的探测，去解决你circle语用户query里面的查询条件和你数据库真实字端案不匹配的这样一些问题。

基于整体的这些上下文然后再去做一个大模型的circle生成。这部分的话就是通过这样一个也会有这种反思的机制，然后根据你生成的结果，然后去做一个纠错的这样一个多次生成。最后的话整体的生成的环节我们还有一个consensus的这样一个共识机制，就是会并行去取比如五次生成，然后你对于这种多超过一半的是同样的结果的话我们就会去采用那一条。

表的话它整个都表征成了一个占用员的形式，像它会有它的一个业务应用场景，然后它的一个字段的说明，然后它的一个表的应用一些视力。列的话也是同样的基于这三层的一个业务拼装的这样一个上下文去给它表真成的一个向量形式。再去通过query的改写之后，通过你的query去做一个表的照回和一个列的照回。

schema linking 的假阳性和假阴性，录选重要的表会更严重一点，因为我们后面还会有一个LMS Selection的这样一个过程，它可以去做一些语意上的一些金牌。如果你表都没有照回回来的话，那它后面生成就是完全没办法。照轨率的话应该是80%以上，然后准确率的话会低一点70%多。

## Q8. 评测数据集

**问题：** 测评数据集怎么收集和标注？有多大？

**回答：** 这个的话主要还是通过运营它的一个人工的一个编造。因为我们第一部分的话这一块的数据还是很精确的，我们也不太希望我们的黄金测试机通过那个最开始的种子黄金测试机去通过大模型生成，因为那样的话可能它的一个可靠性还是会差一点。

IG那部分的话也是通过用户真实的一些他们日常会提问的一些问题，然后我们去通过运营他人工的一个标注。Test2Circle也是我们之前有一个DI查询的这样一个入口，也是通过那一部分的query日志，然后把它给捞出来。复杂任务类型大概是100条的一个样子，IG大概是300条，text to circle大概也是200条。

## Q9. LLM API 网关

**问题：** 如果设计 LLM API 网关，对外提供统一接口接不同模型，除了路由还要考虑什么？格式差异、限流怎么办？

**回答：** 我先从这个兼容性这一块考虑吧，就是说把这个功能性完善，就是你给他相当于给用户一个统一的入口，然后他能够不关心以后后面的一个provider是谁。我们是需要肯定做一个设备层的，就是我们提供一个通用的这样一个模型服务的接口，接口里面去给它定义好比如说它的一个模型的请求。

System Prompt格式不一样位置不一样，那我们肯定是要做协议的转发。你肯定是要把我们内部维护的History这些历史消息，包括你的System Prompt，然后去给它拼接到它对应的不同模型的请求的那个协议的对应的位置。

provider限流的话，首先我们自己的内部应该也是要有限流处理的。如果能够获取到下游provider的限流的话最好能够做到对齐。如果不能的话我们就可能需要去做一个手动的一个降级的一个限流的一个调整。恢复的话我们没有办法控制，或者我们只能去做提示用户可以做模型的切换。

## Q1. 自我介绍

**问题：** 如果准备好的话，可以先做一个自我介绍。

**回答：** 面试官您好，我叫陈宏，目前在 Shopee 负责广告系统架构以及 AI Agent 架构开发。

在 Shopee 主要有两段项目经验。第一段是作为核心开发者参与广告系统全链路从 0 到 1 的搭建和持续演进，保障高并发环境下稳定性，以及算法效果持续优化迭代。这段经历让我对在线架构和广告策略算法有比较深入的了解和实践。

第二个项目是主导商家运营助手 Agent 落地，解决商业运营在知识获取、数据查询以及综合决策分析三个环节的效率低下问题。设计了混合多级 Agent 架构、上下文四层记忆机制，以及 plan and execute 多智能体工作范式。

上一段工作在百度做机器学习框架训练优化、模型分析体系建设，以及模型调研一站式平台，以模型仓库为中心对接模型训练和模型上线，提升模型调研端到端效率。整体技术领域聚焦在线 AI 架构，具备算法和工程双视角。

## Q2. 商家运营助手项目介绍

**问题：** 可以介绍一下你在 Shopee 做的多 Agent 商家运营助手吗？

**回答：** 这个项目主要解决三个痛点。随着广告系统持续演进，业务和策略越来越复杂，商家运营在知识查询、数据查询、综合决策分析三个环节存在痛点。

知识查询方面，知识库散落在多个文档里，策略机制也分布在各个文档。运营同学想查知识时，以前要人工看文档、理解吸收，效率很低。

数据查询方面，运营需要 follow 广告组投放表现，诊断曝光下降等异常。以往更多是向数据团队提需求，让数据团队拉数据，再自己分析，中间存在数据黑盒，不能方便快速拿到满足需求的数据。

复杂归因诊断和优化建议方面，运营需要定位广告投放为什么有问题、哪里有问题、怎么解决。以前大量依赖人工，需要运营、产品、策略沟通对齐，效率比较低。

基于这个背景，我们提出基于 AI 能力的 Agent 助手，解决这三个环节效率问题。技术架构是基于意图理解做路由，分发到下游不同能力 Agent。意图分成知识查询、数据查询、归因诊断和策略优化、闲聊、unknown 五类。前三类路由到对应能力 Agent，unknown 触发意图澄清，闲聊调用普通大模型回答。

## Q3. RAG Agent 是怎么做的

**问题：** RAG Agent 这块怎么做？是你们自己做的还是开源框架？

**回答：** RAG Agent 提供知识查询能力。我们从 simple RAG 开始，为了解决知识查询里知识分布碎片化、chunk 机制导致多跳问题处理不好，改造成 Agentic RAG，让模型自己决定什么时候搜索、搜索什么、什么时候停止。

这块是我们自己做的，从文件 chunk 切分到后面的搜索召回都是自己做。

## Q4. 文件怎么切分

**问题：** 自己做的话，你们怎么切分文件？

**回答：** 最开始用固定大小长度切分，但发现几个问题。切小的话粒度特别细，切大又特别粗；一开始没有做 overlap，上下文缺失也比较严重。

后来对分块机制做了优化，采用父子结构。通过细粒度 chunk 召回，再回溯到父粒度 chunk 扩充上下文，缓解上下文碎片和缺失问题。

构建方式是从小往上走，先做最小粒度切分，再回溯到上一层次。比如 sentence 属于某个 paragraph，就认定上层片段是这个 paragraph；paragraph 又能合成章节层次。

## Q5. 支持什么文件类型，候选人是否负责 RAG 切分开发

**问题：** 你们处理什么类型文件？RAG 系统是你开发的还是和同事一起做？

**回答：** 主要是网页文档，经过清洗和转换后变成纯文本 PDF 文件，最终切分是针对 PDF 处理。

我没有负责 RAG 里面文本切分的开发，但我是作为项目 owner 全程跟其他同学做设计和对齐。我其他核心模块有开发。

## Q6. 文本片段怎么存，为什么用 ES 和 Qdrant

**问题：** 文本片段怎么存？为什么用 ES？向量数据库用什么，为什么选它？

**回答：** 文本片段主要存在向量数据库和 ES 里面。用 ES 是为了做混合检索，提高召回率。

向量数据库用 Qdrant。我们调研了 Milvus、ES 和 Qdrant。Milvus 是比较完整的生产级项目，索引类型支持最好，查询延时也低，但运维复杂、成本高。ES 也考虑过，但 ES 不是原生向量检索，它还是原来 LSM 分段查询架构，查询需要段合并，索引也是分段模式，检索效果不是全局向量索引库。Qdrant 是原生向量数据库，聚焦 filter 能力和检索能力，开源且轻量，所以选择 Qdrant。

当时数据量不大，没有做压测。

## Q7. 什么是 Agentic RAG

**问题：** 你讲到 Agentic RAG，它和 ReAct 模式一样吗？除了 ReAct 还有做其他功能吗？

**回答：** Agentic RAG 跟 ReAct 模式类似。它根据 query 先思考，再行动，拿到 observation 后再反思，进行新一轮思考。它可能停止并输出答案，也可能继续选择其他工具执行，是多轮搜索范式。

我们现在主要是从单次召回、排序、生成演变成 ReAct 范式。面试官提到的后置 verify，比如对生成结果做 LLM judge，如果不满足条件再反馈给检索 Agent 重新检索，这个我们有考虑，但现在还没有做。

## Q8. Plan Execute Agent 怎么拆分任务

**问题：** 可以讲一下 Plan Execute Agent 是怎么拆分任务的吗？

**回答：** 规划主要针对复杂任务，比如归因诊断。用户问广告主曝光下降或 ROAS 下降原因时，我们会做 prompt 优化，包括生成规划 DAG 图的格式、few-shot 样例，以及积累标准化 SOP 规划流程作为样例库，再加上系统工具能力上下文，调用 plan Agent 生成 DAG 图式规划定义。

系统根据 DAG 图定义做执行调度。每一步可以并发执行当前没有入度依赖的节点。整个 graph 执行完成后，把所有 subtask 结果汇总到主 Agent，主 Agent 再根据 subtask 结果决定下一轮 replan，还是基于当前信息回答用户。

## Q9. Plan 的格式是什么

**问题：** Plan Agent 生成的计划是什么形式，包含什么？

**回答：** 是 JSON 格式的 DAG 定义。包括每个节点定义。节点内容包括 role、决策、任务 instruction、input 和 output、前序依赖节点 list。

通过 dependency 字段表达依赖关系，dependency 以 node ID 表示依赖节点 ID，用来构建完整 DAG 图，表征每个节点的前序依赖和后续输出关系。

## Q10. 子 Agent 执行失败怎么处理

**问题：** 某个子 Agent 执行失败了，整体流程怎么处理？

**回答：** 会先对失败分类。比如某个工具调用失败，定义为偶发时延失败，可以通过重试解决，就直接进行工具重试。

如果节点完全失败，会判断是否影响后续流程推进。如果不影响，就继续往下执行。如果影响，就做局部 replan：把这一步失败信息标记为失败，再把下游所有节点标记为失败，把信息返回给主 Agent plan，让它做 replan。这样避免所有节点都执行完、消耗大量算力后才从头 replay。

## Q11. Plan 拆分不合理怎么处理

**问题：** Plan 拆出来的结果不合理、子任务过多或过少，有没有遇到？怎么优化？

**回答：** 生产中确实遇到。包括拆分粒度、拆分合理性、结构正确性三个维度。

DAG 图生成后有后置 verifier 校验模块。先校验结构正确性，包括字段是否完整、依赖关系是否正确、有没有环、有没有孤立节点。如果结构有问题，就基于错误重新生成，不进入执行阶段。

粒度问题通过 prompt 约束。我们会在 prompt 里给拆分粒度指导、能力边界定义，让模型知道现在能做什么，以及期望以什么任务粒度规划。这样通过 prompt 约束 action space。

除了结构校验，还有质量校验。通过 LLM judge 判断 plan 合理性，包括节点是否可执行、路径是否高效、是否有很多无效调用、规划粒度是否合适。

## Q12. 工具调用有没有安全检查

**问题：** 工具调用会不会误伤用户文件，或者做危险操作？有没有安全命令检查？

**回答：** 我们这个场景没有，因为提供的是固定工具，不涉及代码和文件写操作。

但像 coding agent 场景，我觉得非常有必要做权限控制和工具治理。工具执行不仅是执行工具这一步，它应该有参数校验、权限控制、权限校验、输出治理，一整套工具调用治理流程。

## Q13. 生产中最棘手的问题

**问题：** 现在生产用的阶段，有没有遇到目前比较棘手的问题？

**回答：** 有。比如归因逻辑有时不准确。广告曝光可能由很多因素组成，会有下钻指标分析。有时候某个特别细微的过滤数异常，但不是主要影响因素，量级不足以影响大盘。模型可能在其他指标都正常的情况下，把这个异常指标作为归因逻辑。实际上这个不成立，所以推理链路合理性还需要优化。

## Q14. 四层记忆架构每层存什么

**问题：** 四层记忆架构每一层存什么？

**回答：** 短期记忆是 subtask 或 Agent 在任务执行过程中积累的会话 history。

文件系统记忆保存工具调用结果，以及一些大文件读取的数据。

工作区记忆是为了解决长程任务上下文持续膨胀导致多阶段目标漂移。最开始会有 plan，把先思考的 plan 写到工作区记忆里，也会有 todolist 文件记录状态。在执行过程中，通过 todolist 和 plan 持续刷新到 prompt，让它持续跟进当前任务。

长期记忆保存两个维度：用户画像和任务经验。每个 session 结束后做两种记忆抽取，写到长期记忆。

## Q15. 记忆怎么被检索和使用

**问题：** 短期记忆、长期记忆怎么检索，怎么用到这些记忆？

**回答：** 每个 query 过来后，有动态 prompt 拼装过程。创建任务后先拼接 system prompt、用户 query，再检索长期记忆并拼进原始 prompt，进行大模型第一次推理。

推理后做 plan，plan 会把计划和 todolist 写到文件里，这就是工作区记忆。工作区记忆在后面执行中会有步数阈值，比如五步后做心跳机制，把当前目标和 todolist 回写到 prompt 最后，做 prompt 约束。

文件系统记忆会在每次工具调用后把完整结果写到文件里，短期上下文只保留摘要信息和文件引用地址。模型后续如果需要看之前结果，就做文件读取动作。

## Q16. 短期上下文怎么压缩

**问题：** 短期记忆到一定程度会变长，会触发压缩吗？除了摘要还有其他方法吗？

**回答：** 会触发压缩。短期上下文到 70% 阈值时，会执行压缩。策略是保留前 10% 和后 10%，中间结果做大模型摘要，原始内容外置到文件系统记忆，再把摘要回补到短期上下文。

除了摘要，主要两个维度：减少上下文体积和外置。减少体积可以只保留最近 N 轮历史消息，也可以整体 summary，但整体 summary 信息丢失密度可能更高。我们采用保留前后、中间压缩，是因为最开始的目标和最近几轮上下文通常更重要，中间步骤大部分已经执行完成，很多是无用信息。

外置包括工具结果外置，以及整个上下文信息外置。

## Q17. 有没有做 prompt caching

**问题：** 有没有了解或使用过 prompt caching？命中缓存和没命中价格差很多。

**回答：** 有了解到，就是把一部分固化 prompt 做缓存。每次保证那部分不变，调用模型时 prompt caching 命中后，推理成本会减少很多。但我们暂时还没有做这一部分。

## Q18. Text-to-SQL 怎么生成 SQL

**问题：** Text-to-SQL 是怎么生成 SQL 的？

**回答：** 我们把一次性生成 SQL 拆成多阶段，每个环节确定性更强，来优化整体 SQL 生成准确率。

包括 query 改写、schema linking，里面有 table recall 和 column recall；然后是 column exploration，做列值探测，解决用户 query 里的查询条件和数据库真实字段值不匹配的问题；再基于这些上下文做大模型 SQL 生成。

生成后会有反思机制，根据执行错误做纠错和多次生成。最后有 consensus 共识机制，并行做多次生成，比如五次生成，如果超过一半结果相同，就采用那一条。

## Q19. 表很多、列很多时怎么做 schema linking

**问题：** 有成千上万张表、每张表很多列时，怎么通过自然语言找到目标表和目标列？

**回答：** 做表召回和列召回。表会表征成向量形式，包括业务应用场景、字段说明、表应用示例。列也类似，基于业务拼装上下文表征成向量。

先通过 query 改写，再通过 query 做表召回和列召回，过滤到 topK。选表时，topK 后还会过一层大模型做语义 selection。

如果一个关键词在很多张表字段里都有，会结合用户上下文，比如用户部门、权限，通过 query 理解和改写，让描述更贴合业务范围，避免因为某个字段相似做误召回。

## Q20. Schema linking 里漏选和多选哪个更严重

**问题：** schema linking 里假阳性和假阴性，漏选必要表和多选不相关表，哪个更严重？

**回答：** 漏选重要表更严重。后面还有 LLM selection 可以做语义精排，如果表都没有召回，后面生成就完全没办法。

整体 Text-to-SQL 当前主要针对简单单表查询会好一点，复杂查询会拖低准确率和召回率。单表准召还是比较 OK。

## Q21. 评测数据集怎么收集和标注

**问题：** 你简历里提到构建测评数据集和多种评分器，数据集怎么收集和标注？

**回答：** 主要通过运营人工标注。最开始的种子黄金测试集不太希望通过大模型生成，因为可靠性会差一点。

RAG 部分用用户日常真实提问，通过运营人工标注。Text-to-SQL 从之前 BI 查询入口捞 query 日志，有 query 和最后 SQL 的匹配关系。复杂任务完全基于人工完整标注。

量级上，复杂任务大概 100 条，RAG 大概 300 条，Text-to-SQL 大概 200 条。

## Q22. 如果设计 LLM API 网关

**问题：** 如果现在让你设计一个 LLM API 网关，你会怎么做？

**回答：** 先从兼容性考虑，提供统一入口，让用户不关心后面的 provider 是谁。用户通过一个模型名参数就可以调用不同模型，代码不用改。

需要做适配层，定义通用模型服务接口，包括模型请求。网关这一层适配不同模型 API，实现协议转换和路由。

除了路由，还要考虑工程治理：稳定性上的超时、限流、熔断、重试；账户体系和权限，比如每个用户对哪些模型有访问权限；计费和额度管理，账户没有额度时拦截；性能方面可以考虑 prompt caching。

不同模型消息格式不一样，比如 system prompt 位置不一样，就要做协议转换，把内部维护的 history、system prompt 拼接到对应模型请求协议的位置。

如果 provider 返回限流，最好内部限流能和下游 provider 限流对齐，避免请求白打。不能对齐时就做手动降级或限流调整，也可以提示用户切换模型。
