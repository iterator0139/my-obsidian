# 网易4面｜问答整理

## Q1. 自我介绍

**问题：** 我们开始吧，你先自我介绍一下。

**回答：** 好的秘书官您好，然后我叫陈宏，然后我目前是在Shopee负责广告系统架构以及AI agent架构的这样开发。然后在Shopee的话主要是两段的项目经验。首先第一段的话是作为核心开发者，然后参与了广告系统全电路的从0到1的一个搭建以及它的一个时序演进，然后这段经验的话主要是让我对整个一个在线的AI，在线的一个在线链路以及整个的广告机制策略这一块有了比较深入的一个实践和了解。

第二个项目的话是主导了这样一个商家运营智能助手agent的一个落地，然后去解决广告商业运营它在知识查询，然后树立查询以及归因诊断这三个场景下的一个效率低下的问题。然后通过这样一个混合多级的这样一个agent架构去对应到不同的一个场景的能力的分发。为了去解决常上下文带来的注意力丢失以及上下文膨胀的问题，设计了四级的记忆机制。

上一段工作经验的话主要是在百度做机学习平台相关的内容，包括模型训练框架的优化和模型分析体制的建设，以及基于模型仓库为中心的一站式模型调研平台。

## Q2. 四层记忆怎么设计

**问题：** 短期、工作区、文件系统、长期记忆，每层写入、读出、淘汰策略怎么设计？

**回答：** 短期的记忆这一块，就是一个我们模型能够看到的session的history，主要是通过内存的list来存整体的消息的绘画历史。每一个subagent和主agent它都是有独立的短期记忆窗口的。

工作区的记忆这一块引入的背景，是为了去解决归因子弹这种长连路的任务长程任务，它会在执行过程中，因为工具调用的一些结果以及一些错误可能会导致整个执行目标的飘移。我们通过工作区记忆去存储plan的规划，第二个就是todolist代办事项，通过这两文件持续跟踪和保持维护它的任务执行状态。

文件系统记忆主要是为了解决工具调用以及上上下文持续膨胀的问题。它通过外置和压缩的方式，存储工具调用完整结果，短期上下文里面只保留摘要信息以及文件引用路径。短期上下文超过预值之后，启动上下文压缩，保留前百分之十和后百分之十，把中间80%做全量外置，再做大模型压缩写回短期记忆。

长期记忆主要是存储任务长期经验。任务执行结束之后，会对整个执行路径做大模型摘要化抽取。比如任务类型是什么，任务是否成功，成功的步骤节点有哪些；失败case也会记录哪一些步骤失败以及失败原因。

## Q3. 长期记忆污染和 judge

**问题：** 怎么避免长期记忆污染？摘要和 judge 用什么模型？为什么选千问3？

**回答：** 这里是有一个准入机制的，就是先抽取了信息之后呢，我们会有一个LMS judge的准入模块，通过泛化能力给它做评分。如果低于打分预值，就会进行拦截，只有符合要求才会写入长期记忆。

门槛设的话会比较高一点，我们分为了5档，只有在45档这两类才会写入。评价标准主要是任务路径是否完整，执行路径规划的结果是否清晰，最后结论是否逻辑电路是否合理。

现在抽取摘要的话主要是用千蚊的235B的那个千蚊3。LMIJUX的话也是这两个模型是同一个模型。因为抽取摘要和评判模型都需要比较强的泛化能力。千蚊3一个是开源生态比较好，第二个是逻辑推理能力以及中文适配能力比较好。我们会有一个小的评测机，构建了大概50条路径，做结构化摘要抽取，然后人工打针。

## Q4. 上下文古烂怎么观测

**问题：** 你们观测上下文古烂是指标还是体感？

**回答：** 两方面都有。第一个是在真实agent运行的时候，因为会有显示的执行调用路径，能看到整个执行路径会慢慢有一些偏移的过程，这是使用体感上。

第二个是工具的平均执行平均调用次数这样的指标。如果注意力丢失，目标飘移，必不可少会导致平均调用次数增长。还会有最后链路评测，和ground truth评测，筛出它和黄金节点的record率和FE分数。record和FE分数越高说明跟黄金规划执行节点越匹配。

## Q5. 参考过哪些 Memory 方案

**问题：** 设计四层记忆有没有参考业界方案？主要区别在哪里？

**回答：** 有参考过一些开源的。长期记忆的话看了一下ZEP和MEMNIN的时间方式，他们也是基于抽取，并且对长期记忆做分类，包括事实的长期系、事件的长期系、procedure的长期系。ZEP在长期记忆检测完成之后，也会做冲突检测以及记忆更新机制。

第二部分是像clock code这一种，当时我们做的时候clock code还没有开源，但是大家对它的机制有一些逆向工程和实践。能看到它有todolist，也能看到它对工具调用的外置和压缩有上下文管理机制。

区别的话我理解我们可能是更加特质化。长期记忆那一块它是已经封装好了准入机制，用户适配化手段比较少。我们这块更加倾向于做整个工具调用、文件管理以及中间任务状态管理。

## Q6. Agent 评估和自动优化

**问题：** 上一个功能后怎么评估、优化？能不能把观测性和评测流程自动化串起来？

**回答：** 我们也是有离线和在线两个评测。新优化功能点开发完成之后，会先进行离线评估，包括黄金测试集的结果准确性评估，工具调用链路效率性评估。问题诊断场景会有100个问题诊断的光处，既包括主音辅音，又包括执行路径label。回跑之后计算归因诊断F1得分，同时还有LMI价值去评判推理逻辑合理性。

当它优于base line的时候，就可以进行AB推流实验。线上因为有用户点彩机制，有采纳度的在线指标，所以借助AB平台分发到用户，基于用户反馈观测线上效果。

自动research auto research理论上可行，但是需要建设基础设施。第一步要有全链路执行数据，这是数据基础。第二步需要诊断模块。上了feature之后自动跑评估，跑完评估之后需要诊断agent，看评分是否达到预期，执行路径有没有不符合预期。然后再基于优化agent loop去做eval、run、optimization这样三阶段loop。

## Q7. 主动策略洞察

**问题：** 被动信息查询向主动策略洞察是什么意思？真正主动洞察需要解决什么？

**回答：** 这个就是基于归因诊断逻辑，给到他一个信息的主动补充以及优化建议。被动信息查询就是他自己需要去做很多数据查询。有了agent的话，agent可以主动给他去做内容提取和推送版。

真正主动洞察，首先需要有信息输入，就像需要有监控的概念一样。拿广告场景来说，广告商家投放广告之后，需要监控广告表现。为每个广告组配备广告效果监控agent，持续通过定时任务拉取广告组投放效果。一旦发现某个业务指标明显异常，就有异常理解模块，看指标是不是真的异常，异常时间和方向，然后触发诊断agent，再到策略优化，最后把优化方案给到运营。

## Q8. IG 知识冲突和 LMWiki

**问题：** IG 知识库新增知识和已有知识冲突怎么办？AIMWiki/LMWiki 和传统 IG 差异是什么？

**回答：** 这里有一个场景，就是存在时间冲突的问题。比如我们的傭军政策，在不同时间会有不同版本。对于这个场景，我们对所有chunk和文本都加上时间戳原信息。结果生成的时候会检测time step冲突，prompt里面优先告诉它使用最新文本信息为准，如果发现冲突就生成风险提示警告。

IG还是基于相似度匹配，包括语意相似度和文本相似度，所以天然缺陷就是语意相关并不表示真实文本一定相关。LMWeek是通过渐进式文本信息查询，类似人类阅读方式，更精准找到跟当前问题匹配的文本信息。随之而来的是工程复杂性和查询耗时问题。IG检索几十毫秒，MWiki需要建计式披露，先看大目录，再做西分子模块信息查询，token销量也更大。

## Q9. 标杆 Agent 产品

**问题：** 标杆 Agent 产品是哪一个？能怎么优化自己的广告商家 agent？

**回答：** 标杆的产品其实还是Clarkode吧。Clarkode整个聪明度和任务可用性体验感非常好。其次还有Cursor，它生存速度非常快，长程任务稳定性也比较好，还有中断、文件恢复这些能力。

稳定性方面，它应该做了一些工具治理，包括工具调用参数调验、权限检验、后置处理、错误从事这一块，有一整套工具调用治理。长程任务也有plan模式，做任务拆解和顺序执行。

优化点首先是整个工具调用全电路，因为这块我们做得没有那么细。第二个可以引入更多可验证中间节点，做中间节点管控，通过子A正能力和plan思想fork出中间结果验证agent，做到自适应修正。

## Q10. Agent 工程师壁垒

**问题：** Agent 工程师核心壁垒来自什么？

**回答：** 我感觉是对模型的理解会更重要一点。工程能力很重要，但是我觉得对模型的理解更重要。因为现在这个阶段，你需要知道模型边界在哪里，它能做什么，工程做什么，系统做什么，这三者清晰区分之后，才能设计出更加智能，随着模型能力进化系统能够更好用的agent。

模型边界一个就是对原理的理解。大模型就是语言概率模型，在大量预训练文本上predict the next token的概率。其次能力从哪里来，能力都是从后训练目标对齐，包括SFT和IIFT这样多阶段后续念，获得代码生成能力、逻辑推理能力。

## Q3. 长期记忆污染和准入

没有达到准度的标准的话，一个就是他整个的上下文的信息里面它会有太多的这样一个噪声，就比如它抽取了错误的这样一个执行节点。第二个的话可能包含了大量的工具调用的这样一些结构在里面。现在的话其实我们是只是做了一个普通的拦截，但是我感觉这一部分内容也是可以去做一个数据的dump，然后基于这样一个样本之后，我们可以去做一些后置的debug case也好，或者说是一些更新的分析也好。

## Q4. 摘要、judge 模型和千问选择

第二个项目是主导商家运营智能助手 Agent 落地，解决广告商业运营在知识查询、数据查询以及归因诊断三个场景下效率低下的问题。通过混合多级 Agent 架构对应不同场景能力分发，同时为了解决长上下文带来的注意力丢失以及上下文膨胀，设计了四级记忆机制。

## Q2. 四层记忆架构每层怎么设计

**问题：** 你提到四层记忆架构，短期、工作区、文件系统、长期记忆，每层写入时机、读取时机和淘汰策略怎么设计？

**回答：** 短期记忆就是模型能看到的 session history，主要通过内存 list 存消息会话历史。每个 subagent 和主 agent 都有独立的短期记忆窗口。写入就是消息累计过程中持续 append。

工作区记忆是为了解决归因诊断这种长链路任务在执行过程中，因为工具调用结果或错误导致执行目标漂移。它存储 plan 规划和 todolist 代办事项，通过这两个文件持续跟踪和维护任务执行状态。每一轮新迭代会把 todolist 和目标 append 到短期记忆最后，让它持续保持目标准确性。写入时机包括 subagent 第一次规划时写入 plan 和 todolist，以及 subtask 执行完成后更新代办清单状态。

文件系统记忆是为了解决工具调用和上下文持续膨胀。它会存储工具调用完整结果，短期上下文只保留摘要和文件引用路径。短期上下文超过阈值后，会启动上下文压缩机制，保留前 10% 和后 10%，中间 80% 全量外置，再用大模型压缩后写回短期记忆。

长期记忆主要存储任务长期经验。任务执行结束后，会对执行路径做大模型摘要抽取，比如任务类型、任务是否成功、成功规划步骤节点、失败 case 的失败步骤和原因，然后保存到长期记忆。使用时机是在第一次规划时，context builder 动态组装上下文，包括用户问题、问题定义上下文、平台操作历史、SOP 流程和长期经验。

## Q3. 长期记忆怎么避免污染

**问题：** 怎么避免长期记忆污染，比如把错误东西写进去，有没有回避或审核机制？

**回答：** 有准入机制。我们先抽取信息，然后有一个 LLM judge 的准入模块，通过泛化能力做评分。如果低于打分阈值就拦截，只有符合要求才写入长期记忆。

现在门槛设得比较高，分 5 档，只有 4、5 档才写入。评价标准主要是任务路径是否完整、执行路径规划结果是否清晰、最后结论逻辑链路是否合理。主要通过路径合理性和结论合理性做准入。

## Q4. 未达到长期记忆准入标准怎么处理

**问题：** 没达到准入标准通常是什么情况？这一段记忆怎么处理？

**回答：** 没达到标准的情况，一个是上下文里噪声太多，比如抽取了错误的执行节点；第二个是包含大量工具调用结果，信息抽取质量达不到评分条件。

现在只是做普通拦截。但我感觉这部分内容也可以做数据 dump，有样本之后可以做后置 debug case 或更新分析，做额外的系统分析工作。

## Q5. 摘要和 judge 用什么模型

**问题：** 做摘要抽取和 LLM judge 用的是什么模型？为什么选千问？

**回答：** 摘要主要用千问 235B，千问 3。LLM judge 也是同一个模型，因为摘要抽取和评判都需要比较强的泛化能力，所以更倾向用比较强的开源大模型。

选择千问 3，一是开源生态比较好，第二是逻辑推理能力和中文适配能力比较好。公司有模型调用 API。我们也做过小评测，构建大概 50 条路径，对主流模型做结构化摘要抽取，再人工打分。

## Q6. 怎么观测上下文污染或目标漂移

**问题：** 你们观测上下文污染，是指标观测还是使用体感？

**回答：** 两方面都有。真实 Agent 运行时，我们会显示执行调用路径，能看到整个执行路径慢慢有偏移的过程，这是使用体感。

指标上有工具平均调用次数。如果注意力丢失、目标漂移，平均调用次数也会增长。还会有最终链路评测，比较执行链路和 ground truth，筛出和黄金节点的 recall 和 F1 分数。分数越高说明越匹配，所以是离线和在线体感两方面评估。

## Q7. 参考过哪些业界 Memory 方案

**问题：** 设计四层记忆架构时，有没有看过业界 Memory 方案？

**回答：** 有参考一些开源方案。长期记忆看过 Zep 和 Mem0 的实现方式，它们也是基于抽取，并对长期记忆分类，比如事实记忆、事件记忆、procedure 程序化可复用经验。Zep 在长期记忆检测完成后也会做冲突检测、记忆更新机制。

第二部分是 Claude Code 这种任务类型上下文管理。虽然当时 Claude Code 还没有开源，但通过逆向工程和实践能看到它有 todolist 展示，也能看到工具调用结果外置和压缩的上下文管理机制。所以整体吸收了长期记忆和 Claude Code 任务类型上下文管理的思想。

## Q8. 自研四层记忆和社区方案差异

**问题：** 你们这套四层记忆和开源社区方案主要区别在哪里？

**回答：** 我理解我们更加特质化。长期记忆那块，开源方案已经封装好了准入机制，用户适配手段可能少一点。Claude Code 做得更精细，我们这块更倾向做工具调用数据、文件管理，以及中间任务状态管理。整体思想是类似的，区别不是特别大。

## Q9. Agent 开发优化的评测工作流

**问题：** 上一个功能后，你们会做哪些事情来评估好不好，接着怎么优化？

**回答：** 我们有离线和在线两个评测。新优化功能开发完成后，先做离线评估，包括黄金测试集结果准确性评估、工具调用链路效率评估。

以问题诊断场景为例，有 100 个问题诊断 case，既包括主因辅因，也包括执行路径 label。回跑后计算归因诊断 F1 得分，同时用 LLM judge 评判推理逻辑合理性，再看执行链路效率和准确性。

离线指标优于 baseline 后，会做 AB 推流实验。线上有用户点赞踩和采纳度指标，借助 AB 平台分发到用户，基于用户反馈观测线上效果。多个 feature 会做消融实验，看单一因素影响程度。

## Q10. 能否把观测、评测、优化流程自动化

**问题：** 现在有可观测和测试基础，能不能把观测、评测、定位问题、优化流程更自动化串联起来，让 Agent 更快迭代？

**回答：** 理论上可行，有点像 auto research 或自进化。需要建设基础设施。

第一步要有全链路执行数据，这是数据基础。第二步需要诊断模块。上了一个 feature 后自动跑评估，评估后用诊断 Agent 看评分是否达到预期。如果不符合预期，定位问题在哪里；如果达到预期，也看执行路径有没有不符合预期的情况。

拿到诊断信息后，再基于优化 Agent loop，把执行路径、诊断信息和调整策略作为上下文，让优化 Agent 做对应优化。比如发现 prompt 哪里设置不好，就针对性优化，优化后继续复跑 eval，再做 run 和 optimization，形成三阶段 loop。

## Q11. 做自进化机制需要多久、分几阶段

**问题：** 如果要做这个自进化和自动迭代，大概需要多久，投入多少能力，分几个阶段？

**回答：** 首先要把一版机制先跑通。第一版机制拉通出来还好：把长程任务所有工具执行数据 dump 下来，开发诊断 Agent，基于评测指标做对应诊断，这是必要项。

有诊断结果后，再做策略优化 Agent。我觉得搭整体 workflow 时间会比较少，但如果要让系统真的 work，就涉及到优化诊断准度和策略优化有效性，这两个方面要花时间。

最底层的东西是评估黄金测试集一定要非常公正和客观，因为它是所有反馈信号的基座。

## Q12. “主动策略洞察”是什么意思

**问题：** 简历里写从被动信息查询向主动策略洞察，主动策略洞察怎么说？

**回答：** 这个是基于归因诊断逻辑，给到信息的主动补充以及优化建议。原来的被动信息查询是运营需要自己做很多数据查询。有了 Agent 后，Agent 可以主动给他做内容提取和推送。

这里我说的主动洞察，是运营使用系统后，通过诊断，Agent 给他比较完整的分析和建议。真正的 proactive 方向可以参考常驻型 Agent，一旦有状态，就可以做定时任务和主动挖掘。

## Q13. 从半自动到真正主动洞察要解决什么

**问题：** 真正的主动洞察、主动策略分析，需要解决什么关键问题？

**回答：** 首先要确定一个确实可以做主动数据洞察的场景，然后做拆分。

需要有信息输入，类似监控。拿广告场景来说，为每个广告组配备广告效果监控 Agent，定时拉取广告投放效果表现。一旦发现某个业务指标有明显异常，就通过异常理解模块判断指标是否真的异常、异常时间和方向。基于这些信息自动触发诊断 Agent。

整体就是基于数据监控、数据触发、数据处理信息 loop，做闭环交付。最后把策略优化方案给到运营，让运营获得主动式数据洞察。

## Q14. RAG 知识库冲突怎么处理

**问题：** RAG 从原始数据切分入库后，如果新增知识和已有知识库结论相违背，怎么保证知识库信息准确？

**回答：** 有时间冲突的场景，比如佣金政策在不同时间有不同版本。我们对所有 chunk 和文本加上时间戳元信息，在结果生成时检测 timestamp 冲突，在 prompt 里优先告诉它使用最新文本信息。如果发现冲突，可能生成风险提示警告。

现在整体知识方面还是采用 RAG 召回方式。

## Q15. AI Wiki 和传统 RAG 的优势、不足、差异

**问题：** 你听说过 AI Wiki 那套机制吗？和传统 RAG 相比，优势、不足和差异是什么？

**回答：** 从架构看，RAG 还是基于相似度匹配，包括语义相似度和文本相似度。天然缺陷是语义相关不表示真实文本一定相关。

AI Wiki 是渐进式文本信息查询，类似人类阅读方式，能够更精准找到和当前问题更匹配的文本信息。所以一定程度上文本准确性会好于 RAG 直接检索。

但随之而来是工程复杂性和查询耗时。RAG 检索很快，几十毫秒可以完成一次检索；AI Wiki 需要渐进式披露，先看大目录，再看细分子模块，多次检索会慢，token 消耗也更大。

另一个难点是文本存储和索引构建。向量索引库相对简单，AI Wiki 需要维护符合 LLM native 的文本组织结构，还要处理 Wiki 里的噪声、冲突、增量更新或全量编译。关键策略是在编译层最大程度保证原始信息无偏，只优化编译逻辑来维护知识库准确性。

## Q16. 知识检索和知识工程未来怎么看

**问题：** 你怎么看后续知识检索或知识工程的发展？

**回答：** 我感觉这是大趋势，未来肯定更加 LLM native。模型天生喜欢看文本，让它用向量检索方式其实不一定好。

后续不管内部场景还是外部数据，都希望有管理得非常好的知识库作为知识底座，通过上下文管理和知识检索做上下文优化，让模型在上下文里拿到最少的信息，但又能准确回答问题。

## Q21. 怎么了解模型边界

**问题：** 模型边界是通过什么了解的？

**回答：** 一个是对原理的理解。大模型本质是语言概率模型，在大量预训练文本上 predict next token。它的能力来自后训练目标对齐，包括 SFT、RLFT 这些多阶段后训练，让它获得代码生成能力、逻辑推理能力。

有了这层认知，就能知道模型智能边界在哪里，然后围绕边界设计脚手架：感官层包括数据输入、文件系统操作，后续可能接入现实世界传感器；工具层可能通过 MCP 接入更多工具，还需要工具优选机制；执行层要保证执行稳定性和状态管理稳定性，做到端到端结果交付。
