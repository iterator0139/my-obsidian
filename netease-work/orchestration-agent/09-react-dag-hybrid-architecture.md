# ReAct + DAG 混合编排架构

## 核心结论

不应在纯 ReAct 和纯 DAG 之间二选一：

> DAG/状态机负责全局控制，ReAct 负责局部决策。

工作流图提供依赖、并行、检查点、重试、审计和恢复；ReAct 处理节点内部的不确定性和动态探索。

## 分层规划

```text
任务目标
→ TaskSpec 与验收契约
→ 粗粒度任务图
→ 工作流调度
→ ReAct Agent 执行节点
→ 节点验证
→ 更新任务图
→ 任务级验收与交付
```

### 任务级

确定目标、输入、约束、风险、期望产物和验收标准。

### 流程级

使用 DAG 或状态机管理 Agent 依赖、并行、超时、降级、人工审批和任务恢复。

### 节点级

复杂节点内部使用 ReAct：观察 → 推理 → 行动 → 再观察，直到满足节点验收条件或触发失败分支。

## 适用边界

| 场景 | 推荐方式 |
|---|---|
| 用例生成 | 固定工作流 + 生成节点内 ReAct |
| 自动化脚本生成 | DAG 管理生成、编译、执行；ReAct 负责失败修复 |
| 冒烟测试 | 持久化工作流；测试 Agent 内部使用 ReAct |
| 探索性测试 | ReAct 为主，但受工作流预算、权限和终止条件约束 |
| 发布门禁 | 确定性状态机、规则校验和人工审批，不依赖自由探索 |

## 运行时要求

- 使用持久化状态机，不依赖对话上下文保存任务状态。
- 每个节点具备输入输出契约、前置条件、验收条件和失败分支。
- 支持检查点、局部重跑、幂等、超时、重试、降级和人工接管。
- ReAct 受到步数、成本、时间、权限和副作用边界约束。
- 节点完成必须经过验证器确认，不能由 Agent 自行声明完成。
- 根据执行观测动态追加、删除或替换后续节点。

## 最终架构分工

| 能力 | 负责组件 |
|---|---|
| 目标理解 | Task Compiler / Planner |
| Agent 选择 | Router + Capability Registry |
| 任务依赖与调度 | DAG / Workflow Runtime |
| 节点内探索 | ReAct Agent |
| 结果判断 | Validator / Oracle |
| 异常恢复 | Runtime + Replanner |
| 权限与副作用控制 | Policy Engine |
| 业务交付 | Result Aggregator / Delivery Adapter |

## 关键判断

纯 ReAct 的问题是状态、恢复、审计和成本不可控；纯 DAG 的问题是面对未知情况不够灵活。混合架构的原则是：

```text
确定的流程 → DAG / 状态机
不确定的步骤 → ReAct
执行异常 → ReAct 分析 + 工作流恢复
新分支 → 动态更新任务图
```
